### Interpretation of imprecise wording (CLAUDE.md: inputs may be casual)

- **"Pills"** = the `.badge` family (status, type, role, scope, warning chips), not removable chips.
- **"Slip to a new line"** = a control that sits beside text and wraps below it when the text is long. Wrapping is correct only when the *container* is narrower than the controls alone.
- **"Object action"** = an action on the whole record that is not a workflow step: Edit, Archive/Restore, Delete permanently, Export, Subscribe. **Workflow transitions** (Submit, Approve, Reject, Retire, Withdraw) are different: they depend on status and stay visible beside the status.
- **"Project codes … nested"** = each project gets its own short code used to qualify item codes; confirmed it does not concatenate down the tree (Q7).
- **"Forms"** = every create/edit form in a Modal, SidePanel or inline card, whatever its field count (Q13).
- **"Available"** (N12) = a module is *entitled* to the organisation by the server, *enabled* by the organisation, and *on by default for new projects*. These are three existing tiers (`OrganizationModuleEntitlement`, `OrganizationModuleEnablement.enabled`, `.default_project_enabled`); "all available on new installs" means all three default to on.
- **"Org pain points" / "org versions"** (N18) = organisation-level definition rows (pain point types, action types, ...) that a project inherits when it has none of its own.
- **"Active"** (N20) = the state a record reaches when it leaves draft and becomes usable (persona `active`, requirement `approved`, ...), whatever each type calls it; the per-type mapping is in Phase 16's review.
- **"Tags (aka keywords)"** (N22) = free-text labels on a record, not custom fields (typed, structured) and not categories (a fixed type).
- **"Scope"** (N26) = which records a search may look in: this project, every project the user can access, or a module-defined unit (in Compliance, one standard). It is not a filter on the results page, which narrows further.
- **"Context of the search"** (N26) = which *fields* are matched (any field a visible record type declares as searchable: ID, title, description, notes, comments, tags, ...), chosen from a searchable dropdown; not which project or type.
- **"Item of any type"** (N26) = every registered artefact type the user can view, plus projects themselves (Q26); not users or groups.
- **"ID"** (N26) = the record's human-readable code (`REQ-001`, qualified or not).
- **"Parent" / "children"** (N24) = ancestor and descendant projects along `Project.parent_project_id`; whether that means one level or the whole chain is Q22.

### Phase 12 — Container health check reports unhealthy on a working install (N11)

**Why:** an operator on a second device sees the app serving but a container reported unhealthy; monitoring and `depends_on: service_healthy` are only trustworthy if the probe matches reality. **Risk addressed:** false "unhealthy" (alert noise, blocked dependants) and its opposite, `/health` returning 200 while the database is down. **Outcome:** probes that agree with what users see on any host, IPv4-only, IPv6-first or dual-stack.

1. **Diagnose with evidence first.** Ask for, from the failing host: `docker compose ps`, `docker inspect --format '{{json .State.Health}}' <container>` (the last five probe outputs name the failing command and its error), `docker exec <frontend> getent hosts localhost`, and `docker exec <frontend> wget -qO- http://127.0.0.1:3000/health`. Ranked suspects: (1) frontend probe `localhost` resolves to `::1` and nginx listens on IPv4 only; (2) a slow host exceeding the 100-second retry budget during first-boot migrations (`HEALTHCHECK` has no `start-period`); (3) a monitor probing a path the reverse proxy does not expose (`/health` is not under `/api/`, see `docs/deployment.md`); (4) the MCP server or docs container rather than the app. Record the finding in `docs/decisions.md`.
2. **Fix (applies whichever suspect is confirmed, because all are cheap):** probes use `127.0.0.1` in `frontend/Dockerfile`, `backend/Dockerfile`, `mcp-server/Dockerfile`, `docs/website/Dockerfile` and `docker-compose.yml`; nginx gets `listen [::]:3000;` beside the IPv4 listener; every `HEALTHCHECK` and compose `healthcheck` gets a `start_period` (60s, backend 120s) so slow first boots do not burn the retry budget; keep the retry count.
3. **`/health` honesty.** Return HTTP 503 with the existing JSON body when the database is unreachable, so `curl -f` and load balancers see it. Keep the 200 body shape for healthy. Add a bounded timeout to the probe query so a hung database does not hang the check. `/metrics` unchanged.
4. **Docs:** troubleshooting page entry "container shows unhealthy but the app works" with the three commands above; `docs/deployment.md` and the website observability page mention the probe address.
- **Tests:** backend test that `/health` returns 503 and the degraded body with the database dependency forced to fail, 200 when healthy; a CI check (script) that every probe command in the Dockerfiles and compose files uses `127.0.0.1`, not `localhost`.
- **Done 2026-10-18 (notes).** Diagnosed on the local test stack (`localhost` is `::1`, services IPv4-only: suspect 1 confirmed). The IPv6 listeners were added too (user instruction, and a standing `CLAUDE.md` rule): nginx `[::]`, backend and docs dev server on `::`, MCP server on a pre-bound dual-stack socket. Details in `docs/decisions.md`.

**Why:** a new install shows few modules because each is opt-in per organisation, and the server admin has no UI for the entitlement and default levers the backend already has. **Risk addressed:** a feature set that looks absent; admins offered switches they cannot meaningfully use. **Outcome:** a fresh install has everything on; the server admin controls defaults and per-organisation availability from Server Management; nobody sees a module they cannot use.

```mermaid
flowchart LR
    S["Server: entitled to org?"] -->|no| H1["Hidden from org and project admins"]
    S -->|yes| O["Org: enabled?"]
    O -->|no| H2["Hidden from project admins"]

- **Server default module states (Q15, Q16).** New table `ServerModuleDefault(module_key, org_enabled, project_default_enabled)` (explicit-override-only, same pattern as `OrganizationModuleEntitlement`); `registry.is_module_enabled` and `resolve_default_project_enabled` fall back to it before the registry's `default_enabled`. - **Server Management UI (new "Modules" section, `ModuleAdministrator` or Server Admin):** (a) entitlement policy toggle (Open/Closed; exists as `PUT /system/module-entitlement-policy`); (b) default org module states grid (module × "enabled for new orgs" × "on for new projects"), with a "Apply to all organisations" confirm (Tier 2) that writes org rows; (c) per-organisation availability: pick an organisation, toggle entitlement per module, show the effective state and which tier decided it. Every change is audit-logged (`services/audit.py`) and covered by the access-control policy.
- **Hiding (N14, Decided by: User).** `GET /orgs/{id}/modules` omits non-entitled modules for non-server-admin callers; `GET /projects/{id}/modules` omits modules the organisation has disabled or has no entitlement for, and the sub-component lists follow. The project admin module list, project-module toggles and sub-component toggles render only what the API returns. Server admins calling the system endpoints see everything. A project that already holds an override for a now-hidden module keeps the row (re-enabling the module brings it back).
- **Existing orgs (Q15):** nothing changes automatically; the "Apply to all" action is the explicit route.
- **Module boundary:** no per-module code; the server table and UI iterate the registry. `org_creation_choices` seeding is unchanged (check at build time that it does not conflict with the new default).
- **Nested projects:** `ServerModuleDefault` is server-wide, not a project definition table; not applicable, recorded.
- **Tests:** resolution matrix (entitled/not × org enabled/not × server default × org override × project override) for module and sub-component; fresh-install bootstrap seeds all on, migration on an existing database seeds nothing; non-server-admin responses omit hidden modules, server admin sees all; audit rows for each change; Storybook for the Server Modules section; Playwright for the full path (server admin withdraws a module from an org; the org admin and project admin no longer see it).

### Phase 18 — Tags on every item type (N22)

**Why:** items need lightweight, cross-cutting classification (a theme, a release, a regulation) that no fixed field covers. **Risk addressed:** tag sprawl and near-duplicates, an unfindable folksonomy, tags that bypass project permissions. **Outcome:** tags on any item, a governed vocabulary, filters in every list, and the tools to keep it tidy.

    P -->|"click"| O["open_target page<br/>via artefactPaths"]
```

**Header box (Decided by: Agent, from the user's sketch).**
- A search field in the top bar immediately left of the notification bell, with the **scope selector always attached to it** (a compact "This project ▾" control inside the field's left edge), not appearing only once typing starts. Reason: a control that appears mid-typing moves the layout under the cursor and hides the fact that scope exists; always-visible costs about 120px.
- **Scopes are a registry, not a fixed list** (**Decided by: User**, 2026-10-18; mechanism Decided by: Agent). Core ships two built-in scopes, **This project** and **All projects**. Any module may register more (Compliance registers **This standard**; another module could register, say, one library or one engagement programme) through a generic extension point on both sides, so no core file names a module or a module's scope:
  - Frontend: `TierAModuleDefinition.searchScopes: [{ key, label(ref), narrowness, match(pathname) -> { refId } | null }]`. `match` says whether the current page is inside that scope's unit and returns its id; core calls every registered `match` and renders whatever matches (the same render-prop/callback convention as `routes` and `orgAdminSections`).
  - Backend: `ModuleDefinition.search_scopes: dict[key, SearchScope]` where `SearchScope.resolve(db, caller, ref_id) -> ScopeResolution | None` returns the project id set the unit spans and, per artefact type, an optional extra restriction on that type's query (for a standard: its clauses and versions only). `None` means "not found or not allowed", answered identically either way, so a ref in another organisation or one the caller cannot read reveals nothing. Types the resolution does not list are not searched in that scope. The module's own enablement gate applies first, so a scope from a disabled module is neither offered nor accepted.
  - URL and API carry `scope=project`, `scope=all` or `scope=<module_key>:<scope_key>:<ref_id>`.
- **The default scope is the narrowest scope that matches where the user is when they start typing** (**Decided by: User**). Each scope declares a `narrowness` (built-ins: All projects 0, This project 100; a module scope declares its own, defaulting to 200, since a unit inside a project or organisation is usually narrower). Core picks the highest `narrowness` among the scopes whose `match` succeeds, so on a standard's pages the default is This standard, in a project it is This project, and elsewhere All projects, and a future module scope slots in with no core change. The user can widen it from the selector, which lists every matching scope plus the broader built-ins; the organisation choice (multi-organisation users only) is a filter, not a scope.
- Submit by **Enter or a visible Search button** (a `<form role="search">`, so the button is also the accessible submit). Shortcut `/` focuses the box (not while typing in another field); `Esc` closes the dropdown, then clears and blurs. Empty query does nothing; the box keeps the last query and scope when the results page is open.
- **Live dropdown (Q27, Decided by: User; details Decided by: Agent).** Under the box, the top 8 results for the current scope and default fields, grouped by record type, each row with code, title, project label and type badge, and a footer "See all results for ‘q’" that opens the page. **Anti-flicker rules:** (1) a 300ms debounce after the last keystroke, and no request under 2 characters; (2) a new request aborts the in-flight one (`AbortController`) and a late response is discarded if the query has since changed; (3) while a request is in flight the **previous results stay on screen**, dimmed slightly, and are replaced in one render when the new ones arrive (never cleared to a spinner or an empty state between keystrokes); (4) a small inline spinner in the field, shown only if a request takes longer than about 250ms; (5) results already fetched for the same query, scope and fields are reused for the session’s next few minutes, so backspacing does not refetch; (6) "No results" appears only after a completed request for the current query. **Keyboard/a11y:** the ARIA combobox pattern: arrow keys move through results, Enter on a highlighted result opens it, Enter with nothing highlighted opens the page, Esc closes; results announced to screen readers through a polite live region (count only, not per keystroke). The dropdown uses the same endpoint, authorisation and logging rules as the page, so the only extra load is the debounced requests, bounded by the rate/timeout rules below.
- Narrow widths: the field collapses to an icon button that opens it full-width; the scope selector stays inside it.

**Search page `/search` (Decided by: Agent).** Full state lives in the URL (`q`, `scope`, `types`, `orgs`, `projects`, `fields`, `archived`, `sort`, `page`) so a search can be shared, bookmarked and reached with Back. The API call is a POST (below), the URL is only client routing.
- **Filters** (shared `FilterPanel`, layout per the style guide): **organisation (only when the user belongs to more than one)**, record type (multi-select, each option with its result count), project (multi-select over the scope's allowed projects, nesting shown; reuses Phase 20's resolver and project label), status (through each type's label map, never raw enums), "include archived/retired" (off by default, as the link finder), and updated-between dates. Type counts come back with the results so the filter shows only types that matched and the user may view.
- **Search in (fields):** a **multi-select dropdown with its own filter box** (the shared searchable multi-select; build or reuse one, per the shared-component rule), because the union of fields across all types is long. Options are the fields the visible record types declare as searchable, merged by key and label so common ones appear once (*ID*, *Title*, *Description*, *Comments*, *Tags* after Phase 18) and type-specific ones keep their own name (*Rationale*, *Mitigation*, *Acceptance criteria*, ...), each with a muted hint of which types carry it. **Default selection: ID, Title, Description** (**Decided by: User**). The dropdown shows only fields of types the user can view in the current scope. A record type is searched on the selected fields it has; a type with none of them is not searched, and the page says so in one line ("Not searched: Risks (no selected field)") so a type is never silently missing. The selection is URL state, carried from the header dropdown to the page, and not persisted as a preference.
- **Match mode:** *Contains* (default, case-insensitive, all words must match, in any order) and *Exact phrase*. Regular expressions were considered and dropped (**Decided by: User**, 2026-10-18); nothing in the design needs a pattern engine, and dropping it removes the ReDoS and timeout surface.
- **Results:** ranked list (relevance tiers: exact code, code prefix, title, other fields; ties by most recently updated; a `sort=updated` option), one `ItemRow` (Phase 3) per hit: type badge, code through `RecordCode` (Phase 6, qualified outside the current project), title, status badge, muted project label, and a **snippet** of the first matching field with the match highlighted. Snippets only ever come from fields the user could read on the record's own page. Paged (25 per page); the total is shown as exact up to 500 and "500+" beyond, and paging deeper than 500 is refused with a prompt to refine, so merge cost is bounded.
- **Opening a result:** the click goes to the record's page through the existing `artefactPaths`. Some types have no page of their own, or belong to a parent: an engagement finding opens its **engagement**. The provider returns `open_target = {artefact_type, id, anchor?}` (the finding's own type and id when it has a page; otherwise the owner's), and the frontend resolves it with the target type's `artefactPaths` entry plus an optional anchor so the page scrolls to the matched record. A backend test fails when a searchable type has neither its own path nor an `open_target` rule, so no result can be a dead row (same coverage-test idea as `browse_levels`). Ctrl/Cmd-click opens a new tab (rows are real links).
- Empty and error states: no results (suggests widening scope, dropping filters, or searching more fields), too-short query, timeout ("narrow the search").

**Backend (generic extension point, Decided by: Agent).**
- `ModuleDefinition.search_providers: dict[artefact_type, ArtefactSearchProvider]`, beside `ArtefactSummaryProvider`. A provider declares `fields` (`key`, a user-facing `label` and a SQLAlchemy column or expression; keys and labels shared across types, such as `id`, `title`, `description`, merge in the dropdown; **opt-in per field**: nothing is searchable by default, so Restricted-classified or consent-sensitive columns are excluded by omission), a base query restricted to a project (and to an optional module scope ref), `open_target`, and summary data for the row. Core types (requirements, actions, change requests) register through the same mechanism in core, not a special path. Registration is a **hard requirement of a new artefact type**: a coverage test fails for a registered type with neither a provider nor an explicit `not_searchable` reason (a CLAUDE.md agent rule is added with the phase, beside the codes rule).
- `POST /search` (body, not query string: see Logging). Service `services/search.py`: (1) resolve the scope once (This project: self; All projects: every project the caller can read across their organisations, narrowed by the optional organisation filter; a module scope: its `SearchScope.resolve`, giving the project set and the per-type restrictions), using Phase 20's `project_hierarchy` resolver, cycle-safe and capped; (2) drop projects where the caller lacks read; (3) per type, drop it where the module or sub-component is off in that project or the caller lacks `view` (FGAC) there, identical to the link finder; (4) run each provider's query with the project set, field set, match mode and filters, fetching `offset + limit` rows per type; (5) merge, rank and slice. Org-scoped types (personas, stakeholders, ...) respect per-project hiding through the owning module's visibility rule, the same one `get_many_in_project` uses. **Omit, never redact**: a hit the caller cannot fully see is not returned, so counts do not leak either (type counts are computed after authorisation).
- **Projects as results (Q26):** a built-in provider over projects the caller can read, matching name and code.
- **Performance (Decided by: Agent):** query-time search per type, not a central search index. A central `search_document` table would make ranking and paging simple, but it adds a second copy of every record's text that erasure, hard delete, per-project hiding and permission changes would each have to reach, which is the class of defect this phase most wants to avoid. Revisit if measurement says no: first add `pg_trgm` GIN indexes on the title and code columns of the large tables (one migration, no behaviour change). Phase work includes measuring on the e2e seed plus a generated large dataset and recording the numbers in `docs/decisions.md`. Bounds: minimum 2 characters, per-type row cap, a per-search `statement_timeout` (5s, one setting; a timeout answers "narrow the search"), and the project-set size cap. The live dropdown adds a lower limit (8 rows) so its queries stay cheaper than the page's.
- **Logging and SOC 2 (Decided by: Agent):** query text may hold anything a user pasted, so it is **never written to application logs, audit events or traces** (those record the scope, field keys, match mode, result count and duration); the API takes a POST body so reverse-proxy access logs, which Alloy ships to Loki, do not carry it. The SPA route `/search?q=...` can appear in the frontend server's access log on a hard load or refresh; the phase checks the nginx log format and drops the query string there if it does. A search is a read, so it writes no audit event (consistent with other reads); because the dropdown multiplies request volume, per-user rate limiting reuses the platform's existing limiter if there is one (otherwise the debounce, abort, timeout and caps are the bound and the gap is recorded in the access-control policy). Consult the access-control and system-operations policies first.
- **MCP:** one `search_records` tool (query, scope, organisations, types, fields, match mode, limit) over the same service, so an agent finds records without crawling every list. `mcp-server/skill/reqtrack-mcp/SKILL.md` and the generated reference update in the same change (CLAUDE.md MCP rule).
- **Nested projects / groups:** no new project-scoped definition table, so no fallback decision is needed; scope and project filter use the existing hierarchy. No person field is added; an "owner/assignee" filter is not part of this phase (the filter would need principal support for groups, so it is recorded as a follow-up in `docs/decisions.md` rather than shipped user-only).
- **Not done:** saved searches, search history, regular expressions, searching file contents or attachments, fuzzy or stemmed matching, users and groups as results (Q26), highlighting inside the record page after opening.

**Sub-phases (each shippable):** 23a backend service, provider registration, the core and existing-module providers, coverage and isolation tests, measurement; 23b header box with live dropdown, `searchScopes` registration, search page, filters, field picker; 23c Compliance registers "This standard" through the scope registry (the first user of it), MCP tool, docs website page, seeds.

**Tests:** backend: coverage (every registered type has a provider or a reason; every searchable type resolves an open target), isolation matrix (another organisation, a project without read, module off, sub-component off, FGAC `view` missing, a hidden org persona, archived, a record the caller can see only in another project), scope resolution on a three-level tree, per-field opt-in (a non-declared column is never matched), Contains/phrase semantics, the default field set (ID, title, description) and a type with no selected field reported as not searched, the organisation filter present only for a multi-organisation user, cross-organisation isolation (a user in two organisations sees each organisation's records only through that organisation's gates), the timeout, pagination merge order and the 500 limit, `open_target` for a finding, a registered module scope (the Compliance standard) restricts to its own types, rejects a foreign organisation's or unreadable ref identically to a missing one, and is refused when its module is off; default-scope selection by `narrowness` using a test-only scope; a boundary test that no core file names a module scope; no query text in logs (caplog), query-count bound independent of result size. Storybook: header box (each scope, keyboard, narrow), live dropdown (loading with previous results kept, empty, error), search page (results, empty, many filters, long titles, qualified codes), scope selector, field picker (long list, filtered). Playwright: type and Enter, change scope, filter by type and project, pick extra fields in the filterable field dropdown, default scope inside a project and inside a standard, the dropdown not flickering to empty while typing (debounce, kept previous results), organisation filter visible only for a two-organisation user, click a finding and land on the engagement, "This standard" inside a standard, a user without access to a project never sees its records.

### Phase 24 — Record codes in reports, CSV and PDF exports, bundles and embedded references (N7, N27)

**Why:** a person reading a report, a CSV opened in a spreadsheet or a printed PDF cannot name a record to a colleague, and cannot tell two records with the same name apart, because these outputs still show titles only. Phases 6 to 8 flagged this three times. **Risk addressed:** the same inconsistency the record-code pattern was written to stop (every output formatting, or not formatting, its own code); a code leaking in a form that ignores the organisation's switch; a bundle that matches records by a code an import renumbers (the Phase 7 defect). **Outcome:** every output that names a record shows its code in the same form the screen would, through one shared formatter, and a new report cannot skip it unnoticed.

- **Inventory first (a step, recorded in `docs/decisions.md`):** every report (`ReportDefinition` section, table column, figure label), CSV and PDF export, project and organisation bundle export, MCP tool result and embedded reference in an API response (`RepresentedPersonaOut`, held needs, `StakeholderGroupRefOut`, change-request and review rows, notification text) that names a record. Classify each: shows a code already / needs one / exempt (with the reason, for example a figure axis, or a record whose type is exempt from codes).
- **One formatter (the 85-file problem):** a server-side `services/codes` helper that takes a record's code and its owner (project, or organisation for an organisation-owned record) and returns the display form by the same rule as `utils/recordCode.ts`: an organisation-owned record or a record from another project is always qualified; a record in the report's own project is qualified when the organisation enforces it. A report is a single-project, single-run output, so the requesting person's preference is **not** applied (Decided by: Agent, carried from Phase 6), which keeps a saved or scheduled report reproducible. The report framework passes the helper to each section builder, so a module report calls it rather than formatting. Frontend report views render the server's string, not their own.
- **A guard against regression:** a test over the report catalogue that every registered report's rows for a seeded record contain that record's code (the coverage-test pattern used for search providers and link finders), and a `CLAUDE.md` rule that a new report column naming a record uses the formatter.
- **Embedded references:** add `unique_code` (and the owner code where the record may be organisation-owned) to the small reference schemas listed above, and show it through `ScopedRecordCode` in the chips and rows that use them. These are additive fields.
- **Bundles and CSV:** a CSV gains a Code column (or a code-led label) wherever it has a name column; a bundle export carries each record's code as informational data only, and an import still numbers records afresh and still matches references by title (`label_title`), never by code. Spreadsheet formula-injection protection is kept: a cell now begins with the code, so the existing test that a title starting `=` is neutralised is re-checked.
- **MCP:** tool results that return records carry the code where the record has one; update the skill and regenerate the references (`mcp-server` and module tool references).
- **Not done:** rewriting codes inside free text (comments, descriptions that quote a code); changing how an import numbers records.
- **Tests:** backend per report and export (the code appears; qualified for an organisation-owned record and for a record from another project; the organisation's enforce switch on and off; the person's preference ignored); coverage test over the catalogue; bundle round trip unchanged by codes (import numbers afresh, references still resolve by title, two records with one title still handled as before); CSV formula neutralisation with a leading code. Storybook for each report view and chip that changed. Playwright: one report per module opened and downloaded as CSV, asserting a code column; an organisation-owned Persona chip on a Stakeholder shows `ACME-PER-001`.
- **Sub-phases (each shippable):** 24a inventory, the shared formatter and the report framework hook, plus core reports; 24b module reports (Context & Strategy, Stakeholders, Decisions, Risks, Compliance); 24c CSV, PDF and bundle exports, embedded references, MCP, docs, seeds.

## 6. Risks

| Risk | Mitigation |
|------|------------|
| Plan archive breaks hundreds of references | Mechanical rewrite, link checker in CI, review by count. |
| Pill/row sweep changes layout in unexpected places | Measure first; geometry check; `.row` is not changed globally. |
| Project-code backfill collides or produces ugly codes | Deterministic collision suffix; admins can edit before the policy is tightened; backfill tested on the demo and e2e datasets. |
| Org-scoped codes leak across organisations | Counter keyed by organisation; cross-org isolation tests. |
| Activity endpoint exposes data or misses events | 9a coverage audit first; reuse the read gate; filtered projection; isolation tests. |
| Header/menu change breaks many Playwright specs | Grep the old buttons up front; update in the same phase. |
| Organisation code collides with a project code, making a qualified code ambiguous | Codes share one namespace per organisation; the uniqueness check covers both; tested. |
| Docs image built with the wrong base path, so internal links 404 | `baseUrl` is a build arg; CI smoke test requests a nested page at the configured path. |
| Forms sweep never ends | Rule-based inventory, signed off; batches; user can stop between them. |
| Flipping module defaults switches modules on in live orgs | Fresh-install seeding only; server default table, not the registry constant; explicit "Apply to all" action (Q15). |
| Hiding modules from admins hides a module someone is still using | Hiding is display only; rows and data stay; server admin sees all; the module's own 404 gates are unchanged. |
| Health probe change masks a real fault | Probe still hits `/health`; `/health` now returns 503 on database failure; the diagnosis step records evidence before the fix. |
| Org-default tombstones diverge from the nested-project fallback | One resolver subtracts them; nested-chain tests; decision recorded before building (Phase 15). |
| Save and activate bypasses a separation-of-duties rule | Same permission and self-approval checks as the transition; atomic create plus transition; per-type review. |
| Quick-link leaves a record created but unlinked | Documented as valid state; Toast with retry; bulk call is atomic. |
| Tags become an unmanaged folksonomy, or leak across projects | Normalisation, restricted mode, merge and usage tables; tags carry the same read gate as the record; cross-project isolation tests. |
| Scope filter exposes or slows | Allowed project set resolved once and filtered by read gate and module enablement; omit, never redact; query-count test. |
| Help text written once and rotting | Text beside the labels in `strings.ts`, build-failing scan for missing `help`, reviewed in Phase 10 batches. |
| Search discloses a record the caller cannot open, or leaks via counts | Same project read, module and FGAC gates as the link finder, applied before querying; counts computed after authorisation; omit never redact; isolation matrix test. |
| Substring search, multiplied by a live dropdown, is slow or abused | 300ms debounce, abort of superseded requests, session cache, 8-row dropdown limit, `statement_timeout`, per-type row cap, minimum query length, 500-result depth limit; measurement recorded; `pg_trgm` indexes are the pre-agreed first remedy. |
| Cross-organisation "all projects" mixes tenants | Per-organisation gates; organisation label on every row; organisation filter for multi-organisation users; isolation test with a two-organisation user. |
| Query text leaks into logs, traces or Loki | POST body, logs carry scope/counts/duration only, caplog test, nginx query-string check. |
| A new module type is unsearchable or opens a dead page | Coverage test: provider or `not_searchable` reason, plus a resolvable open target; agent rule. |
| Scope: this is large | Phases 1–2 and 12–14 ship alone; each later phase is independently shippable; order above is the recommendation, not a dependency chain beyond the arrows. |
