# Decisions Log

This log records architectural and implementation decisions made while building ReqTrackManager to the **Ossa (v1)** and **Pelion (v2)** milestones defined in [docs/requirements.md](requirements.md). It exists so future contributors understand *why* the system looks the way it does, not just what it does. `docs/requirements.md` is authoritative and unchanged; this log explains how ambiguous or underspecified requirements were interpreted in code.

## Scope

Ossa (v1) implements every row in `docs/requirements.md` tagged `Ossa (v1)`, at both `Requirement` and `Recommended` priority. Pelion (v2) additionally implements every row tagged `Pelion (v2)`, built directly on top of the Ossa (v1) codebase (nothing from v1 was removed or restructured). Everything tagged `Massif (v3)` or `Murchison (v4)` was **not** built, including: task assignment/voting in change-request review, the standalone provisioning API/port, SSO/OAuth wiring, and IBM DOORS import/export. The "Pelion (v2)" section below records the scoping and implementation decisions made for that milestone; everything above it predates and still applies.

## Authentication and identity

- **Native auth now, SSO seam only.** `AuthBackend` (`backend/app/auth_backends/base.py`) is a small protocol with one implementation, `NativeAuthBackend` (email + bcrypt password). C-U-06/C-U-07 ask for pluggable backends and optional OAuth/SSO; actually wiring Keycloak/Authentica is Pelion-adjacent (E-U-01) and wasn't built, but the seam exists so adding a second backend doesn't require touching the rest of the app.
- **Login IP logging without geolocation (C-A-07).** Every login attempt writes a `login_events` row with the raw IP. Resolving IP → location was deliberately left as a nullable `location` column rather than calling an external geo-IP service at login time, to avoid a runtime network dependency and an API-key requirement in a self-hostable product. Follow-up: wire an offline MaxMind-style database when this becomes a priority.
- **Server admin bootstrap (I-M-05/06/08).** `backend/app/services/bootstrap.py` runs on every app startup (idempotent): creates the configured server-admin user if absent, and — if `SERVER_ADMIN_CREATE_ORG` is enabled — a default organisation with that user as org admin, matching the "on first install" wording without needing a separate CLI step.

## Roles and permissions

- **Fixed role vocabulary, not customisable permissions.** Ossa (v1) uses exactly the org roles (`org_admin`, `project_creator`, `member`) and project roles (`project_manager`, `project_administrator`, `stakeholder`, `member`) from C-U-01/C-U-03. Customisable permission schemes are a Pelion/Massif-era concern; project groups (C-U-11) are therefore just a way to bulk-assign one of these four fixed roles, not a general permission-authoring tool.
- **Project manager implies administrator + stakeholder.** Per the C-U-03 clarification, `get_effective_project_roles` (`backend/app/services/rbac.py`) folds `PROJECT_MANAGER` into also granting `PROJECT_ADMINISTRATOR` and `STAKEHOLDER` capabilities, and any assigned role implies baseline `MEMBER` (view) access.
- **Org admin ≠ automatic project content access.** The C-U-01 clarification ("no project access is guaranteed... apart from org admin being able to manage project settings") is implemented as two separate dependencies: `require_project_manage` (org admins pass) for settings/stage/component/group endpoints, and `require_project_view` (org admins do **not** automatically pass) for requirement/change-request content. An org admin who also wants to read requirements needs an explicit project role, same as anyone else.
- **Org-group nesting resolves one level deep.** A `ProjectGroupMember` row may point at a user or an org group (C-U-12); permission resolution flattens org-group membership into the containing project group's role. Cycle prevention is limited to not letting a group contain itself — deeper nested-group graphs aren't a requirement here and would add complexity with no described use case.
- **C-U-08/C-U-09 (must always have a manager).** Enforced two ways: `revoke_project_role` blocks removing the last direct project-manager assignment, and `deactivate_org_user` (in `backend/app/routers/orgs.py`) checks every project in the org after deactivating a user — if that removal leaves a project with zero managers, the *acting admin* is assigned as manager, matching the requirement's specific wording.

## Requirement lifecycle and change management

- **Identity vs. version split, not `valid_from`/`valid_to` on one row.** `solution-architecture.md` suggests temporal columns directly on core entities; in practice, `Requirement` holds only stable identity (project/component/category, generated code, creator, archival state) while `RequirementVersion` holds every mutable field plus `valid_from`/`valid_to`/`version_number`. The "current" version is the row with `valid_to IS NULL`. This gives the same point-in-time query capability with a simpler mental model: identity never changes, content always changes through a new version row. Change requests mirror the same pattern (`ChangeRequestVersion`).
- **Locking is per-requirement, not per-project-stage.** C-G-12 says changes are change-request-only "once a requirement is approved for a project stage." This is implemented as `is_locked` = the requirement's current version status is `approved` or `completed` — checked directly rather than by asking whether the project's current stage is approved. Approving a stage (`backend/app/services/baseline.py`) bulk-transitions every non-archived requirement still in `draft`/`reviewed` to `approved` and snapshots a `Baseline`/`BaselineItem` row per requirement (C-G-10) in the same transaction, so in practice stage approval and the lock happen together — but the lock itself is a property of the requirement, which is what C-G-12 actually says.
- **Unique requirement IDs (C-G-06/C-G-07).** `{component.prefix}-{category.prefix}-{project.next_requirement_seq:03d}`, e.g. `SW-PERF-014`. The sequence is a per-project counter that only increments, so archived requirements' numbers are never reused, satisfying the C-G-06 clarification.
- **Ordering is move-up/move-down, not drag-and-drop (C-E-01/02/03).** Each orderable entity (`ProjectComponent`, `ProjectCategory`, and a requirement's `sort_order` within its component/category) has a persisted integer position and a `/move` endpoint that swaps it with its neighbour. This satisfies the requirement without a drag-and-drop dependency in the frontend; requirement reordering is additionally blocked outside the scoping stage, per the C-E-03 clarification.
- **Discussion threads are not the change log (C-A-09 clarification).** `ReviewComment` (discussion, C-R-01) and `RequirementVersion`/`ChangeRequestVersion` (change log) are separate tables from the start, so the UI's change-log view never needs to filter comments out after the fact.

## Documentation contradiction: C-A-08 vs. notifications

C-A-08 ("date/time a notification was read must be recorded") is tagged `Ossa (v1)`, but the entire notification feature (C-N-01 through C-N-05) is tagged `Pelion (v2)`. There is nothing for a "notification read" event to attach to in v1. Rather than build a speculative read-receipt schema ahead of the feature it depends on, this was treated as a documentation dependency and deferred alongside notifications themselves — flagged here per the project's instruction to challenge assumptions rather than implement contradictory requirements literally.

## Reporting

- **ReportLab over WeasyPrint for PDF (R-F-01).** ReportLab is pure-Python with no system-level dependencies (WeasyPrint needs Cairo/Pango), which keeps the backend Docker image simple. Markdown pre/post sections (R-G-01/R-G-02) are parsed with `markdown-it-py` and walked token-by-token into ReportLab flowables (headings, paragraphs, bullet lists) — enough fidelity for introduction/appendix-style content without a full HTML rendering stack.
- **CSV export (R-F-02)** is a straightforward tabular dump of the same requirement rows used for the PDF table.

## Realtime

- **WebSocket pub/sub is in-process (I-A-04).** `backend/app/services/pubsub.py` is a single-process broadcaster; the endpoint is explicitly optional per the requirement text ("may expose"), and a single-backend-instance deployment is exactly what Ossa (v1)'s deployment model is. Scaling to multiple backend replicas would need a shared broker (Redis pub/sub or similar) — a natural extension point, not a v1 requirement.

## Infrastructure

- **Enum columns use `sqlalchemy.Enum(..., native_enum=False)`, not plain `String`.** An early version used `Mapped[SomeEnum] = mapped_column(String(N))`, which stores correctly but returns a plain `str` (not the enum) on read — anything calling `.value` on a freshly-loaded attribute would crash. `models/base.py::str_enum()` fixes this while keeping the column a plain VARCHAR (no Postgres `CREATE TYPE`/migration friction when adding a new enum member).
- **Migrations run automatically at startup (I-M-02/I-M-03).** `backend/app/migrations.py::run_migrations()` runs `alembic upgrade head` from the FastAPI lifespan handler before the bootstrap step. A fresh or upgraded deployment self-migrates on boot instead of requiring an operator to run Alembic by hand first and failing with raw "column does not exist" errors in the meantime.
- **One hand-written initial migration.** `alembic/versions/0001_initial.py` creates the schema via `Base.metadata.create_all()` rather than 22 transcribed `op.create_table()` calls, keeping the migration in lockstep with the models (the single source of truth). Future schema changes should be added as normal incremental Alembic migrations generated with `--autogenerate`.
- **Observability: metrics/health always on, Loki/Tempo/Grafana/Alloy opt-in.** The Ossa-tagged requirements (I-M health checks, Prometheus `/metrics`) are wired into the default `docker compose up`. The broader Loki/Tempo/Grafana/Alloy stack described in `solution-architecture.md` is architecture-level, not individually Ossa-tagged, so it's an opt-in Compose profile (`docker compose --profile observability up`) — the default stack stays fast to start. The backend does not yet emit OpenTelemetry traces; the Alloy config's OTLP receiver is ready to forward them to Tempo the moment that instrumentation is added.
- **i18n (U-U-02): a single string table, not a full i18n library.** `frontend/src/i18n/strings.ts` centralises every UI string behind a `t()` lookup. No second language ships in v1, but no component hardcodes text inline, so adding a translated locale is additive rather than a rewrite.

## Security hardening pass

After the initial v1 build, a dedicated hardening pass was run: two parallel vulnerability-scan sub-agents (backend; frontend/infra) proposed candidate findings, then each candidate was independently re-verified by a fresh sub-agent against a strict false-positive rubric before anything was treated as real. Five findings were confirmed and fixed; two were deliberately excluded as false positives. Regression tests for every fix live in `backend/tests/test_security_hardening.py`.

**Fixed:**

- **IDOR: requirement links/comments not scoped to project** (`backend/app/routers/requirements.py`). `create_link`/`list_links`/`add_comment`/`list_comments` validated the caller's role against the `project_id` path param but never checked that `requirement_id` actually belonged to that project — a member of Project A could read or write comments/traceability links on any requirement in Project B just by knowing its id. Fixed via a shared `_get_requirement_in_project` helper (also now validates a link's `target_requirement_id` the same way) that every such handler calls before touching the resource.
- **IDOR: change-request comments not scoped to project** (`backend/app/routers/change_requests.py`). Same bug, same fix pattern (`_get_cr_in_project`), for `add_comment`/`list_comments` on change requests.
- **Privilege escalation: project-group membership across projects** (`backend/app/routers/projects.py`). `add_project_group_member`/`remove_project_group_member` were gated by `require_project_manage` against `project_id`, but never checked that `group_id` belonged to that project. A manager of *any* project could look up another project's default "Project Managers" group id (visible to anyone with view access to that other project) and add themselves to it via their *own* project's manage-permission check, inheriting the other project's manager role. Fixed with `_get_group_in_project`.
- **Cross-tenant escalation: org-group membership across organisations, and cross-org group nesting** (`backend/app/routers/orgs.py`, `backend/app/routers/projects.py`, `backend/app/services/rbac.py`). Same missing-ownership-check pattern for org groups (`add_org_group_member`/`remove_org_group_member` didn't verify the group belonged to the `organization_id` in the URL), plus a related and more structural gap: nesting an org group into a project group (`add_project_group_member` with `org_group_id`) never checked that the org group belonged to the *project's own organisation* — an org group from a completely different organisation could be nested in, and `get_effective_project_roles`'s nested-group resolution would grant its members the project role regardless of tenant boundary. Fixed at both the write path (reject nesting a foreign-org group) and, as defense in depth, the read path (`get_effective_project_roles` now joins through `Project`/`OrgGroup` and only honours nested-group rows where the org group's organisation matches the project's organisation).
- **ReportLab markup injection (SSRF / local file read) in PDF reports** (`backend/app/services/reports.py`). `Paragraph()` from ReportLab parses its `text` argument as a restricted markup language (`<b>`, `<font>`, `<img src="...">`, etc.), not plain text. Requirement names/reasoning, the project name, and the custom pre/post Markdown report sections are all user-supplied and were passed to `Paragraph()` unescaped — a `<img src="file:///etc/passwd">` or an internal-URL `<img>` tag would be parsed as real markup and fetched/rendered server-side by ReportLab (whose pre-5.0 default `trustedSchemes` include `http`, `https`, and `file`), any project member being able to trigger it via the report-generation endpoint. Fixed by escaping (`xml.sax.saxutils.escape`) every user-controlled string before it reaches `Paragraph()` — table cells, the title, and rendered Markdown block content — so `<`/`>`/`&` always render as literal characters rather than being parsed as markup.

**Considered and excluded as false positives** (per the review's filtering criteria):

- *Unescaped `VITE_API_BASE_URL` in the generated `env-config.js`* — the value only ever comes from an operator-set `docker-compose.yml` environment variable, which is a trusted deploy-time input, not attacker-controlled; no path exists in this codebase for an external party to influence it.
- *Postgres port (5432) published to the host in `docker-compose.yml`* — at the time, this was the documented local-development quick-start compose file (alongside hardcoded dev-only credentials already flagged as "override in production"), so publishing the port was judged a defense-in-depth/hardening consideration rather than a concrete flaw. **Update (Pelion v2 infrastructure split):** the root `docker-compose.yml` is now the production-oriented stack, and no longer publishes the Postgres port at all — the dev/test stack that still does so (`tests/container/docker-compose.yml`) is unambiguously not production-facing, so this is no longer even a judgment call.

## Testing

- **Backend tests run against real PostgreSQL, not SQLite.** The schema uses Postgres-specific types (`UUID`, `JSONB`), so `backend/tests/conftest.py` creates a dedicated `reqtrack_test` database on the same Postgres server used by docker-compose, with tables truncated between tests rather than mocking the database.
- **A Playwright E2E suite (`tests/playwright/`) runs against the actual docker-compose stack** (not a dev server), exercising the full golden path in a real browser: login → create project → components/categories → requirement → stage approval (lock) → change request → PDF report → theme toggle. This is the only reliable way to confirm the shipped Docker images actually work together, not just that each service passes its own tests in isolation.

## Pelion (v2)

Pelion (v2) implements every row in `docs/requirements.md` tagged `Pelion (v2)`, on top of the Ossa (v1) codebase above. It reuses existing v1 architecture wherever possible (the identity/version split, the RBAC dependency style, the audit-event helper, the router/schema/service layering, and the frontend's `t()` string table) rather than introducing parallel mechanisms.

### Schema migration strategy

- **Squashed into the same `0001_initial.py` baseline, not a second migration.** Every Pelion v2 model change (new columns on `User`/`Organization`/`Project`/`RequirementVersion`/`ChangeRequestVersion`, and new tables for files/notifications/custom fields/favourites) was added directly to the existing models and folded into `alembic/versions/0001_initial.py`'s `Base.metadata.create_all()`, rather than written as an incremental `op.add_column`/`op.create_table` migration. This only works because `create_all()` reflects the *current* model state at the time it runs — attempting to layer a second migration on top produced "column already exists" errors, since 0001 would create the new columns too. This is a deliberate pre-release-only shortcut: there is no real production deployment yet to preserve data for, so squashing is safe. **The moment this system has a real deployed database that must be upgraded in place, all future schema changes must go back to normal incremental Alembic migrations** (`alembic revision --autogenerate`) rather than editing 0001 again — the docstring at the top of that file repeats this warning.
- **`tests/conftest.py`'s schema fixture now runs real Alembic (`run_migrations()`) against a `DROP SCHEMA public CASCADE`/`CREATE SCHEMA public` reset**, instead of calling `Base.metadata.create_all()`/`drop_all()` directly. The app's own startup path runs `alembic upgrade head` every boot (Ossa v1's I-M-02/03 decision); tests need to exercise that same path rather than a second, divergent schema-creation mechanism. Per-test cleanup uses a single `TRUNCATE ... CASCADE` statement rather than per-table `DELETE` in dependency order, because `use_alter`-based FK cycles (e.g. `users.avatar_file_id` → `file_assets` → `file_assets.uploaded_by` → `users`) make a strict deletion order impossible to compute generically.

### Files and storage

- **Pluggable storage backend, exercised for real via MinIO, not just implemented in the abstract.** `backend/app/storage_backends/{base,local,s3}.py` defines a `FileStorageBackend` protocol with `LocalFileStorageBackend` (filesystem) and `S3CompatibleFileStorageBackend` (boto3; works against MinIO or real S3), selected via `STORAGE_BACKEND=local|s3`. MinIO is added to the default `docker-compose.yml` stack and is the default backend, so I-M-10 ("must support different storage backends") is verified against an actual running S3-compatible service during manual and automated verification, not only against local disk.
- **A single `file_assets` table backs every upload use case** (requirement attachments, org shared resources, avatars, org logos) rather than one table per use case, since they all need the same metadata (storage backend, key, filename, content type, size, uploader). Requirement attachments additionally go through a `requirement_files` link table (many-to-many, so the same shared org resource can be linked to multiple requirements per C-M-04 without duplicating the file).
- **Local backend path-traversal defense in depth.** Storage keys are always generated by `app/services/files.py` (UUID-based), never taken from user input directly, so path traversal via a key isn't attacker-reachable in practice — but `LocalFileStorageBackend._path_for()` still resolves the path and checks `is_relative_to()` the base directory before any read/write, as defense in depth rather than relying solely on that invariant holding forever.
- **Disk-usage monitor (I-M-11) is a single testable function plus a thin timer loop.** `check_disk_usage_once()` in `backend/app/services/disk_monitor.py` contains all the actual threshold/dedup logic and takes the storage backend and prior warned-state as plain arguments; `run_disk_monitor_loop()` is just a 15-minute `asyncio.sleep` wrapper around it. This split exists specifically so the branching logic (warn once, don't repeat while still over threshold, re-warn after recovery) can be unit-tested (`backend/tests/test_disk_monitor.py`) without waiting on the real timer or touching a real filesystem's `shutil.disk_usage`.

### Notifications

- **In-process asyncio background tasks, not a separate worker service.** Both the instant-notification email path and the daily-digest batch job run as `asyncio` tasks started from the FastAPI lifespan handler, consistent with the existing single-instance WebSocket pub/sub pattern (`services/pubsub.py`). A dedicated worker service is a real future step (already called out in `solution-architecture.md`'s "Production deployment path") once a single backend replica stops being sufficient — not required for this deployment model.
- **MailHog as the default SMTP endpoint.** Rather than requiring a real mail provider to exercise C-N-01–05, the default Compose stack runs MailHog and points `SMTP_HOST`/`SMTP_PORT` at it, so sent notification emails are genuinely inspectable (http://localhost:8025) during development, testing, and manual verification — not just logged or mocked.
- **Notification triggers were added at existing call sites**, not as a generic event-bus: project-group join, stage transitions, change-request submit/decide, password change, and org-role permission grant. Permission *revocation* does not currently fire a notification — only grant does; this is a narrower interpretation of C-N-04 than might be expected and is a candidate follow-up if revocation notifications turn out to matter in practice.

### Customisation

- **Custom field values reuse the existing version-history mechanism instead of a second, parallel history system.** `CustomFieldDefinition` (project-scoped, `entity_kind` requirement|change_request) defines the schema; the actual *values* live in a plain `custom_fields JSONB` column added directly to `RequirementVersion`/`ChangeRequestVersion`. Every requirement/CR edit already creates a new version row (C-A-02/C-A-09), so custom field values automatically get the same point-in-time history for free.
- **A change request's `custom_fields` payload is validated against `CustomFieldEntityKind.REQUIREMENT` definitions, not `CHANGE_REQUEST` definitions.** These values represent proposed attribute values for the requirement being created/modified (mirroring `proposed_name`/`proposed_reasoning`) and are copied onto the requirement's version on approval — so they must be validated against the schema that governs requirements, not change requests. A separate `CustomFieldEntityKind.CHANGE_REQUEST` kind still exists in the data model for attributes describing the change request itself (e.g. an "urgency" field), but no workflow currently collects or consumes those values; this is a deliberate, documented scope gap rather than an oversight.
- **Terminology overrides are a fixed, closed set of keys, not a freeform key-value store.** `TERMINOLOGY_KEYS` in `backend/app/schemas/project.py` enumerates exactly the overridable nouns (project, stage, component, category, requirement, change_request); the update endpoint rejects unknown keys. An open-ended per-project vocabulary would require every frontend string to become dynamically templated, which is a much larger change than C-C-03 actually asks for.

### Templates

- **`clone_project()` deep-copies configuration and requirements, resetting workflow state.** Cloning a template project (C-E-05) copies components, categories, custom field definitions, groups and group memberships, and requirements (reset to `draft` status, with any project-specific custom field ids remapped to the new project's definitions) — but never copies change requests, comments, or audit history, since those describe the *history* of the template project, not a starting configuration for a new one.
- **PM auto-assignment has an explicit fallback when cloning.** C-U-10 says the creator is normally added to the Project Managers group automatically; C-E-05 says this doesn't apply when creating from a template (groups/members are copied from the template instead). If that copy leaves the new project with zero managers (e.g. the template's manager group had no members), the creator is still added as a fallback so C-U-08 ("every project must have a manager") can never be violated by a template that happens to be manager-less.

### Auditing and attribution

- **Creator reassignment (C-A-11/C-A-12) is restricted to project managers, checked server-side at creation time.** `POST .../requirements` and `POST .../change-requests` accept an optional `creator_id`; if present, the caller must hold the `project_manager` role (or be a server admin) or the request is rejected with 403 — anyone who can create a requirement/CR at all can still create one attributed to themselves, but only a manager can attribute it to someone else.
- **The project changes-over-time view (C-A-10) excludes discussion comments by default.** `get_project_changes()` merges audit events, requirement version history, and change-request version history into one timeline; `ReviewComment` rows are only included when the caller explicitly passes `include_comments=true`, consistent with the Ossa v1 decision that discussion threads are not the change log.

### UI discovery

- **Favourite projects sort ahead of everything else, then alphabetically.** `GET /api/v1/projects` computes the caller's favourited project ids and sorts the response with `(not is_favorite, name.lower())` as the key, so favourites always appear as a contiguous block at the top regardless of the `role`/`stage_status`/`search` filters also applied. Favouriting is a simple per-user join table (`FavoriteProject`) with `PUT`/`DELETE .../favorite` endpoints, not a field on `Project` itself, since it's user-specific rather than project-wide state.

### Logging

- **`alembic/env.py`'s `fileConfig()` call now passes `disable_existing_loggers=False`.** Migrations run automatically on every app startup (see Infrastructure, above), which means `logging.config.fileConfig(alembic.ini)` also runs on every startup, *after* uvicorn has already configured its own `uvicorn`/`uvicorn.error`/`uvicorn.access` loggers. `fileConfig()` defaults to `disable_existing_loggers=True`, which sets `.disabled = True` on every logger not explicitly listed in `alembic.ini`'s `[loggers]` section — silently killing uvicorn's access/error logging (and every `logging.getLogger(__name__)` logger elsewhere in the app) for the entire life of the process. This was a real, confirmed bug, verified via the raw container JSON log file having zero lines beyond the startup banner despite heavy real traffic. It also happened to be why the database bug below went undiagnosed for a while — there was no traceback to read. After the fix, `docker compose logs backend` shows a normal per-request access log and any real exception traceback.

### Database: the test suite was wiping the live database

- **Root cause: `tests/conftest.py` used `os.environ.setdefault("DATABASE_URL", ".../reqtrack_test")`, which is a no-op whenever `DATABASE_URL` is already set — and it always is inside the `backend` service container, to the real application database (`postgresql://reqtrack:reqtrack@db:5432/reqtrack`).** The test suite's session-scoped `_schema` fixture runs `DROP SCHEMA public CASCADE` / `CREATE SCHEMA public` at both session start *and* session teardown. Running the suite via `docker compose exec backend pytest` — a completely reasonable-looking command — was therefore dropping the real dev/demo database's entire schema twice per run, leaving it with **no tables at all** after the run finished (the teardown drop doesn't re-run migrations). The running app process kept its connection pool open, so it kept accepting requests, but every query then failed with `psycopg2.errors.UndefinedTable: relation "users" does not exist` — a hard 500 on every authenticated endpoint, while `/health`'s own lightweight check happened to still report OK. This was misdiagnosed at the time as a vague "connection pool wedge," fixed only by restarting the backend (which re-runs migrations and re-bootstraps the admin user, masking the real cause and quietly losing whatever demo data existed).
- **Fix: a hard startup guard in `tests/conftest.py`.** After resolving `DATABASE_URL`, the conftest module now asserts the resolved database name ends in `_test` and raises `RuntimeError` immediately if not, before the destructive session fixture can run. This makes the failure mode "the test suite refuses to start, with a clear error" instead of "the test suite silently destroys whatever database it happens to be pointed at." `setdefault` is still used first, purely as a convenience default for runners that haven't set `DATABASE_URL` at all.
- **Structural fix: tests run against their own isolated stack, not by `exec`-ing into the application container.** The root `docker-compose.yml` is now the production-oriented stack (no test database anywhere near it); `tests/container/docker-compose.yml` is a separate, fully isolated stack whose `backend` service's `DATABASE_URL` already points at `reqtrack_test` — so `docker compose exec backend pytest` there just works, with the safety guard confirming it rather than needing to catch a mistake.
- **The `_schema` fixture no longer drops the schema at session teardown, only at session start.** The teardown drop was redundant (the *next* session's own setup already guarantees a clean slate) and, once tests could share a database with a live app in `tests/container/`, actively harmful: it left that app's own backend with zero tables until its next restart. Removing the teardown drop means a live app sharing the test database instead finds its tables intact but empty after a test run (a clean `401` on login, since the bootstrap admin was truncated along with everything else) rather than a `relation "..." does not exist` `500`. `docker compose restart backend` (which re-runs migrations and re-bootstraps the admin) recovers it either way — this is a documented, expected part of using the shared dev/test stack for both manual testing and pytest, not a bug.

### Frontend component testing (Storybook)

- **Storybook (`frontend/.storybook/`) plus `@storybook/addon-vitest` for automated story tests**, not just a manual component browser. `npm run storybook` gives a visual explorer; `npm run test-storybook` runs every story as a real headless-Chromium test via Vitest's Playwright browser provider, so a story that fails to render or fails an assertion in its `play` function fails CI the same as any other test — a component explorer nobody automates checking against tends to silently rot.
- **The preview's `withTheme` decorator applies the exact same mechanism the real app uses** (a `data-theme` attribute on `<html>`, read by `src/styles/theme.css`'s CSS variables) rather than a Storybook-specific theming shim, so stories render with the actual product palette. A toolbar toggle switches themes while browsing; `LightTheme`/`DarkTheme` story exports pin `globals: { theme: ... }` explicitly so both are exercised by `test-storybook` on every run regardless of whatever theme was last selected in the UI (U-U-01: light and dark are both first-class, not just supported).

### Testing and verification process notes

- **The Docker Compose `backend` and `frontend` services do not bind-mount source** — they `COPY` the source at build time. Editing backend or frontend code and then testing against the *already-running* containers (`docker compose exec backend pytest`, or exercising the UI at localhost:3000) silently tests stale code until `docker compose build <service> && docker compose up -d <service>` is run. This tripped up Pelion v2 verification more than once (a backend test file and a frontend UI change were both validated against stale containers before the rebuild step was remembered) — worth calling out explicitly since the mistake produces no error, just misleading "it works" or "it's broken" signals from the wrong code.
- **Password-changing Playwright steps must revert via a direct API call in a `finally` block, not a second UI round-trip.** The new Pelion v2 E2E spec (`tests/playwright/tests/pelion-v2.spec.ts`) changes the shared bootstrap admin's password to exercise the password-changed notification, then must restore it, since `golden-path.spec.ts` and every future run depend on the fixed bootstrap password staying valid. Reverting through a second UI form submission proved flaky (a `page.reload()` issued immediately after clicking "Change password" can abort the still in-flight request before the browser sends it); reverting via `page.request.post(...)` with the token read out of `localStorage` is synchronous from the test's perspective and doesn't depend on any UI timing. The forward change also now explicitly awaits the `change-password` network response (`page.waitForResponse`) before doing anything else, for the same reason.
- **The favourites E2E assertion clears any pre-existing favourites via the API before asserting sort order.** Because favourite state persists in the shared dev database across repeated runs of the same spec, asserting "this project is now first" is only deterministic if the test first removes whatever an earlier run left favourited.

### Requirements audit fixes

A five-way parallel code-reading audit against every Ossa (v1) / Pelion (v2) row in `docs/requirements.md` found 23 real gaps (86 of 109 requirements were already fully met). All 23 were fixed in one pass; C-U-07 (a real OAuth/SSO backend) and C-U-15 (an actual multi-org membership operational path) were explicitly left as documented seams per the user's own scope call, since both are substantial new features rather than bug fixes.

- **I-M-05 (most significant fix): the server-admin role no longer bypasses any organisation/project data access.** Every RBAC dependency in `services/rbac.py` (`require_org_role`, `require_project_role`, `require_project_view`, `require_project_manage`) and every scattered inline `is_server_admin` check across `routers/{orgs,projects,requirements,change_requests,files,ws}.py` previously granted an unconditional bypass — directly contradicting I-M-05's explicit "does not give access to data within organisations" clarification. The fix is not a blanket removal: one dependency, `require_org_admin_or_server_admin`, exists specifically for the one documented carve-out (server admin creating the *initial* user of a newly created org, per I-M-05's own clarification) and is used only by `create_org_user`. `list_organizations`/`get_organization` deliberately keep a server-admin bypass since `OrganizationOut` is thin directory metadata (id/name/logo), not "data within the organisation," and the server admin needs to see an org exists to complete the one capability the requirement grants. Tests that relied on the old bypass to act inside a second org (`test_cannot_nest_org_group_from_another_organization`, `test_report_rejects_resource_from_another_organization`) were updated to create a genuine org_admin user in that org first, via a new `create_org_admin_in()` conftest helper — this mirrors the real deployment flow the fix now enforces rather than reintroducing a bypass.
- **A genuine, previously-undetected runtime bug was caught by configuring ruff (N-E-04): `services/rbac.py`'s nested-org-group-in-project-group role resolution used `OrgGroup` in a live query but never imported it**, so `get_effective_project_roles()` raised `NameError` whenever that branch executed — meaning C-U-12 ("organisation groups can be used inside project groups") was completely broken for its one legitimate scenario. No existing test exercised a valid same-organisation nesting (only the cross-org rejection case), so this shipped unnoticed. Fixed with the missing import plus a new regression test (`test_org_group_nested_in_project_group_grants_effective_role`) that actually exercises the nested-resolution path.
- **C-U-02 ("all project users must be an organisation user") is enforced with a small `_require_user_in_org()` check** in `assign_project_role` and `add_project_group_member` (routers/projects.py), rather than only being documented as design intent in a comment as before.
- **C-A-05 project-group audit logging now mirrors the org-group side.** `create_project_group`, `add_project_group_member`, `remove_project_group_member`, `assign_project_role`, and `revoke_project_role` all gained `log_event` calls; previously only the equivalent organisation-group endpoints did.
- **C-U-08's "a project must always have ≥1 manager" guard now also applies to group-based removal**, not just direct role revocation — `remove_project_group_member` checks `get_project_managers()` the same way `revoke_project_role` already did, using the same simplified "is this the current sole manager" check (not a full per-path simulation) for consistency with the existing logic.
- **C-N-01's `STAGE_SCOPING` notification now actually fires.** The type existed in the enum and the frontend string table but was never in `_STAGE_NOTIFICATION_TYPES`. Since a project's very first stage is created directly in `create_project()` (never through `create_stage`/`transition_stage`, the only two callers of the notify helper), every real caller of `_notify_stage_transition` is, by construction, never the "brand new project" case the requirement excludes — so adding the entry to the map was sufficient; `create_stage` was also updated to actually call the notify helper (and to log the real actor instead of `None`, a small pre-existing side gap).
- **C-E-04's org default-template setting now actually affects project creation.** `create_project()` falls back to `Organization.default_template_project_id` when the caller omits `template_project_id`; the frontend's "New project" form pre-selects the org's default in its template dropdown so the choice is visible and still overridable. Known limitation, documented rather than solved with a schema change: selecting "None (blank project)" in the UI sends the same `null` as never touching the field, so it currently still resolves to the org default when one is configured — a true override would need a distinct sentinel value in `ProjectCreate`, judged out of proportion for this pass.
- **C-U-16 (org admin locking a user's display name) gained the missing write path**: `PUT /orgs/{id}/users/{user_id}/display-name-lock` plus a lock/unlock toggle in the Org Admin users table. Enforcement already existed; only the ability to *set* the lock was missing.
- **I-M-06: a new `PUT /api/v1/system/users/{user_id}/server-admin` endpoint lets an existing server admin grant or revoke the role on another user**, matching the requirement's literal wording ("this user can assign any user on the system, the server admin permission role") — previously `is_server_admin` was only ever set once, at bootstrap, with no way to extend it afterward.
- **I-A-04: `WEBSOCKET_ENABLED` (default `true`) controls whether `ws.router` is mounted at all** in `main.py`, rather than it always being mounted with no way to disable it.
- **C-A-07 IP geolocation is implemented as a background task, not an inline call**, so it can never add latency to or block the login response. `services/geoip.py` resolves an IP's approximate location via a free, keyless third-party API (`ip-api.com`) only when `GEOIP_LOOKUP_ENABLED=true` (default `false`, since this is a real external dependency and privacy trade-off the user must opt into) and only for addresses outside `GEOIP_LOOKUP_EXCLUDE_CIDRS` (defaults to the standard private/loopback ranges). `routers/auth.py`'s `login` schedules `resolve_and_store_login_location` via FastAPI `BackgroundTasks` *after* the response is built, updating the `LoginEvent` row in a fresh DB session. Every failure mode (disabled, excluded address, network error, timeout) resolves to doing nothing — never an exception that could affect login.
- **U-P-06 pagination is opt-in, not a forced page size**, preserving C-G-05 ("no artificial limit"): the requirements/projects/change-requests list endpoints accept optional `limit`/`offset` and report the pre-slice total via an `X-Total-Count` response header (added to `CORSMiddleware`'s `expose_headers`, since custom response headers aren't visible to browser JS otherwise); omitting both still returns every match, unchanged from before. The frontend's three list pages use a new `api.getPage()` client method and a shared `<LoadMoreButton>` component for simple incremental "load more" pagination at 30 items/page.
- **U-P-05's file count is scoped to requirement attachments within the project, not organisation-wide shared resources** — `ProjectMetricsOut.file_count` counts distinct `FileAsset` rows reachable via `RequirementFile` for the project's own requirements, since shared resources aren't scoped to a single project and counting them would conflate two different things the requirement's "number of files in project" wording doesn't ask for.
- **C-C-03 terminology overrides are applied through a new `TerminologyProvider` React context** (`frontend/src/context/TerminologyContext.tsx`), fetched once per project and provided from `Layout.tsx` down to every page. Applied to the nav labels and the Requirements/Change-Requests page titles and "New X" buttons — deliberately not to every single occurrence of "requirement"/"stage"/etc. across the whole UI (dozens of call sites), which would be disproportionate scope for this pass. Pluralisation is a naive `+"s"` (`useTermPlural`), which reads correctly for the regular-noun default terms but not for an override with an irregular plural (a project would need to type the plural form directly as its override in that case).
- **U-U-03's landing preference is now actually read at login.** `LoginPage.tsx`'s `resolveLandingPath()` sends the user to a specific project id, the overview list, or (for "auto") the sole accessible project if there's exactly one — previously this was stored but login always hardcoded `navigate("/projects")`. The Preferences UI gained a "which project" picker for the specific-project case; `AuthContext`'s `login`/`verify2fa` now return the resolved `User` so the redirect can be computed immediately without waiting on a state re-render.
- **U-C-02: the organisation logo now renders in the app's main header**, not only on the Org Admin settings page, via the same `TerminologyProvider` fetch (extended to also carry `orgLogoFileId`) — shown next to the text wordmark whenever a project (and therefore an organisation) is in scope.
- **U-U-02: the flagged hardcoded strings were moved into the i18n table**, and one adjacent real bug was fixed in passing — the "new requirement" form's reasoning textarea was using the `status` placeholder string instead of `reasoning`.
- **I-M-04: `scripts/backup.sh`/`restore.sh` now also cover local file storage.** The root `docker-compose.yml` previously had no volume for `STORAGE_LOCAL_DIR` at all — despite `docs/deployment.md` already warning "this directory must be a persistent volume" — so a `STORAGE_BACKEND=local` deployment silently lost files on container recreation. Fixed with a named `reqtrack_local_files` volume, and `backup.sh` now archives it (`docker compose exec backend tar czf ...`) whenever the running backend's `STORAGE_BACKEND` is `local`, alongside the existing `pg_dump`. `STORAGE_BACKEND=s3` (the Compose default) is unaffected — MinIO's own backup/replication tooling is still the right approach there.
- **N-E-04/N-E-07: ruff (backend) and ESLint flat config (frontend) are now configured and pass with zero errors**, not previously configured at all. Both are intentionally mechanical gates (pycodestyle/pyflakes/import-sort/modernise/bugbear for Python; TypeScript + React Hooks + Fast Refresh recommended rules for TS) rather than exhaustive Google style guide enforcement — full docstring coverage (`D` rules) is deliberately not part of the ruff config; see N-E-05 below for why that's a separate, narrower pass instead of a repo-wide mechanical gate. `ruff`'s line-length is set to 150 (the codebase's existing max is 146) rather than the stricter 80-char Google default, to avoid a disruptive one-off reformat of already-written code. `B008` (function-call-in-default-argument) is disabled since it flags FastAPI's `Depends(...)` dependency-injection idiom, which is the correct pattern, not a bug.

Two nested FastAPI dependency closures got a one-line "see the enclosing factory's docstring" instead of a duplicate full docstring, since the enclosing `require_org_role`/`require_project_role` factory functions already fully document the returned closure's behavior.

## Multi-org, multi-persona E2E workflow suite

Full catalogue and rationale in [docs/e2e-workflows.md](e2e-workflows.md); summarized here for the decisions log.

- **Bulk seed data goes through the real API, driven by a standalone script, not direct DB writes.** `backend/scripts/seed_e2e_dataset.py` authenticates as personas and calls the same endpoints the UI does, so seeding exercises the actual validated code paths rather than risking a fixture that's inconsistent with real invariants (unique requirement codes, auto-PM-on-project-creation, etc.). Originally, one exception — deleting the zero-org server-admin persona's `user_org_roles` row directly via SQL — was needed because no product endpoint let a user leave an organisation at all. That gap is now closed (see the next bullet), so the script has zero direct-DB steps: even that persona's departure from its one org is now a real API call, `DELETE /orgs/{id}/membership`, which the seed script's own successful run exercises as a live test of the new endpoint.
- **Self-service "leave organisation" (`DELETE /api/v1/orgs/{organization_id}/membership`).** Found missing while building the E2E suite above; the user asked for it to be built once the suite was otherwise complete. Deliberately narrower than `deactivate_org_user`'s C-U-09 fallback (which reassigns the *acting admin* as a project's new manager when removing someone else): here the caller is the one leaving, so there's no natural recipient for an orphaned manager/admin role to fall back to. Rather than guessing who should inherit it, the endpoint refuses (409) if leaving would strip the org of its last `org_admin`, or leave any of its projects with zero managers, and asks the caller to reassign those roles first. Frontend: a "Leave organisation" button on `OrgAdminPage.tsx`, visible to any member of the org being viewed (not gated to admins, since any role can leave). Tests: `backend/tests/test_rbac.py`.
- **A server admin can only ever be the first org_admin of a *brand-new* organisation, never granted a role in an org they don't already belong to.** `create_org_user`'s server-admin carve-out (`require_org_admin_or_server_admin`, per I-M-05 above) only covers creating a new user; `assign_org_role` requires a genuine `org_admin` caller with no carve-out. This is existing, correct behavior — flagged here because it meant the seed script needed a throwaway "bootstrap helper" user as a second org's first admin, purely to hand off a role to the real persona, mirroring how a human admin handoff would actually work.
- **Change-request Approve/Reject and requirement Archive/edit-form visibility now check the viewer's actual project role, not just the entity's state.** Found while building the change-request approval-separation workflow: both controls were rendered for any project member once a CR was submitted or a requirement unlocked, relying entirely on the backend's 403 to stop the click — correct security-wise, but not a working workflow for the user who sees a button they can never use. Fixed with a new `frontend/src/hooks/useMyProjectRoles.ts` (reads `ProjectListItemOut.my_roles`, the cheapest existing source of this without a new endpoint) in `ChangeRequestDetailPage.tsx` and `RequirementDetailPage.tsx`. The same pattern likely exists elsewhere (e.g. the Requirements list's "New Requirement" button); left as a documented gap rather than a repo-wide pass, since only these two were exercised by this suite's own workflows.

### Full hardening/validation pass

A follow-up parallel security audit (three agents: backend auth/authz, backend input-validation/injection, frontend) covering the whole codebase, not just this session's diff, per the user's explicit request. Two real, high-confidence findings, both fixed and covered by new regression tests; everything else came back clean (RBAC/IDOR boundaries, JWT/session handling, file-path/SSRF/deserialization surfaces, and the frontend's DOM-sink surface were all specifically checked and found sound).

- **Stored XSS via unrestricted uploaded-file Content-Type served inline (High).** `GET /api/v1/files/{file_id}` (`backend/app/routers/files.py`) served every file with the uploader's client-claimed `Content-Type` (never validated against the actual bytes) and `Content-Disposition: inline` — any user with upload rights (a low bar: any project editor for requirement attachments, any authenticated user for their own avatar) could upload a `text/html`/`image/svg+xml` payload that executes as a same-origin page when a more privileged user opens the link, with immediate access to this same endpoint's `?token=` query-param auth and `localStorage`. Fixed by restricting `inline` disposition to a small safe-to-render allowlist (`image/png`, `image/jpeg`, `image/gif`, `image/webp`, `image/x-icon`, `application/pdf` — SVG deliberately excluded since it can embed scripts too) and forcing `attachment` for everything else, plus an `X-Content-Type-Options: nosniff` header on every response from this endpoint. Test: `backend/tests/test_files.py::test_html_attachment_is_forced_to_download_not_rendered_inline`.
- **CSV formula/DDE injection in the requirements export (Medium).** `generate_csv_report` (`backend/app/services/reports.py`) wrote user-editable requirement fields (name, reasoning, clarification, etc.) straight into CSV cells; a value starting with `=`, `+`, `-`, `@`, tab, or CR is interpreted as a formula by Excel/LibreOffice on open — and this export exists specifically for spreadsheet review (R-F-02), making that a realistic workflow, not a theoretical one. Fixed with a `_csv_safe()` helper that prefixes any such value with `'` (stripped from display, never executed) before writing, per OWASP's standard CSV-injection mitigation. Test: `backend/tests/test_reports.py::test_csv_report_neutralizes_formula_injection`.
- **`leave_organization` didn't clean up `OrgGroupMember` rows, and its sole-manager guard couldn't see nested-org-group-derived managers.** Caught during self-review of the new endpoint (not the parallel audit): project access can be granted through an org group nested into a project group (C-U-12), and `get_project_managers` deliberately only resolves *direct* managers (see its own docstring) — so the original implementation could let a user "leave" an org while silently retaining full project access, including manager rights, through a still-active, still-authenticated session (deactivation-based removal doesn't have this exposure, since `is_active=False` blocks all further API access regardless). Fixed by also deleting the caller's `OrgGroupMember` rows for the organisation's groups, and by extending the sole-manager check to fold in `get_effective_project_roles` (which does resolve nested groups) alongside the existing direct-manager check. Note: the "blocking" branch of this fix is currently unreachable through the API in practice — `revoke_project_role`/`remove_project_group_member` independently refuse to remove a project's last *direct* manager using the same nested-group-blind resolver, so a project can never actually reach "zero direct managers, one nested-group manager" today — but it's kept as correct defense-in-depth, documented in `backend/tests/test_rbac.py::test_last_direct_manager_cannot_be_revoked_even_with_a_nested_group_backup`.

### Round 2 hardening: races, session lifecycle, infrastructure

A deeper pass per the user's explicit "go deeper" request: business-logic race conditions, session/credential lifecycle, and infrastructure/config, plus re-examining prior areas more critically. Custom fields and the report data-flow were re-audited and came back clean (no new findings). All fixes below are covered by `backend/tests/test_rbac.py`, `backend/tests/test_user_security.py`, and the full Playwright suite; every backend test (141) and every Playwright spec (10) pass together against a freshly-reset database.

**Business-logic races (TOCTOU, closed with Postgres row locking via `.with_for_update()`):**

- **Change-request double-decision race** (`backend/app/routers/change_requests.py`). `decide_change_request` read the CR with a plain `db.get()`; two concurrent Approve/Reject calls on the same submitted CR could both pass the "is it still submitted" check before either commit landed, double-applying the decision's side effects. Fixed by selecting the row `with_for_update()` so the second concurrent request blocks until the first commits, then sees the now-decided state and is rejected.
- **Org/project manager-count races across four endpoints** (`revoke_project_role`, `remove_project_group_member` in `backend/app/routers/projects.py`; `deactivate_org_user`, and the new `leave_organization`, in `backend/app/routers/orgs.py`). Each independently counts remaining managers/admins before allowing a removal that would drop the count to zero, but without a lock, two concurrent removals of *different* managers could both read "count is 2, safe to remove" and both proceed, leaving zero. Fixed with new `lock_project_for_update`/`lock_organization_for_update` helpers in `backend/app/services/rbac.py`, called before each count check.
- **Stale-subscription content leak on role removal.** When a user's last role on a project was revoked (via any of the four endpoints above), their `Subscription` and `FavoriteProject` rows for that project's requirements/change-requests weren't cleaned up — since notification delivery doesn't re-check current access at send time, they'd keep receiving content updates for a project they'd just lost all visibility into. Fixed with `engagement.remove_subscriptions_and_favorites_for_projects`, called wherever a removal drops a user's effective project roles to empty.

**Session/credential lifecycle:**

- **No token revocation on password change or 2FA disable (High).** JWTs were purely stateless — changing your password (e.g. after suspecting a compromised session) or disabling 2FA didn't invalidate any token issued before the change; a stolen token kept working for its full remaining lifetime regardless. Fixed with `User.token_version`, an integer embedded in every token as the `tv` claim and checked for exact equality against the user's current value on every request (`app/deps.py`); `change_password`/`disable_2fa` increment it, deterministically invalidating every previously-issued token including the one used to make the change. A first attempt compared JWT `iat` against a `tokens_invalid_before` timestamp instead; it was rejected after testing turned up an inherent boundary bug — `iat` is only second-precision, so a token issued in the exact same second as its own revocation could compare as still-valid or (after truncating both sides to fix that) as already-expired-before-issuance, depending on which way the tie was broken. A version counter has no such ambiguity. Regression tests: `backend/tests/test_user_security.py::test_password_change_invalidates_the_old_token`, `::test_2fa_disable_invalidates_the_old_token`.
  - **Frontend fallout, found by re-running the Playwright suite after this fix:** `PreferencesPage.tsx`'s change-password/disable-2FA handlers kept using the now-dead token from `localStorage` for subsequent requests instead of expecting the session to end — the UI just silently broke (401s on reload) rather than prompting re-login. Fixed by having both handlers call `logout()` and redirect to `/login` with a "you've been signed out" message (`LoginPage.tsx` reads it from router state) immediately after a successful change, since the backend has already invalidated the session at that point regardless of what the frontend does.
- **Login response distinguished deactivated accounts from wrong passwords (Medium — user enumeration).** The login endpoint returned a distinct "This account is deactivated." message, and returned it *before* verifying the password — letting an attacker enumerate which emails are registered-but-deactivated accounts without knowing any password. Fixed in `backend/app/auth_backends/native.py`: password verification now always runs first (against a module-level dummy hash when the account doesn't exist or belongs to a different auth backend, to equalize timing with the real-account path), and every failure path returns the same generic `"Invalid email or password."`. Test: `backend/tests/test_user_security.py::test_login_error_does_not_distinguish_deactivated_from_wrong_password`.
- **WebSocket connections outlived their issuing token's expiry.** `backend/app/routers/ws.py`'s connection handler authenticated once at handshake and then held the connection open indefinitely — a token that expired mid-session kept a live, fully-privileged socket open. Fixed by decoding the token's `exp` claim at handshake and checking it every 60 seconds in the receive loop, closing the connection (code 4401) once it's passed. **Correction (later hardening review, see "Deep hardening review" below): this fix covered `exp` only** — it did not add a `token_version` check, so a password change/2FA-disable did not actually close an already-open socket as this entry originally (incorrectly) claimed. That's a separate, since-fixed gap; see below.

**Infrastructure/config:**

- **Weak default Postgres password in the production compose file.** Root `docker-compose.yml` fell back to a hardcoded `reqtrack` password if `POSTGRES_PASSWORD` wasn't set in the environment, in both the `db` service and the embedded `DATABASE_URL`. Fixed by switching both to Compose's fail-fast `${VAR:?message}` form, so a production deploy without an explicit password refuses to start rather than silently running with a guessable one. `docs/deployment.md` updated accordingly.
- **MinIO root credentials used directly by the backend.** The backend authenticates to MinIO/S3 storage with the root account rather than a scoped-down user — not auto-remediated (no code path to change), but documented as a deployment hardening step in `docs/deployment.md` with exact `mc admin user add`/`policy create`/`policy attach` commands to scope a dedicated bucket-only credential for production use.

**Re-audited, came back clean:** custom field value storage/rendering (no injection path — values are always parameterized or escaped the same way as other user content, per the round-1 ReportLab fix), the CSV/PDF report data-flow end to end (confirms the round-1 fixes still hold and no new sink was introduced since).

## Massif (v3)

Massif (v3) implements every Massif-tagged row in `docs/requirements.md` except the three enterprise-auth requirements each large enough to be their own project (E-U-01/E-U-02/E-P-02) — see below for how those were scoped instead. E-P-01 ("allow multiple organisations") required no new work: `Organization` has been a first-class multi-tenant model since Ossa (v1), and server admins have always been able to create additional organisations.

### Review scheduling (C-R-06, C-R-07, C-R-08, C-R-09, C-R-10)

`RequirementVersion` gains `review_date`, `review_lead_days`, `reviewer_id`, `review_reminder_sent_at` — placed on the versioned table, not the `Requirement` identity row, because C-R-06's clarification requires them to only change on creation or via a change request, the same CR-gated path every other content field already uses (`apply_new_version`/`create_requirement` in `backend/app/services/requirements.py` gained matching parameters, with the same `*_explicitly_set` disambiguation pattern already established for `target_stage_id`). A new `RequirementReview` table (`backend/app/models/requirement.py`) records outcomes (C-R-07); the "due for review" definition (`backend/app/services/reviews.py`) is `review_date` in the past *and* no `RequirementReview` recorded since that date — this lets a requirement drop off the due list once reviewed without ever mutating `review_date` itself outside a change request, satisfying the immutability clarification literally rather than by approximation.

A new APScheduler job (`backend/app/services/scheduler.py`, `send_due_review_reminders`) sends the C-R-08 reminder once per review cycle (tracked via `review_reminder_sent_at`, reset to unset on every new version so an unrelated edit can't suppress a future reminder), to the assigned reviewer or every project manager if none is assigned.

### Change-request tasks and stakeholder voting (C-R-02, C-R-03, C-R-04)

`ChangeRequestTask` and `ChangeRequestVote` (`backend/app/models/change_request.py`), both scoped to project-manager creation/decision rights except that a task's own assignee may toggle `is_done` without manager rights. Voting is explicitly advisory: `ChangeRequestVote` never touches `ChangeRequest.status`, and `decide_change_request`'s existing project-manager-only gate is completely unchanged — the vote tally is just additional visible input the decision-maker sees alongside the CR, per C-R-03's own reasoning ("promoting collaborative decision-making," not "replacing the decision").

### Stage review deadlines and "assumed approval" (C-R-05)

`ProjectStage` gains `review_deadline`; a new `StageReviewResponse` table records explicit stakeholder approve/reject responses per review cycle (cleared when a new deadline is set, so a later cycle isn't contaminated by an earlier one's responses). The daily scheduler sweep (`auto_approve_overdue_stage_reviews` in `backend/app/services/stages.py`) auto-approves a stage once its deadline passes, *unless* at least one stakeholder explicitly rejected — matching C-R-05's literal wording ("if they have not provided a response, then it's assumed they have approved") while never silently overriding a raised objection. This asymmetric policy (silence = approve, objection = block) was flagged to the user as the one substantive judgment call in the design and confirmed before implementation.

### Completion tracking (C-P-02, C-P-03)

`ProjectStage` gains `completed_at`/`completed_by` (mirroring the existing `approved_at`/`approved_by` pattern). Rather than adding parallel `is_completed` fields to `Requirement`, C-P-03 reuses `RequirementStatus.COMPLETED` — an enum value that already existed in the codebase (already locked requirement edits via `LOCKED_STATUSES`, already counted in dashboard/report status breakdowns) but had no dedicated endpoint reaching it. `POST /requirements/{id}/complete` transitions `APPROVED → COMPLETED` directly (bypassing the change-request requirement, like archiving already does, since this is a status transition a project manager makes directly rather than content requiring review) — "who/when" is captured by the resulting version's existing `created_by`/`created_at`, with no new columns needed. Stage completion (`POST /stages/{id}/complete`) takes an explicit `cascade_to_requirements` flag, defaulting to `false` per C-P-02's clarification.

### User directory with access-review filters (C-A-13)

Originally scoped as a dedicated "access review" endpoint; broadened during planning per explicit feedback into query filters (`stale_since_days`, `never_logged_in`, `has_2fa`, `org_role`, `has_project_access`) on the *existing* `GET /orgs/{organization_id}/users` member-listing endpoint, plus a new server-admin-only `GET /system/users` with `no_org_membership` (C-A-13's literal "orphaned account" clarification). Authorization was called out explicitly given this codebase's history of under-scoped org/project checks (see the round-1 hardening section above): the org-scoped filters require `require_org_role(OrgRole.ORG_ADMIN)` resolved against the specific `{organization_id}` in the path (not "an org admin somewhere"), while the unfiltered base listing keeps its existing member-level access; `GET /system/users` requires `require_server_admin` with no org-admin fallback of any kind and deliberately omits `org_role`/`has_project_access` from its response, since those only have meaning scoped to one organisation and would otherwise leak cross-tenant membership through a nominally tenant-blind endpoint (I-M-05). Negative-path tests for all three boundaries live in `backend/tests/test_access_review.py`.

### Selectable report templates (R-G-05)

R-G-05's row in `docs/requirements.md` has the same title text as R-G-04 but different reasoning (branding/presentation vs. shared-resource sections) — read as a documentation copy-paste artifact rather than a literal duplicate, confirmed with the user, who chose "selectable report templates" over the alternative reading of "just render the org logo." `ReportTemplate` (org-scoped, matching how the org logo already works) stores an accent colour, a cover-page toggle, a logo toggle, and footer text; `generate_pdf_report` (`backend/app/services/reports.py`) gained an optional `branding: ReportBranding` parameter threading these into the existing ReportLab styling, falling back to today's plain output when no template is selected.

### SSO login, tested against a real Keycloak instance (E-U-01, E-P-03)

See [enterprise-integration.md](enterprise-integration.md) for the full design. In brief: a real OIDC authorization-code flow (`backend/app/routers/auth_oidc.py`), provider-agnostic via standard discovery, tested end-to-end with a real Keycloak container in `tests/container/docker-compose.yml` and a Playwright spec (`tests/playwright/tests/e2e-workflows/sso.spec.ts`) that drives an actual browser through Keycloak's own login form — not just designed on paper, per the user's explicit instruction that this specifically be tested, not merely documented. The provisioning logic it's built on (`backend/app/services/oidc_provisioning.py`) is written to be reused directly by the not-yet-built SCIM path (E-U-02), so that blueprint isn't speculative.

A genuine Docker-networking problem surfaced during testing — the backend reaches Keycloak via the Compose-internal hostname, but a real browser can only reach the published port, and both must resolve to the *same* issuer URL for token validation to work — resolved via Keycloak's own hostname-pinning config plus a narrowly-scoped, dev/test-only backend setting (`OIDC_INTERNAL_BASE_URL_OVERRIDE`) that rewrites only the backend's own outbound calls, never anything the browser sees. Left unset (a no-op) in the production compose file, since a real IdP's public URL is normally reachable from the backend directly.

**Follow-up, same session:** added a per-org `oidc_required_group` access gate, deliberately separate from `sso_group_mappings` — the mapping list decides *which* role a successfully-admitted user gets, while `oidc_required_group` decides *whether* they're admitted at all, checked in `oidc_callback` before any local account is provisioned or token issued (`services/oidc_provisioning.meets_required_group`). A user outside the required group who authenticates successfully at the IdP is redirected to `/oidc-complete?error=not_provisioned` and shown "Your organisation has not provisioned you access." — the refusal is this app's own policy layered on top of a genuinely successful IdP login, not an IdP-side failure, so no re-registration is needed once an admin adds them to the group. Extended `sso.spec.ts` with two more real-Keycloak-driven tests (blocked user denied, admitted user still gets in) rather than only unit-testing `meets_required_group` in isolation, consistent with the standing instruction that SSO behaviour be proven against a real IdP. One implementation snag: the blocked-then-admitted flow was originally written as two `test.step`s sharing one browser context, which failed because Keycloak's own SSO session (not this app's) persisted across steps and silently reused the first (blocked) user's session instead of showing a fresh login form for the second user — fixed by splitting into two separate `test()` blocks, each with Playwright's default fresh browser context, matching the pattern the first two SSO tests already used successfully.

E-U-02 (SCIM) and E-P-02 (a separate-port provisioning API) were scoped out of this pass — each is effectively its own project — and are covered as an implementable blueprint in `enterprise-integration.md` instead, per the user's explicit choice during planning.

### Massif (v3) hardening pass

Following this project's standing security-review workflow (see the round-1 "Security hardening pass" section above), the new Massif (v3) code — chiefly the OIDC subsystem, since it's the largest new externally-reachable attack surface added this phase — was put through the same three-stage identify → independently re-verify → report process. Four findings survived at confidence ≥8; all four were fixed and the full verification sequence (184 backend tests, 14 Playwright specs including all 4 SSO tests) re-run clean afterward.

**SSRF via org-configurable OIDC endpoints (High).** `Organization.oidc_issuer_url` is set by an org admin, not a server admin, and every OIDC step (`discover`, the token exchange, JWKS fetch) makes an outbound HTTP call built from it or from values returned by *its* discovery document (`token_endpoint`, `jwks_uri`) — so a malicious discovery document could redirect later calls to an entirely different host than the one an admin configured. Fixed in `backend/app/services/oidc_client.py` with `_assert_safe_external_url`, called before every outbound fetch: resolves the hostname via `socket.getaddrinfo` and rejects any resolved address that isn't `ipaddress.is_global` (blocks loopback, link-local, private ranges, and DNS-rebinding-style redirects to internal services), not just a naive hostname-string check. Skipped only when `oidc_internal_base_url_override` is configured (the dev/test-only Keycloak-networking escape hatch above), since that setting exists specifically to point the backend at an internal, non-public address on purpose. Unit-tested directly (no network calls, literal-IP hostnames) in `backend/tests/test_oidc_client.py`.

**Follow-up, raised by the user:** a genuinely self-hosted IdP (on-prem Keycloak/Authentik with no public IP, common on a corporate LAN/VPC) would be rejected by this guard by default — it's indistinguishable from an attacker-controlled internal target from the guard's point of view. Rather than weakening the default, added a second, deployment-level (not per-org) opt-in: `oidc_allow_private_network_targets` (`OIDC_ALLOW_PRIVATE_NETWORK_TARGETS` env var, default `false`), which disables the public-IP check entirely when set. Documented as a blanket, deployment-wide allow that should only be enabled when every org sharing the deployment is trusted not to point its issuer at the deployment's own internal infrastructure — appropriate for single-tenant or fully-trusted-tenant deployments, not one serving mutually-untrusted organisations. See [enterprise-integration.md](enterprise-integration.md).

**`external_subject` cross-issuer collision (proactive, sub-8 confidence but fixed anyway).** The OIDC spec only guarantees `sub` uniqueness *within a single issuer*; matching on `external_subject` alone (as originally implemented) meant two different, unrelated identity providers asserting the same raw subject string would resolve to the same local account. Fixed by adding `User.oidc_issuer` and matching on `(external_subject, oidc_issuer)` together in `find_or_provision_user` (`backend/app/services/oidc_provisioning.py`); covered by a new regression test asserting two different issuers with an identical `sub` value provision two distinct accounts.

**`last_login_at`/`is_2fa_enabled` info leak on the broadened user-directory endpoint (Medium).** The C-A-13 filter work above correctly gated the org-scoped *filters* to org admins, but the endpoint's response body was populating these two fields for every caller regardless of admin status — meaning a plain org member could learn any other member's 2FA status and last-login timestamp just by calling the existing unfiltered listing. Fixed in `backend/app/routers/orgs.py`'s `list_org_users` by gating both fields on the same `is_admin` check already used for the filters, rather than only gating the filters themselves.

**Login-CSRF / session-fixation via a trusted callback URL (Medium).** `OidcCompletePage.tsx` originally accepted any `token` value found in its own URL with no proof it belonged to the current browser's own in-flight login — an attacker who completes their own legitimate SSO or native login could hand a victim a crafted `/oidc-complete?token=...` link and silently log the victim's browser into the attacker's account. Fixed by having the frontend generate a random nonce and store it in `sessionStorage` *before* navigating to the login-start endpoint (`OrgLoginPage.generateClientNonce`); the backend round-trips it through the signed `state` parameter (`security.create_oidc_state_token`, now `(organization_id, client_nonce)`) and the eventual callback redirect, and `OidcCompletePage` refuses to accept a token whose nonce doesn't match what it itself stashed. As a second, related improvement made at the same time: the token handoff moved from the query string (`?token=...`, which proxies commonly log and which persists in browser history) to the URL fragment (`#token=...`, never transmitted to any server over HTTP), cleared from the visible URL via `history.replaceState` immediately after being read.

### Playwright flakiness surfaced (not introduced) by this pass

Adding new nav links ("Requirements due for review," "My reviews due") and new advisory-action buttons ("Vote to approve"/"Vote to reject," stage review-response "Approve"/"Reject") exposed several pre-existing Playwright specs using loose, non-exact `getByText`/`getByRole(..., {name})` locators that happened to still be unique before this pass but are legitimate substring/text matches against the new UI. Fixed by switching the affected assertions to `exact: true` or role-scoped locators (`golden-path.spec.ts`, `mockup-engagement.spec.ts`, `pelion-v2.spec.ts`, `e2e-workflows/change-request-approval-separation.spec.ts`). Separately, three specs' "New project" step relied on the org picker defaulting to the correct organisation, which broke once the E2E seed script's three additional organisations sort alphabetically before "Default Organization" — fixed by selecting the org explicitly, using the project's already-established `toContainText(expected option)` wait pattern (stronger than a bare `not.toHaveCount(0)`, which can be satisfied by an unrelated combobox elsewhere on the page before the real one has even mounted).

## SOC 2 compliance: documentation package and codebase remediation pass

A full SOC 2 readiness documentation package was generated at `docs/soc2/` — a system description, a Security + Confidentiality Trust Services Criteria control matrix, and eleven individual policies (information security, risk assessment, access control, change management/secure development, operations/monitoring/logging, incident response, vendor management, data classification/confidentiality, encryption/key management, data retention/disposal, security awareness training), each grounded in the actual codebase rather than generic boilerplate, with known gaps stated explicitly rather than hidden. `CLAUDE.md` was updated with a "Compliance: SOC 2 Policy Adherence" section making these policies binding on future agent work in this repository — before touching auth/RBAC/secrets/audit-logging/retention/vendor integrations, consult the relevant policy and don't silently regress a documented control.

That policy set was then used as the basis for a full codebase compliance review — four parallel, read-only audits (access control/session management, secrets/encryption/tenant-isolation, audit-logging/monitoring, change-management/dependency-hygiene), each independently verified against the actual code before being trusted, following the same identify → verify → remediate discipline as the security-hardening passes above. Every confirmed finding was fixed and the full verification sequence (198 backend tests, up from 189; 14 Playwright specs including all 4 SSO tests) re-run clean afterward.

**Cross-organisation account deactivation/archival (High).** `deactivate_org_user` and `archive_org_user` (`backend/app/routers/orgs.py`) correctly scoped the *caller's* admin role to the specific `organization_id` in the request, but never checked that the *target* user actually belonged to that organisation — an admin of Org A could deactivate or archive any user in the system, including one with no relationship to Org A at all. Fixed by requiring `get_effective_org_roles(db, user_id, organization_id)` to be non-empty before either action proceeds, the same membership check `set_display_name_lock` in the same file already used correctly.

**2FA verification had zero audit trail (High).** `verify_2fa` (`backend/app/routers/auth.py`) never called `log_login`, unlike `/login` — success and failure both went unrecorded, and the endpoint didn't even capture the request IP. Combined with the already-documented absence of account lockout, this meant a TOTP brute-force against a stolen password left no trace at all. Fixed by mirroring `/login`'s pattern: every branch (invalid/expired challenge, inactive/misconfigured account, wrong code, success) now calls `log_login` with the outcome and IP, and a successful verification schedules the same geolocation background task `/login` does.

**SSO logins didn't produce a `login_events` row (Medium).** `auth_oidc.py`'s `oidc_callback` logged successful/denied SSO logins to `audit_events` only, never `login_events`, and captured no source IP; a failed token exchange or ID-token verification wasn't logged anywhere. Fixed by adding `log_login` calls on all three outcomes (exchange/verification failure, required-group denial, success), each with the request IP.

**Plaintext secret columns (Medium, and one previously-undisclosed instance).** `Organization.oidc_client_secret` and `User.totp_secret` were already documented known gaps (plain string columns, relying on infrastructure-level disk encryption only); this review additionally found `Organization.smtp_password` was the same risk class but undisclosed anywhere. Rather than patch just the one the user asked about, all three were closed together: a new reusable `EncryptedString` SQLAlchemy column type (`backend/app/models/encrypted_type.py`) transparently encrypts values with Fernet, keyed from a new, independently-rotatable `APP_SECRET_ENCRYPTION_KEY` setting (distinct from `JWT_SECRET`, fail-fast-required in production like the other secrets). Application code reads/writes plaintext as before; only the database ever sees ciphertext. Covered by `backend/tests/test_encrypted_type.py`, which asserts the *raw* database value is genuinely undecryptable ciphertext, not just re-formatted plaintext.

**Missing audit-trail coverage on ~15 mutating endpoints (Medium).** The logging policy claims every action that mutates organisational/project structure is audit-logged; a review of every router found this wasn't quite true — org logo/login-background upload, default-template setting, report-template CRUD, project settings/terminology/report-config updates, component/category create and reorder, change-request task create/update, change-request vote casting, custom field definition create/delete, and requirement link creation and file linking/unlinking all skipped `log_event`. All now call it, following each file's existing pattern (entity type/id, action, actor, project/org scope, and a narrow `detail` dict — not a full request payload).

**WebSocket deactivation-recheck window (Medium, narrowing an already-documented gap).** The `docs/soc2` access-control policy's originally-drafted "deactivation doesn't revoke tokens" gap turned out to be based on an incomplete reading: REST already rechecks `is_active` fresh on every request (`deps.py`), so that part was never actually a gap. The real, narrower one was WebSocket-only — `routers/ws.py`'s connection loop closed on token expiry but never rechecked `is_active` mid-connection, so a deactivated user's already-open socket could keep streaming project updates for up to the token's full lifetime. Fixed by adding a DB-backed `is_active` recheck (`_user_still_active`) on the same ~60-second cadence the loop already wakes up on for its expiry check, closing the socket within one interval of deactivation rather than waiting for token expiry. Project *role* changes are still not rechecked mid-connection — documented as a narrower residual, not eliminated entirely.

**`assign_org_role` path/body `user_id` mismatch (Low).** The endpoint's URL contains `{user_id}` but the handler operated on `payload.user_id` from the request body instead, never comparing the two — not exploitable (the org-admin authorization check was still correctly scoped), but a confused-deputy/audit-trail footgun where the URL a caller was authorized against could diverge from who was actually affected. Fixed by using the path parameter as the sole source of truth; the body's `role` field is still used, but a mismatched body `user_id` is now silently ignored rather than trusted.

**False positive dismissed, not fixed:** an apparent "missing Alembic migration source" (a compiled `0002_pelion_v2_schema.cpython-312.pyc` in `backend/alembic/versions/__pycache__/` with no matching `.py` file) was investigated and found to be a stale, gitignored local build artifact left over from before an earlier migration was squashed into `0001_initial.py` per this project's pre-release convention — not evidence of an undocumented schema change. Deleted for hygiene; no code or documentation change needed.

`docs/soc2/` was updated to reflect every fix above: the access-control policy's deactivation-gap wording was corrected (REST was already fine; the WebSocket case is now fixed too) and gained a note about the cross-org authorization fix; the encryption policy's known-gaps section marks the three plaintext-secret entries resolved and documents `APP_SECRET_ENCRYPTION_KEY`; the confidentiality policy's matching gap entry was struck through; and `trust-services-criteria-mapping.md`'s CC6.3, CC6.5, CC7.2, and C1.1 rows and its summary gap list were updated to match — consistent with the policy's own instruction (and this project's standing practice) not to let documented gaps go stale once the underlying issue is actually fixed.

## Continuous integration

Added `.github/workflows/ci.yml`, closing what the SOC 2 control matrix had flagged as the single most consequential gap against CC4.1/CC8.1: automated test suites existed and passed, but nothing enforced them — they were run manually, whenever someone remembered to. Three jobs:

- **`frontend`** — `npm run lint` + `npm run build` (ESLint, then `tsc -b && vite build`). Fast, no Docker.
- **`backend-and-e2e`** — brings up the *real* `tests/container/docker-compose.yml` stack (the same one developers run locally, deliberately not a hand-rolled set of GitHub Actions `services:` blocks, to avoid a second Postgres/MinIO/Mailhog config that could silently drift from the one actually documented and tested — see the "Two separate Compose stacks" rationale in `deployment.md`), then runs the backend pytest suite with coverage (`--cov-report=xml/html`, `--junitxml`), `ruff check`, and — after the standard restart-and-reseed step pytest's schema-truncation requires — the full Playwright E2E suite. Test results are published as GitHub check annotations (`dorny/test-reporter`) for both the backend and E2E suites separately, a coverage percentage is written to the job summary, and the HTML coverage report and Playwright artifacts are uploaded for download. All of it is gating — a failure at any step fails the job.
- **`docker-build`** — builds (but does not push) the production backend/frontend images, gated on the two jobs above passing. Per explicit instruction, publishing is deliberately not wired up yet: the system hasn't been through enough real-world (developer) usage to trust an automated push. The job builds and tags for `ghcr.io` anyway (proving both Dockerfiles still build) and documents, in comments, exactly what to uncomment (a `docker/login-action` step and `push: false` → `true`) once that changes — no extra secret needed, since `GITHUB_TOKEN` already authenticates to `ghcr.io` once `packages: write` is granted (already is, at the job level).

Before wiring `ruff check` in as a blocking gate, the pre-existing lint state was checked rather than assumed clean — it wasn't: 13 issues (8 import-ordering, 5 unused-variable) had accumulated across several files over the session, invisible until now because nothing had ever run `ruff check` as a gate before. Fixed directly (auto-fix for the import-ordering ones via `ruff check --fix`, manual for the unused-variable ones) rather than either silencing the rule or leaving the new gate red on day one. Same check performed for `npm run lint`/`npm run build` before wiring those in — both were already clean (7 pre-existing `react-refresh` warnings, non-blocking).

Coverage is reported, not gated — no `--cov-fail-under` threshold is enforced, since no baseline had been agreed on. Current backend line coverage is ~90% (198 tests), noted in `docs/soc2/policies/change-management-and-secure-development-policy.md` as a starting point for setting one later.

`docs/soc2/` was updated to match: the change-management policy's "No CI pipeline" gap is marked resolved (with the residual gap — no branch protection requiring the check to pass before merge — restated as its own item, since that's a GitHub repository setting, not something a workflow file can configure), and `trust-services-criteria-mapping.md`'s CC4.1 and CC8.1 rows and summary gap list were updated to match. The README gained a CI status badge and a short "Continuous integration" section.

## Same-origin subpath deployment (API under `/api`, avoiding CORS)

Every REST route the frontend calls already lives under `/api/v1/...` (`backend/app/routers/*.py`'s own router prefixes), so hosting the API at `my.website.com/api/` alongside the UI at `my.website.com/` — one origin, routed by path at the reverse proxy — needed **no backend routing changes at all**: an nginx `location /api/ { proxy_pass http://backend:8000; }` (no path on `proxy_pass`, so the URI forwards unchanged) lines up with the existing path structure automatically. This is also the reason to prefer this pattern over the two-hostname alternative (`app.example.com` / `api.example.com`) where CORS actually matters: putting both on one origin makes the question moot rather than requiring `CORS_ORIGINS` to be configured correctly, since same-origin requests never trigger CORS enforcement in the first place.

What did need a fix: `PUBLIC_API_BASE_URL` needs to be set to an **empty** value (not merely omitted) for this pattern, so the frontend calls the API via relative paths against its own origin instead of an absolute URL. Both `docker-compose.yml` files' `VITE_API_BASE_URL: ${PUBLIC_API_BASE_URL:-http://localhost:8000}` and the frontend's own runtime-config generator (`frontend/docker/env-config-entrypoint.sh`) used `${VAR:-default}` — the colon form, which treats an explicitly-set *empty* string the same as unset and silently substitutes the default anyway. That's the correct behavior for "no default was chosen," but wrong for "empty was chosen on purpose," and there was no way to tell the two apart with a colon in the expansion. Fixed in all three places by dropping the colon (`${VAR-default}`), which POSIX parameter expansion (and Docker Compose's own interpolation, which follows the same rule) only treats as "apply the default" when the variable is truly absent. Confirmed the fix rather than trusting the one-character diff: `docker compose config` with `PUBLIC_API_BASE_URL=""` now shows `VITE_API_BASE_URL: ""` (previously silently became the `http://localhost:8000` default), and a real built frontend image run standalone with `VITE_API_BASE_URL=""` serves a genuinely empty value in its generated `env-config.js`.

The reverse-proxy recipe itself was also verified against the real running stack, not just written from the routing analysis above: an actual nginx container, configured exactly as documented, proxying to the real dev/test backend and frontend containers, returned identical responses (including a real login request) whether called through the proxy's `/api/` path or the backend directly.

Documented in `docs/deployment.md` as a new "Same-origin subpath deployment" section alongside the existing two-hostname TLS/reverse-proxy guidance, with the concrete nginx config, and a note on scope: the `/api/` passthrough only reaches paths that genuinely start with `/api/` on the backend, so `/health`/`/metrics`/`/docs`/`/openapi.json` (none of which carry that prefix) aren't reachable through it without extra one-to-one location blocks — reasonable as a default, since health/metrics are normally scraped over the internal Docker network rather than exposed publicly anyway. Also cross-referenced from the README's frontend configuration note.

## MCP server: AI-assistant access to requirements

Added `mcp-server/` — a fourth deployable component (alongside backend, frontend, and now itself) exposing requirements/projects/organisations to AI assistants via the [Model Context Protocol](https://modelcontextprotocol.io), built on `fastmcp` (the community-maintained Python MCP framework, not just the bare `mcp` SDK — its `get_http_headers()` dependency and `@custom_route` decorator were the two things that made the design below straightforward rather than requiring a hand-rolled ASGI layer).

**The one design decision that mattered: pass-through authentication, not a service account.** Every tool call requires the *caller* to present their own ReqTrackManager access token as an `Authorization` header on the MCP connection; the server does nothing but forward that exact header to the backend on every request it makes. It holds no credentials of its own, stores no token, and implements no authorization logic — the backend's existing, already-hardened RBAC is the only thing deciding what any given call can see. This was chosen over the obvious alternative (the MCP server logging in once as a fixed "integration" account) specifically because that alternative would mean every user of this server sees whatever that one shared account can see, rather than their own actual project memberships — exactly backwards for a codebase whose entire security posture this session has repeatedly hardened around *per-user, per-project* scoping (the SOC2 access-control policy, the IDOR fixes, the cross-org deactivation fix two passes ago). A shared credential would also have been a much larger blast radius if it ever leaked. Six tools, all read-only by design (`list_organizations`, `list_projects`, `get_project`, `list_requirements`, `get_requirement`, `get_requirement_history`) — deliberately not the full API surface; letting an AI *read* requirements is a materially smaller, safer thing to ship first than letting it act on the workflow.

**Input validation at the boundary**: `project_id`/`requirement_id`/`component_id`/`category_id` arguments are validated as syntactically well-formed UUIDs (`uuid.UUID(value)`) before being interpolated into a backend URL, rejected with a clear error otherwise. Not a security boundary the backend doesn't already enforce on its own (FastAPI's UUID-typed path parameters already 422 on malformed input) — but validating it here too means a malformed tool argument can never influence what URL this server itself constructs, closing off a path-confusion class of concern before it's even a question, consistent with this project's established practice of validating at every layer rather than trusting a single upstream check.

**Verified for real, not just designed**: rather than trust the auth-forwarding logic from code review alone, ran it against the actual live dev/test stack using `fastmcp`'s own Python client — confirmed the full tool chain (list projects → search requirements → get detail → get history) returns real, consistent data; confirmed a missing Authorization header, an invalid token, and a malformed UUID argument each fail with the intended clear error rather than a stack trace or a silent empty result; and, most importantly, confirmed that two different real accounts (the demo org admin vs. an unrelated E2E persona in a different organisation) each see only their own accessible projects through this server — the actual pass-through-RBAC guarantee, not just "a request succeeded." A small integration test suite (`mcp-server/tests/test_server.py`, using the same `fastmcp` client) now covers this and runs in CI.

One implementation snag along the way: `fastmcp`'s `get_http_headers()` excludes `Authorization` (and a few other sensitive headers) *by default* — reasonable as a default for a framework where most tools shouldn't see it, but this server's entire purpose is relaying it, so it's called as `get_http_headers(include_all=True)`, deliberately opted back in in exactly the one function that needs it rather than more broadly.

**Deployment and client setup**: added as a fourth service to both Compose stacks (`REQTRACK_API_URL` pointing it at `backend`, its own `/health` check, port `8100`). New `docs/mcp-server.md` covers the authentication model in full, plus concrete setup instructions for the three clients the user asked for by name — Claude Code (including a `mcp-server/scripts/get_auth_header.sh` helper written for Claude Code's `headersHelper` mechanism, which re-runs the login on every connection/reconnect and automatically retries once on a 401/403, working around this app's tokens being short-lived without needing a new long-lived-token feature), VS Code Copilot Chat (the `.vscode/mcp.json` `inputs`-array pattern, avoiding a hardcoded token), and Microsoft Copilot Studio (its native MCP wizard's header-based API-key auth type, which lines up with this server's design directly) — plus generic guidance for any other Streamable-HTTP MCP client. Exposing it to a remote client like Copilot Studio reuses the same reverse-proxy subpath pattern from the previous session's work, with a worked `/mcp/` nginx location block.

**SOC2 documentation updated to reflect a genuinely new surface, not just a new feature**: this is the first component added this session that's meant to be reachable by third-party, customer-chosen infrastructure (Copilot Studio's own cloud) rather than only by this deployment's own frontend. `system-description.md` gained the component itself plus a new CUEC (the customer's own responsibility for which AI platform they connect and what token they give it); the vendor-management policy gained an item explaining that a customer-connected AI platform becomes a genuine subprocessor of *that customer's* data the moment they wire it up, which the Company neither controls nor is responsible for; the confidentiality policy clarifies this is a data-*flow* consideration, not an isolation-*control* gap, since the same RBAC boundary still applies; and the access-control policy notes that this integration deliberately reuses existing session tokens rather than introducing a new credential type, so every existing control in that policy (issuance, 2FA, SSO, the 12-hour lifetime, `token_version` revocation) already covers it.

**Known, documented limitations, not silently worked around**: no long-lived API-token mechanism exists yet in ReqTrackManager, so anything other than Claude Code's self-refreshing `headersHelper` needs periodic manual token updates as the underlying 12-hour session token expires; SSO and 2FA accounts can't complete the non-interactive login helper script (it does a single password POST, which can't finish either flow), so those need a token obtained by hand instead. Both called out explicitly in `docs/mcp-server.md` rather than glossed over.

CI extended to match: `mcp-server` now builds and runs its own `ruff check` and `pytest` suite in the `backend-and-e2e` job (after the E2E dataset is seeded, so its data-dependent test exercises real data rather than skipping), and `docker-build` now also builds (not publishes, same as the other two images) its production image.

## MCP server: expanded tool set, a built-in login page, and SSO without a custom OAuth server

Follow-up to the section above, from two pieces of feedback on the first cut: (1) the tool set only covered requirements, not change requests/comments/votes/notifications/reviews; (2) getting a token still meant hand-crafting a `curl` call, and the user specifically asked whether this server could "bring up an integrated browser or set up a quick server that has an interface to connect," citing VS Code's Azure DevOps ("ado") MCP server as the experience to aim for.

**Tool set grew from 6 to 15**, all read-only, all following the exact same shape as the original six (UUID validation via `_require_uuid`, forwarding through `_call_backend`, full docstrings): `list_change_requests`, `get_change_request`, `list_change_request_votes`, `list_change_request_tasks`, `list_change_request_comments`, `list_requirement_comments`, `list_notifications`, `list_my_reviews_due`, `list_project_reviews_due`. No new design decision here — the pass-through-auth model and RBAC boundary from the original build cover these identically; it was purely a matter of finding and wrapping the right existing endpoints (`routers/change_requests.py`, `notifications.py`, `reviews.py`).

**Rejected: a full custom OAuth 2.1 authorization server**, which is what would be needed to get the *exact* zero-click experience the "ado mcp" comparison implies (the MCP client itself detecting a 401, discovering OAuth metadata, and driving the whole flow with no page ever shown to the user manually). `fastmcp` does ship an `OAuthProvider` abstraction for this, but its own documentation describes it as "an extremely advanced pattern that most users should avoid," requires implementing nine abstract methods (client registration, authorization, code/token exchange and storage, revocation, verification), and is explicitly incomplete in its own docs on PKCE, `state` handling, and `redirect_uri` validation — the exact details that make OAuth authorization servers a well-known place to introduce real vulnerabilities. Not a fit for a project whose security posture this whole session has been built around getting *right*, not fast.

**Built instead: a plain HTML `/login` page, served directly by `mcp-server` itself** (`@mcp.custom_route`) — one of the two options the user explicitly offered ("a quick server that then has an interface to connect"). A user visits it in a browser, submits email/password (with a follow-up TOTP form if the account has 2FA), the page relays those credentials to the backend's own existing `/api/v1/auth/login` / `/api/v1/auth/2fa/verify` server-side, and renders the resulting token plus ready-to-paste Claude Code/VS Code config snippets directly in the response body. It introduces no new authentication mechanism — it's a convenience wrapper around the login endpoint that already existed, not a second credential store. Security details that mattered: the token is only ever in the response *body*, never a URL (same "no secrets in URLs" principle as the earlier SSO login-CSRF fix); every response carries `Cache-Control: no-store`; the submitted email is never echoed back into any HTML (the re-shown form on failure is a fresh, empty one — closing off any need for manual escaping by construction); the password lives only in the request-handler's local scope for the one relay call; no CSRF protection was added because, like the native frontend's own login form, there's no ambient session/cookie authority here to forge.

**Then genuinely got the "already logged in → it just works" experience for SSO orgs**, once asked directly whether the login page detects an existing session (it can't, for native accounts — the frontend keeps its token in `localStorage`, which is strictly origin-scoped and `mcp-server` runs on its own port, so there's no browser mechanism to observe "already logged in" across origins even in principle). SSO is different: ReqTrackManager already has a real, working OIDC flow (`routers/auth_oidc.py`, proven against a real Keycloak instance by `tests/playwright/tests/e2e-workflows/sso.spec.ts`), and an IdP's own browser session is exactly the ambient state that makes flows like `ado`'s feel instant. The one obstacle was that the OIDC callback was hardcoded to always redirect back to the frontend app. Fixed by threading a `client` field (`"app"` or `"mcp"`, restricted to those two literal values by FastAPI's `Query(..., pattern="^(app|mcp)$")`) through the existing signed `state` token (`security.create_oidc_state_token`), and having `oidc_callback` pick between two *fixed, server-configured* redirect bases — `settings.frontend_base_url` (unchanged default) or the new `settings.mcp_server_public_url` — never a caller-supplied URL. This matters: a redirect target taken from client input here would be a textbook open-redirect / token-theft vector (the access token travels in the URL fragment on success), so the design keeps the set of possible destinations fixed at two, chosen only by a value inside a token the server itself signed. `mcp-server`'s `/login?org=<slug>` page adds a "Sign in with SSO" button (via the backend's existing public `GET /orgs/by-slug/{slug}/login-info` lookup) and a new `/login/oidc/complete` landing page that is entirely client-rendered — it performs the identical anti-replay nonce check `OidcCompletePage.tsx` already does (a `sessionStorage` value generated before the redirect, compared against what comes back), for the same login-CSRF reason documented on `create_oidc_state_token`.

**Noticed and closed in passing**: the root production `docker-compose.yml`'s `backend` service never actually set `PUBLIC_BACKEND_URL` or `FRONTEND_BASE_URL` (only the dev/test stack did) — meaning a real production deployment's OIDC redirects would have silently used the `localhost` code defaults. Added both alongside the new `MCP_SERVER_PUBLIC_URL`, all three following the same `${VAR:-default}` convention already used elsewhere in that file.

**Verified for real**: rebuilt both containers; `mcp-server`'s test suite grew to 19 (the original 7, three covering the new tool set, four covering the `/login`/`/login/2fa` credential flow including a genuine round-trip login that produces a token verified to actually authenticate a live tool call, and four covering `/login`'s SSO-branch rendering — unknown org, SSO-disabled org, SSO-enabled org, and the `/login/oidc/complete` shell); a new Playwright spec extends `sso.spec.ts` to drive a real browser through Keycloak's actual login form starting from `mcp-server`'s own `/login?org=...` page (not the frontend), confirming it lands on `/login/oidc/complete` with a token that genuinely authenticates against `/api/v1/auth/me`. Full backend pytest (198) and the full Playwright suite (15, including the new spec) both pass. One process note worth recording since it briefly looked like a regression: running backend pytest against the dev/test stack leaves its database migrated-but-empty afterward (documented already under "Database: the test suite was wiping the live database"), which surfaced as 14 unrelated Playwright failures until `docker compose restart backend && python scripts/seed_e2e_dataset.py` was re-run — not a bug in this pass, just the same existing gotcha CI's own workflow already works around.

`docs/mcp-server.md` updated throughout: the tool table now lists all 15, "Getting a token" leads with the `/login` page (manual `curl` demoted to "the scripting-friendly way"), and "Known limitations" replaces the old blanket "read-only, scoped to requirements" line with the real remaining gap — no zero-click OAuth handshake — explained with the same reasoning as above.

## Personal Access Tokens

Direct follow-up to the section above: `docs/mcp-server.md`'s "Known limitations" had flagged "no long-lived API-token mechanism" since the MCP server was first built — every credential in ReqTrackManager was a 12-hour session JWT, forcing `mcp-server`'s `headersHelper` refresh-script workaround. The user asked for a proper Personal Access Token system: user-created, scoped to whichever organisation(s) the creator chooses, capped by both a per-org admin-configured maximum and a system-wide default, usable as MCP auth, fully self-service via the UI — plus, in follow-up feedback, incident-response bulk revocation at three blast radii (a user's own tokens, an org's, the whole platform) and a per-user/per-token action for an org admin dealing with one departing member.

**Design decisions:**

- **Opaque, hashed secret (`rtm_pat_<43 url-safe chars>`), not a JWT.** Only `sha256(token)` is ever stored (`security.generate_pat`/`hash_pat`) — mirrors how passwords are already treated (hash, never plaintext) and is the standard shape for exactly this credential type (GitHub/GitLab/Stripe all do this). The real reason it's not a JWT: revocation needs to be instant and per-token, which a hash lookup against a DB row gives for free, where a stateless JWT would need a second revocation-list mechanism bolted on anyway.
- **Independent of `User.token_version`.** A password change/2FA-disable still bumps `token_version` and kills every session JWT immediately (unchanged) — but deliberately does *not* touch PATs, which have their own `revoked_at`. Tying them together would defeat a PAT's entire purpose (not needing to reconfigure an integration). User deactivation (`is_active=False`) still kills a user's PATs immediately, same as sessions, since that's checked fresh on every request regardless of credential type.
- **Org scope is a JSONB list on the token row** (`allowed_organization_ids`), not a join table — matches the existing `Organization.sso_group_mappings: JSONB` precedent for "small structured list scoped to one row"; scope is only ever read from a specific token, never queried "which tokens touch org X" in bulk (the org-admin listing endpoint does a JSONB `@>` containment scan instead, cheap enough at this scale).
- **Expiry is recomputed at auth time, not frozen at creation.** `services/pats.effective_expiry` computes `min(pat.expires_at_ceiling, *[pat.created_at + that org's *current* cap for every currently-scoped org])` on every request. This means an org admin *lowering* their cap applies retroactively to already-issued tokens — "maximum time limit... on these being active" reads as an ongoing constraint, not a one-time snapshot at issuance — while *raising* a cap never extends a token past what was already fixed. `expires_at_ceiling` (computed once, at creation, from the caps in effect then) is what's shown in the UI as a stable "expires by" date; the dynamic recheck can only ever pull the true expiry earlier than that, never later. A new `PAT_DEFAULT_MAX_LIFETIME_DAYS` setting (90) is the fallback for any org that hasn't set its own cap, so no PAT is ever unboundedly long-lived by default.
- **PATs never satisfy `require_server_admin`, full stop** (`services/rbac.require_server_admin`) — not even for a genuine server admin's own token. A PAT's entire design is "which orgs can it reach"; that's meaningless for a deployment-wide action, and I-M-05's "server admin doesn't give access to data within organisations" extends naturally to treating a PAT as an inherently org-scoped credential.
- **The org-scope restriction is layered on top of real RBAC, applied at every org/project-scoped dependency factory** (`require_org_role`, `require_org_admin_or_server_admin`, `require_project_role`, `require_project_view`, `require_project_manage` — all in `services/rbac.py`) via a new `check_pat_scope`/`check_pat_scope_for_project` check, reading `request.state.pat_allowed_org_ids` (set only by `deps._resolve_user_from_pat`, so an ordinary session-JWT request pays zero extra queries). It restricts, never grants: a PAT can only ever do what its owner's real roles already allow, narrowed further by scope. Endpoints with `organization_id` in the request *body* rather than the path aren't covered by those factories — audited for this and found exactly one, `POST /api/v1/projects` (project creation, `organization_id` in `ProjectCreate`), fixed with an explicit `check_pat_scope` call in `routers/projects.create_project`.
- **Personal, cross-org-by-nature endpoints are deliberately untouched by PAT scoping** — `GET /notifications`, `GET /me/reviews/due`, `GET /auth/me`. Restricting "which org's *content*" doesn't naturally extend to "your own inbox"; called out explicitly rather than silently decided.
- **Bulk "revoke all" (self/org/platform) fully kills a matching token, never partially narrows it.** An org admin's "revoke all PATs in my org" revokes outright every non-revoked token that includes that org *anywhere* in its scope, even if also scoped to unrelated orgs — a security reset should mean "these tokens are dead," not leave one alive-but-narrowed in a way its owner might not notice. The UI's confirm dialog states this side effect explicitly. A platform-wide reset (server admin only) is framed as pure security/tenancy administration, same category as creating organisations — it never reads or exposes org content or any token secret (hashes aren't reversible), so it doesn't conflict with I-M-05.
- **The org-admin per-token view (`GET /orgs/{id}/pats`) never reveals *which* other organisations a multi-org token also reaches — only a count** (`other_org_count`). Same confidentiality class this codebase already closed for `GET /system/users` ("would leak which orgs a user belongs to"). This is what makes the companion **descope** action (remove just this org from a token's scope, leaving it valid elsewhere) meaningful without leaking cross-tenant membership: the admin doesn't need to know *which* other org to decide revoke-outright vs. descope, and the descope action itself doesn't need that identity either. Descoping down to zero remaining orgs auto-revokes (a token with nothing left in scope can never authenticate anything).
- **Self-service endpoints live under `/api/v1/me/pats` (`routers/pats.py`)**, mirroring the existing `/api/v1/me/reviews/due` convention; org-admin actions live in `routers/orgs.py` and the platform-wide reset in `routers/system.py`, alongside those routers' other org-/deployment-scoped admin actions, rather than a fourth PAT-specific router.

**Verified for real**: 13 new backend tests (`test_personal_access_tokens.py`) covering creation/listing/single-and-bulk revocation, the org-scope restriction on both org- and project-path endpoints (proven against a user with genuine RBAC access to *both* orgs, so a 403 can only be the PAT-scope check, not an ordinary permissions failure), expiry defaults/per-org caps/multi-org min-selection, a requested expiry beyond the cap coming back clamped rather than erroring, an expired token's rejection, retroactive cap-tightening (backdating a token's `created_at` via direct SQL, then lowering the org's live cap, then confirming the token is rejected — no time-mocking infra existed in this suite before, so this is the pattern to reuse for the next test that needs it), a deactivated user's token rejected immediately, PATs rejected at the server-admin gate even for a real server admin, the org-wide and platform-wide bulk resets (including the multi-org "fully killed, not just descoped" side effect and the negative 403 cases), and the org-admin per-token list/revoke/descope flow including the `other_org_count`-only confidentiality assertion and the 404-not-403 non-disclosure check. Full backend suite: 211 passed (198 + these 13), zero regressions from the `rbac.py` changes. A new Playwright spec creates a token through the real Preferences UI, uses it to authenticate a genuine `GET /auth/me` call, revokes it through the UI, and confirms that exact same call now 401s — the deep RBAC/expiry logic is pytest's job; this spec's job is proving the token the UI hands a user is a real, independently-revocable credential, not just correctly rendered. Manually driven a full pass through all three UI surfaces (self-service create/list/revoke in Preferences, org-admin max-lifetime + per-token table + bulk revoke in OrgAdminPage, platform-wide reset in ServerAccessReviewPage) against the live dev stack, confirming a token created through the browser genuinely authenticates a live `curl` call and genuinely stops working the instant it's revoked.

`docs/mcp-server.md`'s "Getting a token" now leads with Personal Access Tokens as the recommended path (the `/login` page's session token demoted to "quick, but short-lived"), and its "Known limitations" marks the long-standing "no long-lived token mechanism" gap resolved. `docs/soc2/policies/access-control-policy.md` gained a new Authentication item introducing PATs as a second bearer-credential type, and amended the item that previously stated there was "deliberately no... API-key mechanism issuing its own broader access" to reference PATs as the intentional, narrowly-scoped exception — a PAT still never grants more than its owner's real roles, so the "no broader access" principle holds, but the line needed to stop implying no such mechanism existed at all.

## Deep hardening review

Requested explicitly as a whole-codebase pass, not scoped to the immediately preceding PAT work. Three parallel reviews (identify → verify → remediate, matching this codebase's own established hardening-pass methodology): authentication/credential handling end to end; authorization and multi-tenant isolation across every router; injection/SSRF/secrets-handling/file-storage safety. Every candidate finding was independently re-verified by reading the actual current code (and, for the storage-key issue, hand-tracing the exact path-resolution arithmetic) before anything was fixed — nothing below was taken on an agent's word alone. Four real, previously-unnoticed issues surfaced; a fifth candidate (WebSocket DNS-rebinding-style TOCTOU in the OIDC SSRF guard) was investigated and correctly judged not a new, reportable gap — already an accepted, documented trust-boundary limitation, not something this pass changed.

**1. Personal Access Tokens could read files outside their declared organisation scope (`backend/app/routers/files.py`).** `download_file` resolves the caller via `get_current_user_header_or_query` (needed so `<img src>` tags can pass the token as `?token=`, which the `require_*` dependency factories in `services/rbac.py` don't support) — meaning it never went through the factories that layer the PAT org-scope check (`check_pat_scope`/`check_pat_scope_for_project`) onto every other org/project-scoped endpoint. It only checked the caller's *real* RBAC role, which a PAT's owner of course still has, even outside what they scoped that particular token to. A PAT created scoped only to Org A could therefore download an Org B file its owner also happens to have genuine access to via their own account — quietly defeating the entire point of scoping a token in the first place, for exactly the endpoint most likely to hold sensitive content (attachments, org resources). Fixed by calling `check_pat_scope`/`check_pat_scope_for_project` explicitly inside `download_file` once the file's owning org/project is resolved, mirroring the pattern `require_project_manage` already uses (resolve resource → derive org → check scope → check role). This is the second body/non-path-scoped gap found in this codebase (the first, `POST /api/v1/projects`, was caught and fixed while building the PAT feature itself) — both share the same shape: an endpoint that resolves the owning org *after* looking up some other resource, rather than taking `organization_id`/`project_id` directly as a path parameter the dependency factories can key off. Worth a mental grep the next time a new resource-scoped endpoint is added. New regression test: `test_personal_access_tokens.py::test_pat_scope_enforced_on_file_download`.

**2. Cross-tenant path traversal in local file storage (`backend/app/services/files.py`, `backend/app/storage_backends/local.py`).** The storage key was built as `f"{organization_id}/{uuid4()}_{filename}"`, with the client-supplied `filename` concatenated in raw — despite `local.py`'s own comment claiming the key was "uuid-based, never taken directly from user input." It wasn't: a filename with **more than one** `../` segment defeats the uuid prefix. The first `../` merges with the prefix into one literal, harmless path component (`<uuid>_..`, since it's adjacent with no separator) — but any *additional* `../` segments in the filename remain real traversal operators. Hand-tracing the resolution: a filename like `../../../other-org-id/evil.txt` normalizes to `<storage_local_dir>/other-org-id/evil.txt` — inside the shared root (so `LocalFileStorageBackend._path_for`'s own confinement check, `is_relative_to(base_dir)`, still passes) but *outside* the uploading org's own key prefix. Every local-backend upload endpoint is reachable by a low-privilege caller (`/me/avatar` needs no role at all; org resources/attachments need only ordinary project/org membership), so this was a real cross-tenant storage **write** primitive — planting or overwriting files in another organisation's on-disk namespace, or a disk-fill DoS scoped to a victim tenant. (A cross-tenant *read* of an existing file would additionally require guessing its random UUID component, so the demonstrated compromise is the write/isolation break, not confirmed exfiltration.) The S3 backend is unaffected — object keys aren't hierarchically resolved, so `../` is just a literal character sequence there. Fixed with a new `services.files._safe_key_component()`: reduces the filename to its final path segment (discarding directory components — and therefore any `..` — entirely, not just the first one) and replaces any remaining non-alphanumeric character, so the generated fragment can never be interpreted as a path separator or traversal operator by any backend that resolves keys hierarchically. The original client filename is still preserved verbatim in `FileAsset.filename` for display/download purposes — only the storage-key fragment is sanitized. New regression test: `test_files.py::test_uploaded_filename_cannot_escape_its_organisations_storage_key_prefix`, asserting directly against the DB row (the storage key isn't exposed via the API) that the key stays confined to `{organization_id}/` with no `..` or `/` surviving from the filename, and that upload/download still round-trips correctly.

**3. Secrets-redaction gap in 422 validation-error responses (`backend/app/main.py`).** `redact_sensitive_validation_errors` blanks a failed field's echoed `input` for `password`/`current_password`/`new_password`/`totp_secret`/`code`, closing the general case of Pydantic's validation errors echoing back whatever was submitted — but `_SENSITIVE_FIELD_NAMES` never included `smtp_password` or `oidc_client_secret`, the exact same class of genuine secret this codebase already encrypts at rest (`EncryptedString`) elsewhere. A request that fails validation on either field (e.g. submitting a non-string JSON value) echoed the submitted secret back verbatim in the response body — the caller's own secret round-tripping to them, not a cross-tenant leak, but a live inconsistency with a protection this codebase had already built for exactly this purpose, and 422 bodies are commonly captured by reverse-proxy/APM/error-monitoring tooling outside the app's own control. Fixed by adding both field names to the set. No new test added — this is a one-line set addition covered by the existing `redact_sensitive_validation_errors` logic path, not new logic; if a future pass wants explicit regression coverage, extend the existing (unwritten) test for that handler alongside a case for one of the currently-covered field names.

**4. WebSocket connections never checked `token_version`, contradicting this codebase's own documentation (`backend/app/routers/ws.py`).** `token_version` is documented in three places as "this system's primary technical incident-containment tool" (access-control-policy.md) — a password change or 2FA disable is supposed to deterministically kill every previously-issued token immediately, including tokens behind already-open connections. The WebSocket handler's handshake and periodic 60-second recheck loop (added in an earlier hardening pass specifically to close "a token that expired, *or was revoked via the `token_version` mechanism*, mid-session," per this doc's own prior wording at the time) in fact only ever checked `exp` and, in the loop, `is_active` — never `tv` against the user's current `token_version`. An attacker holding a stolen session token could keep a live WebSocket connection open and receiving project updates for up to its remaining 12-hour lifetime, *even after* the legitimate user took the exact containment action (a password change) the incident-response plan documents as immediately closing this off. This is a materially more severe gap than the already-accepted 60-second `is_active` window (the two prior entries above and in access-control-policy.md's Known Gaps) — that one is a small, bounded, deliberately-accepted delay; this one was a complete bypass of the mechanism entirely, for as long as a token remained unexpired. Fixed: the handshake now decodes and checks `tv` against `User.token_version` (matching `deps._resolve_user_from_token`'s existing REST check exactly), and the renamed `_user_session_still_valid()` (was `_user_still_active()`) now checks both `is_active` and `token_version` on every periodic recheck. The prior, inaccurate claim in this file's own earlier "WebSocket connections outlived their issuing token" entry (see above) has been corrected in place rather than left standing. New regression tests: `test_websocket_security.py` (a real `client.websocket_connect(...)` round trip proving a token that was valid before a password change is rejected at handshake afterward with code 4401, plus a direct unit check of the renamed recheck function); `test_ws_active_recheck.py` (pre-existing, testing only `is_active`) updated in place for the rename and extended to also pass a `token_version`.

**Not a finding**: SSRF via DNS rebinding on org-configured OIDC endpoints (check-time IP validation vs. connect-time resolution) — a real theoretical gap, but the only actor who could exploit it is the org admin who configured `oidc_issuer_url` in the first place, already the documented trust boundary this project accepts for that setting (an org admin is trusted not to point their own org's issuer at internal infrastructure, same as the existing `oidc_allow_private_network_targets` escape-hatch documents). Investigated and correctly excluded rather than silently skipped.

**Verified for real**: every finding above was confirmed by reading the actual current code (not the audit agents' descriptions alone) before any fix was written; the storage-key path-traversal claim specifically was hand-traced through pathlib's component-stack resolution to confirm the exact "first `..` merges with the uuid, later ones don't" mechanism before trusting it. All four fixes have dedicated regression tests. Full backend suite: 215 passed, zero regressions. Full Playwright suite re-run clean afterward.

## Deep hardening review, round 2

Explicitly requested as a second, *deeper* pass, not a repeat of the first. Three more parallel reviews, deliberately scoped away from what round 1 already covered: race conditions/TOCTOU and privilege-escalation/business-logic integrity; an exhaustive line-by-line re-read of `mcp-server/server.py` plus OIDC role-provisioning's escalation surface plus notification/email content-injection; deployment/infrastructure configuration plus mass-assignment/over-posting. Same discipline as round 1 — every finding independently re-verified against the actual current code before any fix, nothing taken on an agent's word alone. Two findings were surfaced but deliberately left as decisions for the user rather than fixed unilaterally, since both are genuine behavior-change judgment calls, not unambiguous bugs; both were then approved and implemented.

**1. A Stakeholder or Project Administrator could self-approve a requirement via direct edit (`backend/app/routers/requirements.py`).** `update_requirement` gates on `CAN_EDIT_ROLES` (manager, administrator, *or* stakeholder) and passed `payload.status` straight through — but `docs/requirements.md`'s C-U-03 clarification is explicit that requirement approval is a *Project-Manager-exclusive* capability layered on top of what administrators/stakeholders can do, not shared with them (the exact distinction `decide_change_request` already enforces for CR approval, with its own "C-U-03: project manager only" comment — `update_requirement` had no equivalent). Concretely: any stakeholder on a project could `PUT` a requirement with `"status": "approved"`, becoming its own `approval_authority`, locking it, and forcing all further edits through a change request — an authority meant to require Project Manager specifically. Compounding this, the same endpoint allowed jumping straight from `draft` to `"status": "completed"` in one request, skipping the dedicated `/complete` endpoint's own "must already be approved" precondition entirely, regardless of role. Fixed: `update_requirement` now requires `PROJECT_MANAGER` specifically when `payload.status == APPROVED`, and rejects `payload.status == COMPLETED` outright (400), pointing callers at the dedicated endpoint instead. New regression tests in `test_permission_matrix.py`: stakeholder and administrator both rejected (403) attempting approval via direct edit, project manager succeeds, and direct-to-completed is rejected (400) for any caller.

**2. Lost-update race in the Personal Access Token org-admin "descope" action (`backend/app/routers/orgs.py`).** `_get_org_pat_or_404` loaded the PAT row with a plain `db.get()`, and `descope_org_pat` did a read-modify-write on `allowed_organization_ids` (read the list, remove one org, write it back) with no row lock — at Postgres's default READ COMMITTED isolation, two concurrent descopes on the same multi-org token (e.g. org A's admin and org B's admin both reacting to the same incident at once, exactly the scenario this feature exists for) would each read the same pre-removal list, and whichever commits last silently overwrites the other's removal — the "losing" org's admin sees 204 and a real audit-log row claiming success, while the token remains scoped to their org regardless. Fixed with a `SELECT ... FOR UPDATE` row lock in `_get_org_pat_or_404` (the same pattern `lock_project_for_update`/`lock_organization_for_update` already use elsewhere in this file), so the second concurrent call blocks until the first commits, then reads the already-updated list. No new test — this class of fix isn't verifiable without real thread-level concurrency, which this codebase's existing lock-based fixes (`decide_change_request`'s own `.with_for_update()`, the org/project manager-count locks) also don't have automated coverage for; verified by the same code-reading/reasoning this session already applied to those.

**3. `deactivate_org_user` had no protection against ending an organisation with zero active admins, or against self-targeting (`backend/app/routers/orgs.py`).** Unlike the conceptually similar `leave_organization` (which refuses to let a sole admin leave), this endpoint had neither check, and didn't even block `user_id == current_user.id`. On inspection, the "last admin" case turned out to need no separate check at all: since the *caller* must already hold `org_admin` on this exact org to reach this endpoint, and `org_admin` (unlike project roles) is never derived indirectly, the calling admin's own role necessarily survives any deactivation they perform on someone *else* — so once self-targeting is blocked, zero active admins becomes unreachable through this endpoint by construction, with nothing further to check (added, then recognised as dead code once the self-targeting block was in place, and removed rather than shipped unverifiable — matching this project's "don't add validation for scenarios that can't happen" convention). The self-targeting block is the real fix: deactivation sets `is_active=False` on the *whole account*, not just this org's membership (unlike `leave_organization`), so an org-scoped admin action was able to lock a caller out of every organisation they belong to, with no confirmation step. New regression test in `test_rbac.py`: self-targeting rejected (400), a genuinely different admin can still deactivate normally.

**4. Password changes and 2FA enable/disable were never audit-logged (`backend/app/routers/auth.py`).** `change_password`, `confirm_2fa`, and `disable_2fa` all mutate security-critical account state and committed with no `log_event` call at all — the password-change notification is user-facing, not an admin-visible audit trail entry. Every other sensitive mutation in this codebase (role grants, deactivation, PAT bulk-revoke, SSO config changes, etc.) already calls `log_event`; these three didn't, and it isn't listed as an accepted exception in `docs/soc2/policies/system-operations-monitoring-and-logging-policy.md`. Fixed by adding `log_event` calls (`password_changed`, `2fa_enabled`, `2fa_disabled`) to all three. New regression test in `test_user_security.py`, querying the `audit_events` table directly (no existing test infra did this anywhere in the codebase before — added a small `_audit_action_count` helper following the same direct-DB-query pattern used elsewhere this session for PAT/storage-key regression tests).

**5. `mcp-server`'s org-slug lookup interpolated an unencoded query parameter into a URL path (`mcp-server/server.py`).** `_get_org_login_info` built `f"{REQTRACK_API_URL}/api/v1/orgs/by-slug/{slug}/login-info"` directly from the `?org=` query parameter. Reproduced concretely: a crafted `org` value containing `..` or an embedded `?` can make httpx's own URL normalization escape the intended path prefix or split the request at the wrong point, reaching a different backend path than intended. Confirmed low real impact today — this call is always anonymous (no caller token is ever forwarded), and every unauthenticated `GET` on the backend is already meant to be public (`/health`, `/metrics`, and this `login-info` lookup itself) — but fixed anyway with `urllib.parse.quote(slug, safe="")` so correctness here stops depending on that happening to remain true.

**6. OIDC SSO role sync only ever granted roles, never revoked them (`backend/app/services/oidc_provisioning.py`) — the "role ratchet" gap.** `sync_org_roles_from_claims` computed `mapped_roles - existing_roles` and only ever added rows; once a role was granted via a matching IdP group claim, removing the person from that group (or deleting the mapping) never revoked it on a later login — a real timely-deprovisioning gap (CC6.2/CC6.3-relevant) not previously documented anywhere. **Flagged to the user rather than fixed unilaterally**, since the correct semantics involve a genuine tradeoff (sync-down could, if done carelessly, strip a role an admin granted manually outside any SSO mapping, or over-react to a provider that simply doesn't send a groups claim at all) — approved, then implemented: sync-down now revokes exactly `(existing_roles & sso_managed_roles) - mapped_roles` on every login where the IdP *does* assert a groups/roles claim (even an empty one), where `sso_managed_roles` is every role appearing anywhere in `org.sso_group_mappings` — so a manually-granted role outside that vocabulary is never touched in either direction, and an IdP that omits the claim entirely (ambiguous with "doesn't support this claim" rather than "asserts zero groups") is left alone rather than triggering a mass revocation. New regression tests in `test_oidc_provisioning.py`: a role is revoked once its matching claim disappears; a manually-granted, mapping-external role survives; existing roles are left alone when the IdP sends no groups/roles claim at all.

**7. All three containers (backend, frontend, mcp-server) ran as root, with no `USER` directive and no documented rationale anywhere.** Not independently exploitable, but a real, missing defense-in-depth layer this project's own information-security policy commits to ("least privilege and defense in depth... no single control is treated as sufficient on its own"). **Flagged to the user rather than fixed unilaterally**, since getting this wrong (volume/file permission mismatches) risks breaking the running stack — approved, then implemented carefully: each Dockerfile now creates and switches to a dedicated non-root user (`app`/`nginx`/`mcp`), with the backend's `/app/data/files` mount point and the frontend's `/usr/share/nginx/html` + nginx runtime dirs (the frontend's own entrypoint script writes `env-config.js` there at container *startup*, not build time, so that directory needs to be writable by the runtime user, not just readable) explicitly `chown`'d ahead of time so a fresh named volume inherits the right ownership. `docs/deployment.md`/Dockerfile comments note that an *existing* deployment's already-created local-storage volume will still be root-owned after upgrading and needs a one-time `chown` (or a volume reset, consistent with this project's other pre-release "reset and reseed" upgrade path) — not a live gap in a fresh deployment, just a real migration note for an existing one. Verified directly (not just by code review, since a permissions mismatch would only surface at runtime): rebuilt all three images, did a full `docker compose down -v && up -d --build`, confirmed `id` inside each container reports the new non-root user, and specifically exercised the local storage backend's actual write path at its real mount point (`/app/data/files`) end-to-end as that user before trusting the fix.

**Not a finding**: header-injection into outgoing email (CRLF/BCC-injection via a crafted display name) — empirically verified clean; Python's `EmailMessage` header assignment raises on any embedded line-break-like character regardless of what user-controlled text is assigned. HTML-email-body injection — not applicable, this codebase only ever sends plain-text email. Mass assignment via `**payload.model_dump()` against an ORM object — grepped for the pattern across the whole codebase; every instance found builds a JSONB-column dict from validated nested schemas, never a blind ORM constructor call. CORS wildcard-with-credentials, exposed database ports in the production compose, and hardcoded real secrets — all checked, all clean.

**Adjacent robustness issue surfaced but explicitly not fixed (out of this review's scope)**: `send_daily_digests` has no per-user error isolation and defers its `db.commit()` to the end of the loop — an embedded newline in any `Notification.title` (titles are built from unconstrained `str` fields like `Project.name`) would raise inside Python's own header-safety check and silently break the digest for *every* user on *every* org, repeating daily until manually fixed. This is an availability/robustness bug, not a security vulnerability (no unauthorized access or data exposure), so it's noted here for future attention rather than fixed under a hardening review's scope.

**Verified for real**: all seven findings fixed have dedicated regression tests (except #2, the PAT-descope race, per its own entry's explanation). Full backend suite: 224 passed (221 + 3 new OIDC sync-down tests), zero regressions. `mcp-server`: 15 passed, 4 skipped (pre-existing, unrelated — the bootstrap admin's own org has no projects in a fresh reseed). Full Playwright suite: 16 passed, including a real end-to-end exercise of file upload/download against the now-non-root containers.

Explicitly requested as a third, still-deeper pass. Three more parallel reviews, scoped away from everything rounds 1-2 already covered: baselines/custom-field/report-template integrity; cross-tenant validation on resource-*creation* endpoints specifically (as opposed to prior rounds' focus on read/update paths); and a narrowly-scoped, analysis-heavy pair — quantifying whether the already-accepted "no account lockout" gap (which the project has always scoped to unbounded *password* guessing) also covers the 2FA challenge step, plus a check of frontend build/bundle exposure. **1. Adding a member to an org group never checked the member actually belonged to that organisation (`backend/app/routers/orgs.py`).** `add_org_group_member` validated that `group_id` belongs to `organization_id`, but never that `payload.user_id` holds any role in that organisation at all — unlike the structurally parallel `add_project_group_member` (`routers/projects.py`), which explicitly enforces C-U-02 ("all project users must be an organisation user") via `_require_user_in_org`. Because `get_effective_project_roles` resolves project access through org groups nested into project groups purely from `OrgGroupMember` rows (checking only that the *group's* org matches the project's, never that the *member* belongs to that org), an org admin adding an arbitrary user id here — anyone in the system, with zero relationship to the organisation — would silently hand that user full project access the moment the group is (routinely, legitimately) nested into any project group: a genuine cross-tenant privilege escalation, not a data-integrity nit. **2. A `new_requirement` change request's proposed component/category were never validated against the target project (`backend/app/routers/change_requests.py`).** `create_change_request`'s `modify_requirement` branch validates `requirement_id` against `project_id`, but the sibling `new_requirement` path never checked `proposed_component_id`/`proposed_category_id` the same way the direct-create endpoint (`create_requirement_endpoint`) does. Since there's no update endpoint for these fields (write-once, set only at creation) and `decide_change_request` only re-checks `is None` at approval time, an unvalidated cross-project reference would sail straight through approval and get baked permanently into a real `Requirement` row. Fixed by adding the equivalent project-membership check to the `else` branch. New regression test: `test_security_hardening.py::test_cannot_create_change_request_with_component_from_another_project`.

**3. The 2FA challenge step has no attempt limit, and the accepted "no account lockout" gap doesn't actually cover it (`backend/app/routers/auth.py`, `backend/app/security.py`).** The documented gap in `access-control-policy.md`'s Known Gaps is specifically about unbounded *password* guessing — a keyspace large enough that no realistic number of attempts converges toward success, so the absence of lockout there is a reasonable accepted risk. A TOTP code is a *bounded* 6-digit keyspace (10^6), and `verify_2fa` had no attempt counter at all: the 5-minute `2fa_challenge` JWT (`create_2fa_challenge_token`) is stateless and freely reusable for repeated guesses, `/login` (which mints a fresh challenge token) is equally unthrottled, and there's no rate-limiting middleware anywhere in this codebase. Quantified: even at a conservative sustained rate for this single-instance deployment, a single 5-minute window already yields single-digit-percent hit probability, and — critically — an attacker holding a stolen password can simply restart the login flow for a fresh window as many times as they like, since the challenge token itself carries no memory of prior failures. Unlike password guessing, repetition here compounds toward a near-certain eventual bypass rather than staying negligible, making this a materially different and more urgent risk than the already-accepted gap, not a restatement of it. **Flagged to the user for a decision** among per-account lockout, IP-based rate limiting, both, or leaving it as an accepted gap — per-account lockout was chosen. Fixed: `User` gained `failed_2fa_attempts`/`failed_2fa_locked_until`; `verify_2fa` now locks the *account* (not the challenge token) for `two_factor_lockout_minutes` (default 15) after `two_factor_max_failed_attempts` (default 5) consecutive wrong codes, checked before every code comparison — so restarting the login flow for a new challenge token does not reset the lockout, closing exactly the compounding-via-repetition path identified above. Both thresholds are configurable via `Settings`. New regression tests in `test_user_security.py`: repeated wrong codes lock out the account such that even the *correct* code (via a brand-new challenge token) is rejected until the window passes; a backdated `failed_2fa_locked_until` clears the lockout and a correct code succeeds again.

**Not a finding (Part 2 — frontend build/bundle exposure)**: `vite.config.ts` has no `build.sourcemap` setting (Vite's default is off) — confirmed by actually building the frontend and inspecting `dist/`: no `.map` files produced. No hardcoded secrets found in the built bundle or in `frontend/src` (the only credential-adjacent string is the expected, placeholder-valued `VITE_API_BASE_URL` runtime config). Storybook (`build-storybook`) is confirmed dev-only — `frontend/Dockerfile`'s build stage runs only `npm run build` and copies only `dist/`, and `.github/workflows/ci.yml`'s frontend job never invokes `build-storybook` — it is never built into or served by the production image.

**Not a finding (baselines/custom fields/report templates)**: no issues found in this area on this pass.

## Orphaned-account review: server-admin false positive, and closing the "nobody can act on this" gap

The user noticed two problems with the C-A-13 orphaned-accounts review (`GET /api/v1/system/users?no_org_membership=true`): server admins were being listed as "orphaned," and the review page had no action at all — read-only, with no way to do anything about a listed account.

**Server admins incorrectly flagged as orphaned.** A server admin has no organisation membership *by design* (I-M-05) — that's the intended shape of the role, not an oversight — so `no_org_membership=true` now always excludes `is_server_admin=True` users, regardless of any other filter. A new, independent `is_server_admin` filter lets a server admin review the server-admin roster specifically (deliberately *not* restricted to org-less accounts, since I-M-08 lets a bootstrap server admin also hold an organisation of their own).

**No way to act on a listed orphaned account.** Investigation showed this wasn't just a missing button — there was no *endpoint* that could reach one. `deactivate_org_user`/`archive_org_user` (`routers/orgs.py`) both require the target to already belong to the acting admin's organisation (a SOC 2 hardening fix from an earlier pass) — which an orphaned user, by definition, never does. So the exact accounts this review exists to surface were the one category of user nobody in the system could ever deactivate. Two new system-level endpoints close this, deliberately scoped to only ever touch org-less accounts (`_require_orphaned_user`, 400 otherwise — an org member must still be managed through their own organisation's admin console, keeping a server admin's authority tenancy-wide but content-free per I-M-05):
- `POST /api/v1/system/users/{id}/deactivate` (C-U-04; blocks self-targeting)
- `POST /api/v1/system/users/{id}/reactivate` — a genuinely new capability: no lifecycle action anywhere in this codebase previously reversed a deactivation at all, org-scoped or otherwise.

**Grant/revoke server admin got a UI, and a safety net it didn't have before.** `PUT /api/v1/system/users/{id}/server-admin` (I-M-06) already existed but had no frontend surface at all. Building one surfaced a real, previously-unexploited gap: nothing stopped a server admin from revoking their *own* flag (or another's) down to zero active server admins deployment-wide — an unrecoverable lockout, since nobody would then hold the authority to grant it back to anyone short of direct database access. Fixed by rejecting a revocation that would leave zero active server admins (counting only active ones, since a deactivated admin can't do anything anyway) — the same "last admin" shape as `leave_organization`'s existing sole-org-admin check, just computed by count rather than self-targeting alone (a server admin can revoke *someone else's* flag too, not just their own).

## Bug: OrgAdminPage hung forever for a server admin (or anyone) with no role in that org

The user reported a specific org admin URL stuck on "Loading…" forever. Root cause: `OrgAdminPage.reload()` bundles five API calls (`org`, `groups`, `resources`, `projects`, `report-templates`) in one `Promise.all` with no error handling at all, called from a `useEffect` with no `.catch()`. Every one of `groups`/`resources`/`report-templates` requires at least `member` in that specific organisation; a caller with no role there (a server admin browsing the org list they can always see, or a stale bookmark) gets a 403 on all three, the `Promise.all` rejects, `org` state is never set, and the page's only loading gate (`if (!org) return <Spinner />`) spins indefinitely with nothing but a silent unhandled-rejection in the console.

**First fix**: wrapped the bundle in try/catch, added a `loadError` state, and rendered the actual error message (`ApiError.message`, e.g. "Insufficient organisation permissions.") with a link back to Organisations instead of hanging. This alone would have been a regression for server admins, though: I-M-05's one documented carve-out is that a server admin can create an organisation and its initial user with zero prior role — but the *only* UI for that ("Organisation users → New user") lived inside the very page this fix now blocks outright for exactly that caller.

**Investigating that surfaced a real, separate gap**: the user asked how a server admin is supposed to manage/set up an org's users at all if they can't access it. Tracing the actual authorization rules: `create_org_user` (`POST /orgs/{id}/users`) already allows `require_org_admin_or_server_admin` — creating a *new* native user works fine with zero prior role. But `assign_org_role` (the only way to grant a role to an *existing* user) requires the caller to already be `org_admin` of that org — a chicken-and-egg that meant a server admin had no way to make *themselves* admin of an org they created, only to bootstrap someone else's account. This matters for self-hosting deployments specifically, where the server admin is the only person running the system and wants to use their own org, not just provision customers' orgs (a hosting-company shape the existing carve-out already covered fine).

**New endpoint**: `POST /orgs/{id}/join-as-admin` (`routers/orgs.py`) — server-admin-only, self-targeting only, always grants exactly `org_admin`, 400 if already an admin. Deliberately not a general "server admin can grant any role to any user in any org" capability (see access-control-policy.md's amended item 1) — it only lets the platform's single most-trusted actor take on ordinary membership in one specific org, for themselves, mirroring the one-time `server_admin_create_org` bootstrap behaviour (`services/bootstrap.py`) as a general, repeatable, in-app action instead.

**`OrgAdminPage` degraded view**: when the initial bundle 403s, a server admin now sees the org's name (fetched standalone — `GET /orgs/{id}` already has its own server-admin bypass, which is exactly why this one call would have succeeded inside a bundle that otherwise failed) plus two actions: "Become admin of this organisation" (calls `join-as-admin`, then reloads — succeeds fully since they're now a genuine member) and "Create its first admin user" (a minimal email/name/password form posting to the existing `create_org_user` with `role: "org_admin"`, for the hosting-company case where the server admin bootstraps someone *else's* account and deliberately doesn't become a member themselves). A non-server-admin hitting the same 403 still sees the plain error page — they have no carve-out to offer.

New regression tests in `test_audit_fixes.py`: joining as admin works and immediately unlocks ordinary org-admin actions; joining twice is rejected (400); a non-server-admin (even one who's an admin elsewhere) is rejected (403). Manually verified both flows end-to-end in a real browser: created two fresh orgs, used "Become admin" on one (landed on the full, normal admin page afterward) and "Create its first admin user" on the other (confirmed via a direct login as the newly-created account that it can actually administer that org).

**Verified for real**: full backend suite: 238 passed (235 + 3 new), zero regressions. Full Playwright suite re-run once on freshly reseeded data: 16 passed. `docs/soc2/policies/access-control-policy.md` amended (Authorization item 1) to document both server-admin carve-outs precisely, since this is exactly the kind of authorization-surface change CLAUDE.md requires flagging.

## Organisation disable and hard delete

The user asked for a way to handle an organisation that's stopped paying for hosting or simply needs to be archived — offered the choice of a reversible disable, an irreversible hard delete, or both; the user chose both, in the same pass.

- **Disable is a pure access gate, not a data-affecting operation.** `Organization.is_active`/`disabled_at`/`disabled_by` are the only new columns; nothing else changes when an org is disabled. A new `_require_org_active(db, organization_id)` helper in `services/rbac.py` is called — after PAT-scope checks, before the role check — from every org/project-scoped dependency factory (`require_org_role`, `require_org_admin_or_server_admin`, `require_project_role`, `require_project_view`, `require_project_manage`), raising 403 "This organisation has been disabled." **This deliberately blocks the org's own admins too**, not just outsiders — a disable that the org's own admin could route around wouldn't be a usable "stop this org" control at all. It is deliberately *not* applied to `require_server_admin`, `join_organization_as_admin`, or the disable/enable/delete endpoints themselves, since the server admin must always be able to toggle an org's state regardless of its current state, and login itself is untouched (a disabled org doesn't lock out a user who belongs to other, active orgs).
- **Delete is irreversible and gated behind typing the organisation's exact current name** (`OrganizationDeleteConfirm.confirm_name`, checked server-side in `DELETE /orgs/{id}`, not just a client-side guard) — the same "type the name to confirm" pattern used by GitHub/GitLab repo deletion, appropriate given there is no undo.
- **Cascade strategy: DB-native `ON DELETE` actions on the FK columns, not ORM `cascade=` relationships.** Nearly every cross-reference in this codebase is a plain FK column queried via `select()`, not a declared SQLAlchemy `relationship()` collection, so `ondelete="CASCADE"`/`ondelete="SET NULL"` on the column definitions themselves (added across `models/{organization,project,requirement,change_request,custom_field,notification,audit,engagement}.py`) is the mechanism that actually matches how the code reads data, rather than adding a parallel ORM-level cascade layer that would only fire on ORM-mediated deletes. Audit trail rows use `SET NULL` (not `CASCADE`) on `AuditEvent.organization_id`/`project_id` specifically — the audit *row* survives (its `entity_type`/`entity_id`/`detail` already capture the substance of what happened, and the row itself has ongoing compliance/incident-investigation value), only the FK link to the now-gone org is nulled.
- **Three things a DB cascade cannot clean up, handled explicitly in `services/org_deletion.py::delete_organization_cascade`**: (1) real object-storage bytes — a DB-only cascade would delete `FileAsset` rows but leave orphaned bytes in S3/local storage, which `data-retention-and-disposal-policy.md` already treats as a disposal failure, so every file asset is routed through the existing `delete_file()` (removes bytes *and* row) before the org row itself is deleted; (2) `PersonalAccessToken.allowed_organization_ids`, a JSONB list rather than a real FK — every PAT scoped to the deleted org has that org's id stripped from its list (mirroring the existing `descope_org_pat` logic exactly), auto-revoking the token if the list becomes empty; (3) two genuinely polymorphic tables with no real FK at all (`ReviewComment.target_id`/`target_type`, `Subscription.entity_id`/`entity_type`) — a DB cascade would silently orphan these rather than error, so they're deleted explicitly by id, scoped to the org's requirement/change-request ids, before the cascade runs.
- **Users are never deleted, only their `UserOrgRole` rows** (removed via cascade) — a user who loses their only org membership this way becomes "orphaned," a case the access-review tooling already covers (see the "Orphaned-account review" section above).
- **`ServerOrganisationsPage.tsx`** gained a Status column and per-row Disable/Enable/Delete actions (`window.confirm` for disable, since it's reversible; an inline card requiring the exact name for delete, matching the backend's own check so the button is genuinely disabled — not just hidden — until it matches). **`OrgAdminPage.tsx`**'s existing degraded-view logic (from the section above) gained a third branch: when the 403 message indicates the org is disabled, a server admin sees the org's name plus an "Enable this organisation" action instead of the join/create-admin actions, which only make sense for "not a member," not "disabled."
- **Fixed a now-stale assertion while doing this**: `server-admin-scope.spec.ts` previously asserted a server admin's degraded view showed *zero* instances of the org's name — true before the join-as-admin degraded view existed, false now that showing the org name is precisely how that view (and this new disabled-org view) lets the admin confirm which org they're looking at before acting. Updated to assert the name renders as a heading while `Users`/other content still does not.

**Verified for real**: 10 new backend tests (`test_org_lifecycle.py`), including one, `test_delete_cascades_through_everything_including_non_fk_references`, that creates one of literally everything an org can own (project, requirement, comment+reaction, subscription, change request, an uploaded file with real storage bytes, a solo-scoped PAT, a second two-org PAT) and asserts each category is actually gone — not merely orphaned — after deletion, while confirming the surviving member's user row, the two-org PAT (now scoped to just the remaining org), and the audit trail (rows survive, `organization_id` now null, plus exactly one new `action="deleted"` event) all behave exactly as designed. Full backend suite green, zero regressions. New `server-org-lifecycle.spec.ts` Playwright spec drives the full create → disable → re-enable → delete-with-confirmation flow through the real UI; full Playwright suite re-run clean on freshly reseeded data. Manually re-verified the same flow once more directly in a browser against the live dev stack (create "Manual Test Org," disable, confirm "Disabled" badge, enable, confirm "Active" badge, delete with a wrong name first to confirm the button stays disabled, then the exact name, confirm the row disappears).

`docs/soc2/policies/data-retention-and-disposal-policy.md`'s Known Gaps item 1 updated to reflect that hard deletion is no longer an unbuilt gap for organisations specifically (still true for individual users/projects in isolation, which remain deactivation/archival-only).

### Hardening-pass follow-up

Per CLAUDE.md's requirement to run the identify → verify → remediate review for security-sensitive changes, a dedicated hardening pass was run against this feature after it shipped: two parallel candidate-identification sub-agents (backend RBAC/cascade-delete logic; frontend/API surface), then a fresh, independent verification sub-agent per candidate finding — the same process used by this codebase's earlier hardening passes (see "Security hardening pass" above). All five candidates were confirmed real; none were false positives.

**Fixed:**

- **WebSocket connections fully bypassed the org-disable gate** (`routers/ws.py`). `project_updates` authorizes inline (its own `UserProjectRole`/`ProjectGroupMember` query) rather than through one of the five `require_*` dependency factories, so it was never wired to `_require_org_active` at all — not just the documented "already-open socket keeps streaming" exception, but a full bypass: a member could open a **brand-new** connection to a disabled org's project and stream indefinitely. Fixed by resolving the project's organisation id at handshake and rejecting (code 4403) if it's disabled, and by extending the existing periodic re-check (`_user_session_still_valid`, already used for `token_version`/`is_active` revocation) to also re-check `Organization.is_active`, so an already-open connection now closes within one `_EXPIRY_CHECK_INTERVAL_SECONDS` interval too — matching the account-deactivation guarantee this same function already provided. A new boolean-returning `rbac.is_org_active` was added alongside the existing exception-raising `_require_org_active`, since a WebSocket handler can't propagate an `HTTPException` and needs to translate the check into its own close code instead.
- **File downloads fully bypassed the org-disable gate** (`routers/files.py`). `download_file` authorizes via the raw `get_effective_org_roles`/`get_effective_project_roles` helper functions rather than a `require_*` dependency (it needs `?token=` query-param support for `<img src>` use, which those don't offer), so — like the WebSocket case — it was never wired to the check at all. A disabled org's shared-resource files and requirement attachments both remained fully downloadable by any member who still held a role row. Fixed by calling `_require_org_active` explicitly on both code paths, resolving the organisation id via the file's own `organization_id` (org-resource case) or via the new `_project_organization_id` helper (requirement-attachment case), matching the pattern `require_project_view` already uses.
- **Hard-deleting an organisation that had ever had a logo or SSO login-background image set crashed outright, and destroyed other files' storage bytes in the process.** `Organization.logo_file_id`/`login_background_file_id` are self-referential FKs to `file_assets` with no `ondelete` action (an oversight in the original FK-coverage sweep — every *other* org/project-scoped FK got one). `delete_organization_cascade`'s file-deletion loop calls `delete_file()` (which deletes storage bytes before the DB row) on every `FileAsset` the org owns, including its own logo/background asset, with nothing nulling those two columns first — deleting that one `FileAsset` row raised a raw, unhandled `IntegrityError` (no handler exists in `main.py`, so this surfaced as a 500), discovered only via SQLAlchemy's autoflush partway through the loop, by which point every file processed *before* the crash had already had its storage bytes irreversibly deleted while its DB row (and the org's) survived the rolled-back transaction — orphaned metadata pointing at bytes that no longer exist, for an org that wasn't even successfully deleted. Verified via a live repro against the test database before fixing. Fixed with a single targeted Core-level `UPDATE` nulling both columns before the file-deletion loop runs, so the FK reference is gone before any `FileAsset` row is touched — this removes the crash and, since the loop can no longer fail partway through, the storage-data-loss blast radius along with it.
- **`GET /me/reviews/due` leaked requirement metadata (unique code, name, review date) from a disabled organisation indefinitely.** This is the one org-content read in the app with no single `project_id`/`organization_id` path parameter to hang a `require_*` dependency off (it deliberately spans every project the caller has a role in), so it had never been wired to any org-scoping check at all, let alone `_require_org_active`. Fixed by joining `Project`/`Organization` into the existing query and filtering `Organization.is_active`. `get_due_reviews_for_project` (the project-scoped sibling, used by `routers/requirements.py`'s `GET .../reviews/due`) was already covered for free via its `require_project_view` dependency and needed no change.
- **An organisation created with a blank or whitespace-only name defeated `DELETE /orgs/{id}`'s "type the exact name to confirm" safety gate.** `OrganizationCreate.name` had no length or blank validation; for an org named `""`, both the frontend's `deleteConfirmText !== org.name` check and the backend's own `confirm_name != org.name` check are trivially satisfied by an empty string, so the "must not be a stray click" guarantee that gate exists for silently didn't hold for such an org. Fixed with a `field_validator` on `OrganizationCreate.name` that strips surrounding whitespace and rejects a blank result (422), applied only at creation — there is no separate org-rename endpoint. Requires an already-server-admin actor to trigger in the first place (org creation is server-admin-gated), so this was a self-inflicted footgun rather than a privilege-escalation path, but still a genuine defeat of a documented safety control.

**Verified for real**: 7 new backend regression tests (2 in `test_websocket_security.py` covering both the handshake rejection and the periodic-recheck path; 5 in `test_org_lifecycle.py` covering both file-download code paths, the logo/login-background delete-crash fix — reproducing the exact scenario that used to 500 — the reviews-due leak, and blank/whitespace-name rejection including that meaningful surrounding whitespace is still trimmed, not rejected). Full backend suite: 255 passed (248 + 7), zero regressions. Three pre-existing tests in `test_ws_active_recheck.py` updated for `_user_session_still_valid`'s new `organization_id` parameter — no behavioural change for those, since they pass `None`.
