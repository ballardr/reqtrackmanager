# Decisions Log

This log records architectural and implementation decisions made while building ReqTrackManager to the **Ossa (v1)** and **Pelion (v2)** milestones defined in [docs/requirements.md](requirements.md). It exists so future contributors understand *why* the system looks the way it does, not just what it does. `docs/requirements.md` is authoritative and unchanged; this log explains how ambiguous or underspecified requirements were interpreted in code.

## Scope

Ossa (v1) implements every row in `docs/requirements.md` tagged `Ossa (v1)`, at both `Requirement` and `Recommended` priority. Pelion (v2) additionally implements every row tagged `Pelion (v2)`, built directly on top of the Ossa (v1) codebase (nothing from v1 was removed or restructured). Everything tagged `Massif (v3)` or `Murchison (v4)` was **not** built, including: task assignment/voting in change-request review, the standalone provisioning API/port, SSO/OAuth wiring, and IBM DOORS import/export. The "Pelion (v2)" section below records the scoping and implementation decisions made for that milestone; everything above it predates and still applies.

## Authentication and identity

- **Native auth now, SSO seam only.** `AuthBackend` (`backend/app/auth_backends/base.py`) is a small protocol with one implementation, `NativeAuthBackend` (email + bcrypt password). C-U-06/C-U-07 ask for pluggable backends and optional OAuth/SSO; actually wiring Keycloak/Authentica is Pelion-adjacent (E-U-01) and wasn't built, but the seam exists so adding a second backend doesn't require touching the rest of the app.
- **Login IP logging without geolocation (C-A-07).** Every login attempt writes a `login_events` row with the raw IP. Resolving IP → location was deliberately left as a nullable `location` column rather than calling an external geo-IP service at login time, to avoid a runtime network dependency and an API-key requirement in a self-hostable product. Follow-up: wire an offline MaxMind-style database when this becomes a priority.
- **Server admin bootstrap (I-M-05/06/08).** `backend/app/services/bootstrap.py` runs on every app startup (idempotent): creates the configured server-admin user if absent, and — if `SERVER_ADMIN_CREATE_ORG` is enabled — a default organisation with that user as org admin, matching the "on first install" wording without needing a separate CLI step.

## Roles and permissions

- **Fixed role vocabulary, not customisable permissions.** Ossa (v1) uses exactly the org roles (`org_admin`, `project_creator`, `member`) and project roles (`project_manager`, `project_administrator`, `stakeholder`, `member`) from C-U-01/C-U-03. Customisable permission schemes are a Pelion/Massif-era concern; project groups (C-U-11) are therefore just a way to bulk-assign one of these four fixed roles, not a general permission-authoring tool.
- **Project manager implies administrator + stakeholder.** Per the C-U-03 clarification, `get_effective_project_roles` (`backend/app/services/rbac.py`) folds `PROJECT_MANAGER` into also granting `PROJECT_ADMINISTRATOR` and `STAKEHOLDER` capabilities, and any assigned role implies baseline `MEMBER` (view) access.
- **Org admin ≠ automatic project content access.** The C-U-01 clarification ("no project access is guaranteed... apart from org admin being able to manage project settings") is implemented as two separate dependencies: `require_project_manage` (org admins pass) for settings/stage/component/group endpoints, and `require_project_view` (org admins do **not** automatically pass) for requirement/change-request content. An org admin who also wants to read requirements needs an explicit project role, same as anyone else.
- **Org-group nesting resolves one level deep.** A `ProjectGroupMember` row may point at a user or an org group (C-U-12); permission resolution flattens org-group membership into the containing project group's role. Cycle prevention is limited to not letting a group contain itself — deeper nested-group graphs aren't a requirement here and would add complexity with no described use case.
- **C-U-08/C-U-09 (must always have a manager).** Enforced two ways: `revoke_project_role` blocks removing the last direct project-manager assignment, and `deactivate_org_user` (in `backend/app/routers/orgs.py`) checks every project in the org after deactivating a user — if that removal leaves a project with zero managers, the *acting admin* is assigned as manager, matching the requirement's specific wording.

## Requirement lifecycle and change management

- **Identity vs. version split, not `valid_from`/`valid_to` on one row.** `solution-architecture.md` suggests temporal columns directly on core entities; in practice, `Requirement` holds only stable identity (project/component/category, generated code, creator, archival state) while `RequirementVersion` holds every mutable field plus `valid_from`/`valid_to`/`version_number`. The "current" version is the row with `valid_to IS NULL`. This gives the same point-in-time query capability with a simpler mental model: identity never changes, content always changes through a new version row. Change requests mirror the same pattern (`ChangeRequestVersion`).
- **Locking is per-requirement, not per-project-stage.** C-G-12 says changes are change-request-only "once a requirement is approved for a project stage." This is implemented as `is_locked` = the requirement's current version status is `approved` or `completed` — checked directly rather than by asking whether the project's current stage is approved. Approving a stage (`backend/app/services/baseline.py`) bulk-transitions every non-archived requirement still in `draft`/`reviewed` to `approved` and snapshots a `Baseline`/`BaselineItem` row per requirement (C-G-10) in the same transaction, so in practice stage approval and the lock happen together — but the lock itself is a property of the requirement, which is what C-G-12 actually says.
- **Unique requirement IDs (C-G-06/C-G-07).** `{component.prefix}-{category.prefix}-{project.next_requirement_seq:03d}`, e.g. `SW-PERF-014`. The sequence is a per-project counter that only increments, so archived requirements' numbers are never reused, satisfying the C-G-06 clarification.
- **Ordering is move-up/move-down, not drag-and-drop (C-E-01/02/03).** Each orderable entity (`ProjectComponent`, `ProjectCategory`, and a requirement's `sort_order` within its component/category) has a persisted integer position and a `/move` endpoint that swaps it with its neighbour. This satisfies the requirement without a drag-and-drop dependency in the frontend; requirement reordering is additionally blocked outside the scoping stage, per the C-E-03 clarification.
- **Discussion threads are not the change log (C-A-09 clarification).** `ReviewComment` (discussion, C-R-01) and `RequirementVersion`/`ChangeRequestVersion` (change log) are separate tables from the start, so the UI's change-log view never needs to filter comments out after the fact.

## Documentation contradiction: C-A-08 vs. notifications

C-A-08 ("date/time a notification was read must be recorded") is tagged `Ossa (v1)`, but the entire notification feature (C-N-01 through C-N-05) is tagged `Pelion (v2)`. There is nothing for a "notification read" event to attach to in v1. Rather than build a speculative read-receipt schema ahead of the feature it depends on, this was treated as a documentation dependency and deferred alongside notifications themselves — flagged here per the project's instruction to challenge assumptions rather than implement contradictory requirements literally.

## Reporting

- **ReportLab over WeasyPrint for PDF (R-F-01).** ReportLab is pure-Python with no system-level dependencies (WeasyPrint needs Cairo/Pango), which keeps the backend Docker image simple. Markdown pre/post sections (R-G-01/R-G-02) are parsed with `markdown-it-py` and walked token-by-token into ReportLab flowables (headings, paragraphs, bullet lists) — enough fidelity for introduction/appendix-style content without a full HTML rendering stack.
- **CSV export (R-F-02)** is a straightforward tabular dump of the same requirement rows used for the PDF table.

## Realtime

- **WebSocket pub/sub is in-process (I-A-04).** `backend/app/services/pubsub.py` is a single-process broadcaster; the endpoint is explicitly optional per the requirement text ("may expose"), and a single-backend-instance deployment is exactly what Ossa (v1)'s deployment model is. Scaling to multiple backend replicas would need a shared broker (Redis pub/sub or similar) — a natural extension point, not a v1 requirement.

## Infrastructure

- **Enum columns use `sqlalchemy.Enum(..., native_enum=False)`, not plain `String`.** An early version used `Mapped[SomeEnum] = mapped_column(String(N))`, which stores correctly but returns a plain `str` (not the enum) on read — anything calling `.value` on a freshly-loaded attribute would crash. `models/base.py::str_enum()` fixes this while keeping the column a plain VARCHAR (no Postgres `CREATE TYPE`/migration friction when adding a new enum member).
- **Migrations run automatically at startup (I-M-02/I-M-03).** `backend/app/migrations.py::run_migrations()` runs `alembic upgrade head` from the FastAPI lifespan handler before the bootstrap step. A fresh or upgraded deployment self-migrates on boot instead of requiring an operator to run Alembic by hand first and failing with raw "column does not exist" errors in the meantime.
- **One hand-written initial migration.** `alembic/versions/0001_initial.py` creates the schema via `Base.metadata.create_all()` rather than 22 transcribed `op.create_table()` calls, keeping the migration in lockstep with the models (the single source of truth). Future schema changes should be added as normal incremental Alembic migrations generated with `--autogenerate`.
- **Observability: metrics/health always on, Loki/Tempo/Grafana/Alloy opt-in.** The Ossa-tagged requirements (I-M health checks, Prometheus `/metrics`) are wired into the default `docker compose up`. The broader Loki/Tempo/Grafana/Alloy stack described in `solution-architecture.md` is architecture-level, not individually Ossa-tagged, so it's an opt-in Compose profile (`docker compose --profile observability up`) — the default stack stays fast to start. The backend does not yet emit OpenTelemetry traces; the Alloy config's OTLP receiver is ready to forward them to Tempo the moment that instrumentation is added.
- **i18n (U-U-02): a single string table, not a full i18n library.** `frontend/src/i18n/strings.ts` centralises every UI string behind a `t()` lookup. No second language ships in v1, but no component hardcodes text inline, so adding a translated locale is additive rather than a rewrite.

## Security hardening pass

After the initial v1 build, a dedicated hardening pass was run: two parallel vulnerability-scan sub-agents (backend; frontend/infra) proposed candidate findings, then each candidate was independently re-verified by a fresh sub-agent against a strict false-positive rubric before anything was treated as real. Five findings were confirmed and fixed; two were deliberately excluded as false positives. Regression tests for every fix live in `backend/tests/test_security_hardening.py`.

**Fixed:**

- **IDOR: requirement links/comments not scoped to project** (`backend/app/routers/requirements.py`). `create_link`/`list_links`/`add_comment`/`list_comments` validated the caller's role against the `project_id` path param but never checked that `requirement_id` actually belonged to that project — a member of Project A could read or write comments/traceability links on any requirement in Project B just by knowing its id. Fixed via a shared `_get_requirement_in_project` helper (also now validates a link's `target_requirement_id` the same way) that every such handler calls before touching the resource.
- **IDOR: change-request comments not scoped to project** (`backend/app/routers/change_requests.py`). Same bug, same fix pattern (`_get_cr_in_project`), for `add_comment`/`list_comments` on change requests.
- **Privilege escalation: project-group membership across projects** (`backend/app/routers/projects.py`). `add_project_group_member`/`remove_project_group_member` were gated by `require_project_manage` against `project_id`, but never checked that `group_id` belonged to that project. A manager of *any* project could look up another project's default "Project Managers" group id (visible to anyone with view access to that other project) and add themselves to it via their *own* project's manage-permission check, inheriting the other project's manager role. Fixed with `_get_group_in_project`.
- **Cross-tenant escalation: org-group membership across organisations, and cross-org group nesting** (`backend/app/routers/orgs.py`, `backend/app/routers/projects.py`, `backend/app/services/rbac.py`). Same missing-ownership-check pattern for org groups (`add_org_group_member`/`remove_org_group_member` didn't verify the group belonged to the `organization_id` in the URL), plus a related and more structural gap: nesting an org group into a project group (`add_project_group_member` with `org_group_id`) never checked that the org group belonged to the *project's own organisation* — an org group from a completely different organisation could be nested in, and `get_effective_project_roles`'s nested-group resolution would grant its members the project role regardless of tenant boundary. Fixed at both the write path (reject nesting a foreign-org group) and, as defense in depth, the read path (`get_effective_project_roles` now joins through `Project`/`OrgGroup` and only honours nested-group rows where the org group's organisation matches the project's organisation).
- **ReportLab markup injection (SSRF / local file read) in PDF reports** (`backend/app/services/reports.py`). `Paragraph()` from ReportLab parses its `text` argument as a restricted markup language (`<b>`, `<font>`, `<img src="...">`, etc.), not plain text. Requirement names/reasoning, the project name, and the custom pre/post Markdown report sections are all user-supplied and were passed to `Paragraph()` unescaped — a `<img src="file:///etc/passwd">` or an internal-URL `<img>` tag would be parsed as real markup and fetched/rendered server-side by ReportLab (whose pre-5.0 default `trustedSchemes` include `http`, `https`, and `file`), any project member being able to trigger it via the report-generation endpoint. Fixed by escaping (`xml.sax.saxutils.escape`) every user-controlled string before it reaches `Paragraph()` — table cells, the title, and rendered Markdown block content — so `<`/`>`/`&` always render as literal characters rather than being parsed as markup.

**Considered and excluded as false positives** (per the review's filtering criteria):

- *Unescaped `VITE_API_BASE_URL` in the generated `env-config.js`* — the value only ever comes from an operator-set `docker-compose.yml` environment variable, which is a trusted deploy-time input, not attacker-controlled; no path exists in this codebase for an external party to influence it.
- *Postgres port (5432) published to the host in `docker-compose.yml`* — at the time, this was the documented local-development quick-start compose file (alongside hardcoded dev-only credentials already flagged as "override in production"), so publishing the port was judged a defense-in-depth/hardening consideration rather than a concrete flaw. **Update (Pelion v2 infrastructure split):** the root `docker-compose.yml` is now the production-oriented stack, and no longer publishes the Postgres port at all — the dev/test stack that still does so (`tests/container/docker-compose.yml`) is unambiguously not production-facing, so this is no longer even a judgment call.

## Testing

- **Backend tests run against real PostgreSQL, not SQLite.** The schema uses Postgres-specific types (`UUID`, `JSONB`), so `backend/tests/conftest.py` creates a dedicated `reqtrack_test` database on the same Postgres server used by docker-compose, with tables truncated between tests rather than mocking the database.
- **A Playwright E2E suite (`tests/playwright/`) runs against the actual docker-compose stack** (not a dev server), exercising the full golden path in a real browser: login → create project → components/categories → requirement → stage approval (lock) → change request → PDF report → theme toggle. This is the only reliable way to confirm the shipped Docker images actually work together, not just that each service passes its own tests in isolation.

## Pelion (v2)

Pelion (v2) implements every row in `docs/requirements.md` tagged `Pelion (v2)`, on top of the Ossa (v1) codebase above. It reuses existing v1 architecture wherever possible (the identity/version split, the RBAC dependency style, the audit-event helper, the router/schema/service layering, and the frontend's `t()` string table) rather than introducing parallel mechanisms.

### Schema migration strategy

- **Squashed into the same `0001_initial.py` baseline, not a second migration.** Every Pelion v2 model change (new columns on `User`/`Organization`/`Project`/`RequirementVersion`/`ChangeRequestVersion`, and new tables for files/notifications/custom fields/favourites) was added directly to the existing models and folded into `alembic/versions/0001_initial.py`'s `Base.metadata.create_all()`, rather than written as an incremental `op.add_column`/`op.create_table` migration. This only works because `create_all()` reflects the *current* model state at the time it runs — attempting to layer a second migration on top produced "column already exists" errors, since 0001 would create the new columns too. This is a deliberate pre-release-only shortcut: there is no real production deployment yet to preserve data for, so squashing is safe. **The moment this system has a real deployed database that must be upgraded in place, all future schema changes must go back to normal incremental Alembic migrations** (`alembic revision --autogenerate`) rather than editing 0001 again — the docstring at the top of that file repeats this warning.
- **`tests/conftest.py`'s schema fixture now runs real Alembic (`run_migrations()`) against a `DROP SCHEMA public CASCADE`/`CREATE SCHEMA public` reset**, instead of calling `Base.metadata.create_all()`/`drop_all()` directly. The app's own startup path runs `alembic upgrade head` every boot (Ossa v1's I-M-02/03 decision); tests need to exercise that same path rather than a second, divergent schema-creation mechanism. Per-test cleanup uses a single `TRUNCATE ... CASCADE` statement rather than per-table `DELETE` in dependency order, because `use_alter`-based FK cycles (e.g. `users.avatar_file_id` → `file_assets` → `file_assets.uploaded_by` → `users`) make a strict deletion order impossible to compute generically.

### Files and storage

- **Pluggable storage backend, exercised for real via MinIO, not just implemented in the abstract.** `backend/app/storage_backends/{base,local,s3}.py` defines a `FileStorageBackend` protocol with `LocalFileStorageBackend` (filesystem) and `S3CompatibleFileStorageBackend` (boto3; works against MinIO or real S3), selected via `STORAGE_BACKEND=local|s3`. MinIO is added to the default `docker-compose.yml` stack and is the default backend, so I-M-10 ("must support different storage backends") is verified against an actual running S3-compatible service during manual and automated verification, not only against local disk.
- **A single `file_assets` table backs every upload use case** (requirement attachments, org shared resources, avatars, org logos) rather than one table per use case, since they all need the same metadata (storage backend, key, filename, content type, size, uploader). Requirement attachments additionally go through a `requirement_files` link table (many-to-many, so the same shared org resource can be linked to multiple requirements per C-M-04 without duplicating the file).
- **Local backend path-traversal defense in depth.** Storage keys are always generated by `app/services/files.py` (UUID-based), never taken from user input directly, so path traversal via a key isn't attacker-reachable in practice — but `LocalFileStorageBackend._path_for()` still resolves the path and checks `is_relative_to()` the base directory before any read/write, as defense in depth rather than relying solely on that invariant holding forever.
- **Disk-usage monitor (I-M-11) is a single testable function plus a thin timer loop.** `check_disk_usage_once()` in `backend/app/services/disk_monitor.py` contains all the actual threshold/dedup logic and takes the storage backend and prior warned-state as plain arguments; `run_disk_monitor_loop()` is just a 15-minute `asyncio.sleep` wrapper around it. This split exists specifically so the branching logic (warn once, don't repeat while still over threshold, re-warn after recovery) can be unit-tested (`backend/tests/test_disk_monitor.py`) without waiting on the real timer or touching a real filesystem's `shutil.disk_usage`.

### Notifications

- **In-process asyncio background tasks, not a separate worker service.** Both the instant-notification email path and the daily-digest batch job run as `asyncio` tasks started from the FastAPI lifespan handler, consistent with the existing single-instance WebSocket pub/sub pattern (`services/pubsub.py`). A dedicated worker service is a real future step (already called out in `solution-architecture.md`'s "Production deployment path") once a single backend replica stops being sufficient — not required for this deployment model.
- **MailHog as the default SMTP endpoint.** Rather than requiring a real mail provider to exercise C-N-01–05, the default Compose stack runs MailHog and points `SMTP_HOST`/`SMTP_PORT` at it, so sent notification emails are genuinely inspectable (http://localhost:8025) during development, testing, and manual verification — not just logged or mocked.
- **Notification triggers were added at existing call sites**, not as a generic event-bus: project-group join, stage transitions, change-request submit/decide, password change, and org-role permission grant. Permission *revocation* does not currently fire a notification — only grant does; this is a narrower interpretation of C-N-04 than might be expected and is a candidate follow-up if revocation notifications turn out to matter in practice.

### Customisation

- **Custom field values reuse the existing version-history mechanism instead of a second, parallel history system.** `CustomFieldDefinition` (project-scoped, `entity_kind` requirement|change_request) defines the schema; the actual *values* live in a plain `custom_fields JSONB` column added directly to `RequirementVersion`/`ChangeRequestVersion`. Every requirement/CR edit already creates a new version row (C-A-02/C-A-09), so custom field values automatically get the same point-in-time history for free.
- **A change request's `custom_fields` payload is validated against `CustomFieldEntityKind.REQUIREMENT` definitions, not `CHANGE_REQUEST` definitions.** These values represent proposed attribute values for the requirement being created/modified (mirroring `proposed_name`/`proposed_reasoning`) and are copied onto the requirement's version on approval — so they must be validated against the schema that governs requirements, not change requests. A separate `CustomFieldEntityKind.CHANGE_REQUEST` kind still exists in the data model for attributes describing the change request itself (e.g. an "urgency" field), but no workflow currently collects or consumes those values; this is a deliberate, documented scope gap rather than an oversight.
- **Terminology overrides are a fixed, closed set of keys, not a freeform key-value store.** `TERMINOLOGY_KEYS` in `backend/app/schemas/project.py` enumerates exactly the overridable nouns (project, stage, component, category, requirement, change_request); the update endpoint rejects unknown keys. An open-ended per-project vocabulary would require every frontend string to become dynamically templated, which is a much larger change than C-C-03 actually asks for.

### Templates

- **`clone_project()` deep-copies configuration and requirements, resetting workflow state.** Cloning a template project (C-E-05) copies components, categories, custom field definitions, groups and group memberships, and requirements (reset to `draft` status, with any project-specific custom field ids remapped to the new project's definitions) — but never copies change requests, comments, or audit history, since those describe the *history* of the template project, not a starting configuration for a new one.
- **PM auto-assignment has an explicit fallback when cloning.** C-U-10 says the creator is normally added to the Project Managers group automatically; C-E-05 says this doesn't apply when creating from a template (groups/members are copied from the template instead). If that copy leaves the new project with zero managers (e.g. the template's manager group had no members), the creator is still added as a fallback so C-U-08 ("every project must have a manager") can never be violated by a template that happens to be manager-less.

### Auditing and attribution

- **Creator reassignment (C-A-11/C-A-12) is restricted to project managers, checked server-side at creation time.** `POST .../requirements` and `POST .../change-requests` accept an optional `creator_id`; if present, the caller must hold the `project_manager` role (or be a server admin) or the request is rejected with 403 — anyone who can create a requirement/CR at all can still create one attributed to themselves, but only a manager can attribute it to someone else.
- **The project changes-over-time view (C-A-10) excludes discussion comments by default.** `get_project_changes()` merges audit events, requirement version history, and change-request version history into one timeline; `ReviewComment` rows are only included when the caller explicitly passes `include_comments=true`, consistent with the Ossa v1 decision that discussion threads are not the change log.

### UI discovery

- **Favourite projects sort ahead of everything else, then alphabetically.** `GET /api/v1/projects` computes the caller's favourited project ids and sorts the response with `(not is_favorite, name.lower())` as the key, so favourites always appear as a contiguous block at the top regardless of the `role`/`stage_status`/`search` filters also applied. Favouriting is a simple per-user join table (`FavoriteProject`) with `PUT`/`DELETE .../favorite` endpoints, not a field on `Project` itself, since it's user-specific rather than project-wide state.

### Logging

- **`alembic/env.py`'s `fileConfig()` call now passes `disable_existing_loggers=False`.** Migrations run automatically on every app startup (see Infrastructure, above), which means `logging.config.fileConfig(alembic.ini)` also runs on every startup, *after* uvicorn has already configured its own `uvicorn`/`uvicorn.error`/`uvicorn.access` loggers. `fileConfig()` defaults to `disable_existing_loggers=True`, which sets `.disabled = True` on every logger not explicitly listed in `alembic.ini`'s `[loggers]` section — silently killing uvicorn's access/error logging (and every `logging.getLogger(__name__)` logger elsewhere in the app) for the entire life of the process. This was a real, confirmed bug, verified via the raw container JSON log file having zero lines beyond the startup banner despite heavy real traffic. It also happened to be why the database bug below went undiagnosed for a while — there was no traceback to read. After the fix, `docker compose logs backend` shows a normal per-request access log and any real exception traceback.

### Database: the test suite was wiping the live database

- **Root cause: `tests/conftest.py` used `os.environ.setdefault("DATABASE_URL", ".../reqtrack_test")`, which is a no-op whenever `DATABASE_URL` is already set — and it always is inside the `backend` service container, to the real application database (`postgresql://reqtrack:reqtrack@db:5432/reqtrack`).** The test suite's session-scoped `_schema` fixture runs `DROP SCHEMA public CASCADE` / `CREATE SCHEMA public` at both session start *and* session teardown. Running the suite via `docker compose exec backend pytest` — a completely reasonable-looking command — was therefore dropping the real dev/demo database's entire schema twice per run, leaving it with **no tables at all** after the run finished (the teardown drop doesn't re-run migrations). The running app process kept its connection pool open, so it kept accepting requests, but every query then failed with `psycopg2.errors.UndefinedTable: relation "users" does not exist` — a hard 500 on every authenticated endpoint, while `/health`'s own lightweight check happened to still report OK. This was misdiagnosed at the time as a vague "connection pool wedge," fixed only by restarting the backend (which re-runs migrations and re-bootstraps the admin user, masking the real cause and quietly losing whatever demo data existed).
- **Fix: a hard startup guard in `tests/conftest.py`.** After resolving `DATABASE_URL`, the conftest module now asserts the resolved database name ends in `_test` and raises `RuntimeError` immediately if not, before the destructive session fixture can run. This makes the failure mode "the test suite refuses to start, with a clear error" instead of "the test suite silently destroys whatever database it happens to be pointed at." `setdefault` is still used first, purely as a convenience default for runners that haven't set `DATABASE_URL` at all.
- **Structural fix: tests run against their own isolated stack, not by `exec`-ing into the application container.** The root `docker-compose.yml` is now the production-oriented stack (no test database anywhere near it); `tests/container/docker-compose.yml` is a separate, fully isolated stack whose `backend` service's `DATABASE_URL` already points at `reqtrack_test` — so `docker compose exec backend pytest` there just works, with the safety guard confirming it rather than needing to catch a mistake.
- **The `_schema` fixture no longer drops the schema at session teardown, only at session start.** The teardown drop was redundant (the *next* session's own setup already guarantees a clean slate) and, once tests could share a database with a live app in `tests/container/`, actively harmful: it left that app's own backend with zero tables until its next restart. Removing the teardown drop means a live app sharing the test database instead finds its tables intact but empty after a test run (a clean `401` on login, since the bootstrap admin was truncated along with everything else) rather than a `relation "..." does not exist` `500`. `docker compose restart backend` (which re-runs migrations and re-bootstraps the admin) recovers it either way — this is a documented, expected part of using the shared dev/test stack for both manual testing and pytest, not a bug.

### Frontend component testing (Storybook)

- **Storybook (`frontend/.storybook/`) plus `@storybook/addon-vitest` for automated story tests**, not just a manual component browser. `npm run storybook` gives a visual explorer; `npm run test-storybook` runs every story as a real headless-Chromium test via Vitest's Playwright browser provider, so a story that fails to render or fails an assertion in its `play` function fails CI the same as any other test — a component explorer nobody automates checking against tends to silently rot.
- **The preview's `withTheme` decorator applies the exact same mechanism the real app uses** (a `data-theme` attribute on `<html>`, read by `src/styles/theme.css`'s CSS variables) rather than a Storybook-specific theming shim, so stories render with the actual product palette. A toolbar toggle switches themes while browsing; `LightTheme`/`DarkTheme` story exports pin `globals: { theme: ... }` explicitly so both are exercised by `test-storybook` on every run regardless of whatever theme was last selected in the UI (U-U-01: light and dark are both first-class, not just supported).

### Testing and verification process notes

- **The Docker Compose `backend` and `frontend` services do not bind-mount source** — they `COPY` the source at build time. Editing backend or frontend code and then testing against the *already-running* containers (`docker compose exec backend pytest`, or exercising the UI at localhost:3000) silently tests stale code until `docker compose build <service> && docker compose up -d <service>` is run. This tripped up Pelion v2 verification more than once (a backend test file and a frontend UI change were both validated against stale containers before the rebuild step was remembered) — worth calling out explicitly since the mistake produces no error, just misleading "it works" or "it's broken" signals from the wrong code.
- **Password-changing Playwright steps must revert via a direct API call in a `finally` block, not a second UI round-trip.** The new Pelion v2 E2E spec (`tests/playwright/tests/pelion-v2.spec.ts`) changes the shared bootstrap admin's password to exercise the password-changed notification, then must restore it, since `golden-path.spec.ts` and every future run depend on the fixed bootstrap password staying valid. Reverting through a second UI form submission proved flaky (a `page.reload()` issued immediately after clicking "Change password" can abort the still in-flight request before the browser sends it); reverting via `page.request.post(...)` with the token read out of `localStorage` is synchronous from the test's perspective and doesn't depend on any UI timing. The forward change also now explicitly awaits the `change-password` network response (`page.waitForResponse`) before doing anything else, for the same reason.
- **The favourites E2E assertion clears any pre-existing favourites via the API before asserting sort order.** Because favourite state persists in the shared dev database across repeated runs of the same spec, asserting "this project is now first" is only deterministic if the test first removes whatever an earlier run left favourited.

### Requirements audit fixes

A five-way parallel code-reading audit against every Ossa (v1) / Pelion (v2) row in `docs/requirements.md` found 23 real gaps (86 of 109 requirements were already fully met). All 23 were fixed in one pass; C-U-07 (a real OAuth/SSO backend) and C-U-15 (an actual multi-org membership operational path) were explicitly left as documented seams per the user's own scope call, since both are substantial new features rather than bug fixes.

- **I-M-05 (most significant fix): the server-admin role no longer bypasses any organisation/project data access.** Every RBAC dependency in `services/rbac.py` (`require_org_role`, `require_project_role`, `require_project_view`, `require_project_manage`) and every scattered inline `is_server_admin` check across `routers/{orgs,projects,requirements,change_requests,files,ws}.py` previously granted an unconditional bypass — directly contradicting I-M-05's explicit "does not give access to data within organisations" clarification. The fix is not a blanket removal: one dependency, `require_org_admin_or_server_admin`, exists specifically for the one documented carve-out (server admin creating the *initial* user of a newly created org, per I-M-05's own clarification) and is used only by `create_org_user`. `list_organizations`/`get_organization` deliberately keep a server-admin bypass since `OrganizationOut` is thin directory metadata (id/name/logo), not "data within the organisation," and the server admin needs to see an org exists to complete the one capability the requirement grants. Tests that relied on the old bypass to act inside a second org (`test_cannot_nest_org_group_from_another_organization`, `test_report_rejects_resource_from_another_organization`) were updated to create a genuine org_admin user in that org first, via a new `create_org_admin_in()` conftest helper — this mirrors the real deployment flow the fix now enforces rather than reintroducing a bypass.
- **A genuine, previously-undetected runtime bug was caught by configuring ruff (N-E-04): `services/rbac.py`'s nested-org-group-in-project-group role resolution used `OrgGroup` in a live query but never imported it**, so `get_effective_project_roles()` raised `NameError` whenever that branch executed — meaning C-U-12 ("organisation groups can be used inside project groups") was completely broken for its one legitimate scenario. No existing test exercised a valid same-organisation nesting (only the cross-org rejection case), so this shipped unnoticed. Fixed with the missing import plus a new regression test (`test_org_group_nested_in_project_group_grants_effective_role`) that actually exercises the nested-resolution path.
- **C-U-02 ("all project users must be an organisation user") is enforced with a small `_require_user_in_org()` check** in `assign_project_role` and `add_project_group_member` (routers/projects.py), rather than only being documented as design intent in a comment as before.
- **C-A-05 project-group audit logging now mirrors the org-group side.** `create_project_group`, `add_project_group_member`, `remove_project_group_member`, `assign_project_role`, and `revoke_project_role` all gained `log_event` calls; previously only the equivalent organisation-group endpoints did.
- **C-U-08's "a project must always have ≥1 manager" guard now also applies to group-based removal**, not just direct role revocation — `remove_project_group_member` checks `get_project_managers()` the same way `revoke_project_role` already did, using the same simplified "is this the current sole manager" check (not a full per-path simulation) for consistency with the existing logic.
- **C-N-01's `STAGE_SCOPING` notification now actually fires.** The type existed in the enum and the frontend string table but was never in `_STAGE_NOTIFICATION_TYPES`. Since a project's very first stage is created directly in `create_project()` (never through `create_stage`/`transition_stage`, the only two callers of the notify helper), every real caller of `_notify_stage_transition` is, by construction, never the "brand new project" case the requirement excludes — so adding the entry to the map was sufficient; `create_stage` was also updated to actually call the notify helper (and to log the real actor instead of `None`, a small pre-existing side gap).
- **C-E-04's org default-template setting now actually affects project creation.** `create_project()` falls back to `Organization.default_template_project_id` when the caller omits `template_project_id`; the frontend's "New project" form pre-selects the org's default in its template dropdown so the choice is visible and still overridable. Known limitation, documented rather than solved with a schema change: selecting "None (blank project)" in the UI sends the same `null` as never touching the field, so it currently still resolves to the org default when one is configured — a true override would need a distinct sentinel value in `ProjectCreate`, judged out of proportion for this pass.
- **C-U-16 (org admin locking a user's display name) gained the missing write path**: `PUT /orgs/{id}/users/{user_id}/display-name-lock` plus a lock/unlock toggle in the Org Admin users table. Enforcement already existed; only the ability to *set* the lock was missing.
- **I-M-06: a new `PUT /api/v1/system/users/{user_id}/server-admin` endpoint lets an existing server admin grant or revoke the role on another user**, matching the requirement's literal wording ("this user can assign any user on the system, the server admin permission role") — previously `is_server_admin` was only ever set once, at bootstrap, with no way to extend it afterward.
- **I-A-04: `WEBSOCKET_ENABLED` (default `true`) controls whether `ws.router` is mounted at all** in `main.py`, rather than it always being mounted with no way to disable it.
- **C-A-07 IP geolocation is implemented as a background task, not an inline call**, so it can never add latency to or block the login response. `services/geoip.py` resolves an IP's approximate location via a free, keyless third-party API (`ip-api.com`) only when `GEOIP_LOOKUP_ENABLED=true` (default `false`, since this is a real external dependency and privacy trade-off the user must opt into) and only for addresses outside `GEOIP_LOOKUP_EXCLUDE_CIDRS` (defaults to the standard private/loopback ranges). `routers/auth.py`'s `login` schedules `resolve_and_store_login_location` via FastAPI `BackgroundTasks` *after* the response is built, updating the `LoginEvent` row in a fresh DB session. Every failure mode (disabled, excluded address, network error, timeout) resolves to doing nothing — never an exception that could affect login.
- **U-P-06 pagination is opt-in, not a forced page size**, preserving C-G-05 ("no artificial limit"): the requirements/projects/change-requests list endpoints accept optional `limit`/`offset` and report the pre-slice total via an `X-Total-Count` response header (added to `CORSMiddleware`'s `expose_headers`, since custom response headers aren't visible to browser JS otherwise); omitting both still returns every match, unchanged from before. The frontend's three list pages use a new `api.getPage()` client method and a shared `<LoadMoreButton>` component for simple incremental "load more" pagination at 30 items/page.
- **U-P-05's file count is scoped to requirement attachments within the project, not organisation-wide shared resources** — `ProjectMetricsOut.file_count` counts distinct `FileAsset` rows reachable via `RequirementFile` for the project's own requirements, since shared resources aren't scoped to a single project and counting them would conflate two different things the requirement's "number of files in project" wording doesn't ask for.
- **C-C-03 terminology overrides are applied through a new `TerminologyProvider` React context** (`frontend/src/context/TerminologyContext.tsx`), fetched once per project and provided from `Layout.tsx` down to every page. Applied to the nav labels and the Requirements/Change-Requests page titles and "New X" buttons — deliberately not to every single occurrence of "requirement"/"stage"/etc. across the whole UI (dozens of call sites), which would be disproportionate scope for this pass. Pluralisation is a naive `+"s"` (`useTermPlural`), which reads correctly for the regular-noun default terms but not for an override with an irregular plural (a project would need to type the plural form directly as its override in that case).
- **U-U-03's landing preference is now actually read at login.** `LoginPage.tsx`'s `resolveLandingPath()` sends the user to a specific project id, the overview list, or (for "auto") the sole accessible project if there's exactly one — previously this was stored but login always hardcoded `navigate("/projects")`. The Preferences UI gained a "which project" picker for the specific-project case; `AuthContext`'s `login`/`verify2fa` now return the resolved `User` so the redirect can be computed immediately without waiting on a state re-render.
- **U-C-02: the organisation logo now renders in the app's main header**, not only on the Org Admin settings page, via the same `TerminologyProvider` fetch (extended to also carry `orgLogoFileId`) — shown next to the text wordmark whenever a project (and therefore an organisation) is in scope.
- **U-U-02: the flagged hardcoded strings were moved into the i18n table**, and one adjacent real bug was fixed in passing — the "new requirement" form's reasoning textarea was using the `status` placeholder string instead of `reasoning`.
- **I-M-04: `scripts/backup.sh`/`restore.sh` now also cover local file storage.** The root `docker-compose.yml` previously had no volume for `STORAGE_LOCAL_DIR` at all — despite `docs/deployment.md` already warning "this directory must be a persistent volume" — so a `STORAGE_BACKEND=local` deployment silently lost files on container recreation. Fixed with a named `reqtrack_local_files` volume, and `backup.sh` now archives it (`docker compose exec backend tar czf ...`) whenever the running backend's `STORAGE_BACKEND` is `local`, alongside the existing `pg_dump`. `STORAGE_BACKEND=s3` (the Compose default) is unaffected — MinIO's own backup/replication tooling is still the right approach there.
- **N-E-04/N-E-07: ruff (backend) and ESLint flat config (frontend) are now configured and pass with zero errors**, not previously configured at all. Both are intentionally mechanical gates (pycodestyle/pyflakes/import-sort/modernise/bugbear for Python; TypeScript + React Hooks + Fast Refresh recommended rules for TS) rather than exhaustive Google style guide enforcement — full docstring coverage (`D` rules) is deliberately not part of the ruff config; see N-E-05 below for why that's a separate, narrower pass instead of a repo-wide mechanical gate. `ruff`'s line-length is set to 150 (the codebase's existing max is 146) rather than the stricter 80-char Google default, to avoid a disruptive one-off reformat of already-written code. `B008` (function-call-in-default-argument) is disabled since it flags FastAPI's `Depends(...)` dependency-injection idiom, which is the correct pattern, not a bug.

Two nested FastAPI dependency closures got a one-line "see the enclosing factory's docstring" instead of a duplicate full docstring, since the enclosing `require_org_role`/`require_project_role` factory functions already fully document the returned closure's behavior.

## Multi-org, multi-persona E2E workflow suite

Full catalogue and rationale in [docs/e2e-workflows.md](e2e-workflows.md); summarized here for the decisions log.

- **Bulk seed data goes through the real API, driven by a standalone script, not direct DB writes.** `backend/scripts/seed_e2e_dataset.py` authenticates as personas and calls the same endpoints the UI does, so seeding exercises the actual validated code paths rather than risking a fixture that's inconsistent with real invariants (unique requirement codes, auto-PM-on-project-creation, etc.). Originally, one exception — deleting the zero-org server-admin persona's `user_org_roles` row directly via SQL — was needed because no product endpoint let a user leave an organisation at all. That gap is now closed (see the next bullet), so the script has zero direct-DB steps: even that persona's departure from its one org is now a real API call, `DELETE /orgs/{id}/membership`, which the seed script's own successful run exercises as a live test of the new endpoint.
- **Self-service "leave organisation" (`DELETE /api/v1/orgs/{organization_id}/membership`).** Found missing while building the E2E suite above; the user asked for it to be built once the suite was otherwise complete. Deliberately narrower than `deactivate_org_user`'s C-U-09 fallback (which reassigns the *acting admin* as a project's new manager when removing someone else): here the caller is the one leaving, so there's no natural recipient for an orphaned manager/admin role to fall back to. Rather than guessing who should inherit it, the endpoint refuses (409) if leaving would strip the org of its last `org_admin`, or leave any of its projects with zero managers, and asks the caller to reassign those roles first. Frontend: a "Leave organisation" button on `OrgAdminPage.tsx`, visible to any member of the org being viewed (not gated to admins, since any role can leave). Tests: `backend/tests/test_rbac.py`.
- **A server admin can only ever be the first org_admin of a *brand-new* organisation, never granted a role in an org they don't already belong to.** `create_org_user`'s server-admin carve-out (`require_org_admin_or_server_admin`, per I-M-05 above) only covers creating a new user; `assign_org_role` requires a genuine `org_admin` caller with no carve-out. This is existing, correct behavior — flagged here because it meant the seed script needed a throwaway "bootstrap helper" user as a second org's first admin, purely to hand off a role to the real persona, mirroring how a human admin handoff would actually work.
- **Change-request Approve/Reject and requirement Archive/edit-form visibility now check the viewer's actual project role, not just the entity's state.** Found while building the change-request approval-separation workflow: both controls were rendered for any project member once a CR was submitted or a requirement unlocked, relying entirely on the backend's 403 to stop the click — correct security-wise, but not a working workflow for the user who sees a button they can never use. Fixed with a new `frontend/src/hooks/useMyProjectRoles.ts` (reads `ProjectListItemOut.my_roles`, the cheapest existing source of this without a new endpoint) in `ChangeRequestDetailPage.tsx` and `RequirementDetailPage.tsx`. The same pattern likely exists elsewhere (e.g. the Requirements list's "New Requirement" button); left as a documented gap rather than a repo-wide pass, since only these two were exercised by this suite's own workflows.

### Full hardening/validation pass

A follow-up parallel security audit (three agents: backend auth/authz, backend input-validation/injection, frontend) covering the whole codebase, not just this session's diff, per the user's explicit request. Two real, high-confidence findings, both fixed and covered by new regression tests; everything else came back clean (RBAC/IDOR boundaries, JWT/session handling, file-path/SSRF/deserialization surfaces, and the frontend's DOM-sink surface were all specifically checked and found sound).

- **Stored XSS via unrestricted uploaded-file Content-Type served inline (High).** `GET /api/v1/files/{file_id}` (`backend/app/routers/files.py`) served every file with the uploader's client-claimed `Content-Type` (never validated against the actual bytes) and `Content-Disposition: inline` — any user with upload rights (a low bar: any project editor for requirement attachments, any authenticated user for their own avatar) could upload a `text/html`/`image/svg+xml` payload that executes as a same-origin page when a more privileged user opens the link, with immediate access to this same endpoint's `?token=` query-param auth and `localStorage`. Fixed by restricting `inline` disposition to a small safe-to-render allowlist (`image/png`, `image/jpeg`, `image/gif`, `image/webp`, `image/x-icon`, `application/pdf` — SVG deliberately excluded since it can embed scripts too) and forcing `attachment` for everything else, plus an `X-Content-Type-Options: nosniff` header on every response from this endpoint. Test: `backend/tests/test_files.py::test_html_attachment_is_forced_to_download_not_rendered_inline`.
- **CSV formula/DDE injection in the requirements export (Medium).** `generate_csv_report` (`backend/app/services/reports.py`) wrote user-editable requirement fields (name, reasoning, clarification, etc.) straight into CSV cells; a value starting with `=`, `+`, `-`, `@`, tab, or CR is interpreted as a formula by Excel/LibreOffice on open — and this export exists specifically for spreadsheet review (R-F-02), making that a realistic workflow, not a theoretical one. Fixed with a `_csv_safe()` helper that prefixes any such value with `'` (stripped from display, never executed) before writing, per OWASP's standard CSV-injection mitigation. Test: `backend/tests/test_reports.py::test_csv_report_neutralizes_formula_injection`.
- **`leave_organization` didn't clean up `OrgGroupMember` rows, and its sole-manager guard couldn't see nested-org-group-derived managers.** Caught during self-review of the new endpoint (not the parallel audit): project access can be granted through an org group nested into a project group (C-U-12), and `get_project_managers` deliberately only resolves *direct* managers (see its own docstring) — so the original implementation could let a user "leave" an org while silently retaining full project access, including manager rights, through a still-active, still-authenticated session (deactivation-based removal doesn't have this exposure, since `is_active=False` blocks all further API access regardless). Fixed by also deleting the caller's `OrgGroupMember` rows for the organisation's groups, and by extending the sole-manager check to fold in `get_effective_project_roles` (which does resolve nested groups) alongside the existing direct-manager check. Note: the "blocking" branch of this fix is currently unreachable through the API in practice — `revoke_project_role`/`remove_project_group_member` independently refuse to remove a project's last *direct* manager using the same nested-group-blind resolver, so a project can never actually reach "zero direct managers, one nested-group manager" today — but it's kept as correct defense-in-depth, documented in `backend/tests/test_rbac.py::test_last_direct_manager_cannot_be_revoked_even_with_a_nested_group_backup`.

### Round 2 hardening: races, session lifecycle, infrastructure

A deeper pass per the user's explicit "go deeper" request: business-logic race conditions, session/credential lifecycle, and infrastructure/config, plus re-examining prior areas more critically. Custom fields and the report data-flow were re-audited and came back clean (no new findings). All fixes below are covered by `backend/tests/test_rbac.py`, `backend/tests/test_user_security.py`, and the full Playwright suite; every backend test (141) and every Playwright spec (10) pass together against a freshly-reset database.

**Business-logic races (TOCTOU, closed with Postgres row locking via `.with_for_update()`):**

- **Change-request double-decision race** (`backend/app/routers/change_requests.py`). `decide_change_request` read the CR with a plain `db.get()`; two concurrent Approve/Reject calls on the same submitted CR could both pass the "is it still submitted" check before either commit landed, double-applying the decision's side effects. Fixed by selecting the row `with_for_update()` so the second concurrent request blocks until the first commits, then sees the now-decided state and is rejected.
- **Org/project manager-count races across four endpoints** (`revoke_project_role`, `remove_project_group_member` in `backend/app/routers/projects.py`; `deactivate_org_user`, and the new `leave_organization`, in `backend/app/routers/orgs.py`). Each independently counts remaining managers/admins before allowing a removal that would drop the count to zero, but without a lock, two concurrent removals of *different* managers could both read "count is 2, safe to remove" and both proceed, leaving zero. Fixed with new `lock_project_for_update`/`lock_organization_for_update` helpers in `backend/app/services/rbac.py`, called before each count check.
- **Stale-subscription content leak on role removal.** When a user's last role on a project was revoked (via any of the four endpoints above), their `Subscription` and `FavoriteProject` rows for that project's requirements/change-requests weren't cleaned up — since notification delivery doesn't re-check current access at send time, they'd keep receiving content updates for a project they'd just lost all visibility into. Fixed with `engagement.remove_subscriptions_and_favorites_for_projects`, called wherever a removal drops a user's effective project roles to empty.

**Session/credential lifecycle:**

- **No token revocation on password change or 2FA disable (High).** JWTs were purely stateless — changing your password (e.g. after suspecting a compromised session) or disabling 2FA didn't invalidate any token issued before the change; a stolen token kept working for its full remaining lifetime regardless. Fixed with `User.token_version`, an integer embedded in every token as the `tv` claim and checked for exact equality against the user's current value on every request (`app/deps.py`); `change_password`/`disable_2fa` increment it, deterministically invalidating every previously-issued token including the one used to make the change. A first attempt compared JWT `iat` against a `tokens_invalid_before` timestamp instead; it was rejected after testing turned up an inherent boundary bug — `iat` is only second-precision, so a token issued in the exact same second as its own revocation could compare as still-valid or (after truncating both sides to fix that) as already-expired-before-issuance, depending on which way the tie was broken. A version counter has no such ambiguity. Regression tests: `backend/tests/test_user_security.py::test_password_change_invalidates_the_old_token`, `::test_2fa_disable_invalidates_the_old_token`.
  - **Frontend fallout, found by re-running the Playwright suite after this fix:** `PreferencesPage.tsx`'s change-password/disable-2FA handlers kept using the now-dead token from `localStorage` for subsequent requests instead of expecting the session to end — the UI just silently broke (401s on reload) rather than prompting re-login. Fixed by having both handlers call `logout()` and redirect to `/login` with a "you've been signed out" message (`LoginPage.tsx` reads it from router state) immediately after a successful change, since the backend has already invalidated the session at that point regardless of what the frontend does.
- **Login response distinguished deactivated accounts from wrong passwords (Medium — user enumeration).** The login endpoint returned a distinct "This account is deactivated." message, and returned it *before* verifying the password — letting an attacker enumerate which emails are registered-but-deactivated accounts without knowing any password. Fixed in `backend/app/auth_backends/native.py`: password verification now always runs first (against a module-level dummy hash when the account doesn't exist or belongs to a different auth backend, to equalize timing with the real-account path), and every failure path returns the same generic `"Invalid email or password."`. Test: `backend/tests/test_user_security.py::test_login_error_does_not_distinguish_deactivated_from_wrong_password`.
- **WebSocket connections outlived their issuing token.** `backend/app/routers/ws.py`'s connection handler authenticated once at handshake and then held the connection open indefinitely — a token that expired, or was revoked via the `token_version` mechanism above, mid-session kept a live, fully-privileged socket open. Fixed by decoding the token's `exp` claim at handshake and checking it every 60 seconds in the receive loop, closing the connection (code 4401) once it's passed.

**Infrastructure/config:**

- **Weak default Postgres password in the production compose file.** Root `docker-compose.yml` fell back to a hardcoded `reqtrack` password if `POSTGRES_PASSWORD` wasn't set in the environment, in both the `db` service and the embedded `DATABASE_URL`. Fixed by switching both to Compose's fail-fast `${VAR:?message}` form, so a production deploy without an explicit password refuses to start rather than silently running with a guessable one. `docs/deployment.md` updated accordingly.
- **MinIO root credentials used directly by the backend.** The backend authenticates to MinIO/S3 storage with the root account rather than a scoped-down user — not auto-remediated (no code path to change), but documented as a deployment hardening step in `docs/deployment.md` with exact `mc admin user add`/`policy create`/`policy attach` commands to scope a dedicated bucket-only credential for production use.

**Re-audited, came back clean:** custom field value storage/rendering (no injection path — values are always parameterized or escaped the same way as other user content, per the round-1 ReportLab fix), the CSV/PDF report data-flow end to end (confirms the round-1 fixes still hold and no new sink was introduced since).

## Massif (v3)

Massif (v3) implements every Massif-tagged row in `docs/requirements.md` except the three enterprise-auth requirements each large enough to be their own project (E-U-01/E-U-02/E-P-02) — see below for how those were scoped instead. E-P-01 ("allow multiple organisations") required no new work: `Organization` has been a first-class multi-tenant model since Ossa (v1), and server admins have always been able to create additional organisations.

### Review scheduling (C-R-06, C-R-07, C-R-08, C-R-09, C-R-10)

`RequirementVersion` gains `review_date`, `review_lead_days`, `reviewer_id`, `review_reminder_sent_at` — placed on the versioned table, not the `Requirement` identity row, because C-R-06's clarification requires them to only change on creation or via a change request, the same CR-gated path every other content field already uses (`apply_new_version`/`create_requirement` in `backend/app/services/requirements.py` gained matching parameters, with the same `*_explicitly_set` disambiguation pattern already established for `target_stage_id`). A new `RequirementReview` table (`backend/app/models/requirement.py`) records outcomes (C-R-07); the "due for review" definition (`backend/app/services/reviews.py`) is `review_date` in the past *and* no `RequirementReview` recorded since that date — this lets a requirement drop off the due list once reviewed without ever mutating `review_date` itself outside a change request, satisfying the immutability clarification literally rather than by approximation.

A new APScheduler job (`backend/app/services/scheduler.py`, `send_due_review_reminders`) sends the C-R-08 reminder once per review cycle (tracked via `review_reminder_sent_at`, reset to unset on every new version so an unrelated edit can't suppress a future reminder), to the assigned reviewer or every project manager if none is assigned.

### Change-request tasks and stakeholder voting (C-R-02, C-R-03, C-R-04)

`ChangeRequestTask` and `ChangeRequestVote` (`backend/app/models/change_request.py`), both scoped to project-manager creation/decision rights except that a task's own assignee may toggle `is_done` without manager rights. Voting is explicitly advisory: `ChangeRequestVote` never touches `ChangeRequest.status`, and `decide_change_request`'s existing project-manager-only gate is completely unchanged — the vote tally is just additional visible input the decision-maker sees alongside the CR, per C-R-03's own reasoning ("promoting collaborative decision-making," not "replacing the decision").

### Stage review deadlines and "assumed approval" (C-R-05)

`ProjectStage` gains `review_deadline`; a new `StageReviewResponse` table records explicit stakeholder approve/reject responses per review cycle (cleared when a new deadline is set, so a later cycle isn't contaminated by an earlier one's responses). The daily scheduler sweep (`auto_approve_overdue_stage_reviews` in `backend/app/services/stages.py`) auto-approves a stage once its deadline passes, *unless* at least one stakeholder explicitly rejected — matching C-R-05's literal wording ("if they have not provided a response, then it's assumed they have approved") while never silently overriding a raised objection. This asymmetric policy (silence = approve, objection = block) was flagged to the user as the one substantive judgment call in the design and confirmed before implementation.

### Completion tracking (C-P-02, C-P-03)

`ProjectStage` gains `completed_at`/`completed_by` (mirroring the existing `approved_at`/`approved_by` pattern). Rather than adding parallel `is_completed` fields to `Requirement`, C-P-03 reuses `RequirementStatus.COMPLETED` — an enum value that already existed in the codebase (already locked requirement edits via `LOCKED_STATUSES`, already counted in dashboard/report status breakdowns) but had no dedicated endpoint reaching it. `POST /requirements/{id}/complete` transitions `APPROVED → COMPLETED` directly (bypassing the change-request requirement, like archiving already does, since this is a status transition a project manager makes directly rather than content requiring review) — "who/when" is captured by the resulting version's existing `created_by`/`created_at`, with no new columns needed. Stage completion (`POST /stages/{id}/complete`) takes an explicit `cascade_to_requirements` flag, defaulting to `false` per C-P-02's clarification.

### User directory with access-review filters (C-A-13)

Originally scoped as a dedicated "access review" endpoint; broadened during planning per explicit feedback into query filters (`stale_since_days`, `never_logged_in`, `has_2fa`, `org_role`, `has_project_access`) on the *existing* `GET /orgs/{organization_id}/users` member-listing endpoint, plus a new server-admin-only `GET /system/users` with `no_org_membership` (C-A-13's literal "orphaned account" clarification). Authorization was called out explicitly given this codebase's history of under-scoped org/project checks (see the round-1 hardening section above): the org-scoped filters require `require_org_role(OrgRole.ORG_ADMIN)` resolved against the specific `{organization_id}` in the path (not "an org admin somewhere"), while the unfiltered base listing keeps its existing member-level access; `GET /system/users` requires `require_server_admin` with no org-admin fallback of any kind and deliberately omits `org_role`/`has_project_access` from its response, since those only have meaning scoped to one organisation and would otherwise leak cross-tenant membership through a nominally tenant-blind endpoint (I-M-05). Negative-path tests for all three boundaries live in `backend/tests/test_access_review.py`.

### Selectable report templates (R-G-05)

R-G-05's row in `docs/requirements.md` has the same title text as R-G-04 but different reasoning (branding/presentation vs. shared-resource sections) — read as a documentation copy-paste artifact rather than a literal duplicate, confirmed with the user, who chose "selectable report templates" over the alternative reading of "just render the org logo." `ReportTemplate` (org-scoped, matching how the org logo already works) stores an accent colour, a cover-page toggle, a logo toggle, and footer text; `generate_pdf_report` (`backend/app/services/reports.py`) gained an optional `branding: ReportBranding` parameter threading these into the existing ReportLab styling, falling back to today's plain output when no template is selected.

### SSO login, tested against a real Keycloak instance (E-U-01, E-P-03)

See [enterprise-integration.md](enterprise-integration.md) for the full design. In brief: a real OIDC authorization-code flow (`backend/app/routers/auth_oidc.py`), provider-agnostic via standard discovery, tested end-to-end with a real Keycloak container in `tests/container/docker-compose.yml` and a Playwright spec (`tests/playwright/tests/e2e-workflows/sso.spec.ts`) that drives an actual browser through Keycloak's own login form — not just designed on paper, per the user's explicit instruction that this specifically be tested, not merely documented. The provisioning logic it's built on (`backend/app/services/oidc_provisioning.py`) is written to be reused directly by the not-yet-built SCIM path (E-U-02), so that blueprint isn't speculative.

A genuine Docker-networking problem surfaced during testing — the backend reaches Keycloak via the Compose-internal hostname, but a real browser can only reach the published port, and both must resolve to the *same* issuer URL for token validation to work — resolved via Keycloak's own hostname-pinning config plus a narrowly-scoped, dev/test-only backend setting (`OIDC_INTERNAL_BASE_URL_OVERRIDE`) that rewrites only the backend's own outbound calls, never anything the browser sees. Left unset (a no-op) in the production compose file, since a real IdP's public URL is normally reachable from the backend directly.

**Follow-up, same session:** added a per-org `oidc_required_group` access gate, deliberately separate from `sso_group_mappings` — the mapping list decides *which* role a successfully-admitted user gets, while `oidc_required_group` decides *whether* they're admitted at all, checked in `oidc_callback` before any local account is provisioned or token issued (`services/oidc_provisioning.meets_required_group`). A user outside the required group who authenticates successfully at the IdP is redirected to `/oidc-complete?error=not_provisioned` and shown "Your organisation has not provisioned you access." — the refusal is this app's own policy layered on top of a genuinely successful IdP login, not an IdP-side failure, so no re-registration is needed once an admin adds them to the group. Extended `sso.spec.ts` with two more real-Keycloak-driven tests (blocked user denied, admitted user still gets in) rather than only unit-testing `meets_required_group` in isolation, consistent with the standing instruction that SSO behaviour be proven against a real IdP. One implementation snag: the blocked-then-admitted flow was originally written as two `test.step`s sharing one browser context, which failed because Keycloak's own SSO session (not this app's) persisted across steps and silently reused the first (blocked) user's session instead of showing a fresh login form for the second user — fixed by splitting into two separate `test()` blocks, each with Playwright's default fresh browser context, matching the pattern the first two SSO tests already used successfully.

E-U-02 (SCIM) and E-P-02 (a separate-port provisioning API) were scoped out of this pass — each is effectively its own project — and are covered as an implementable blueprint in `enterprise-integration.md` instead, per the user's explicit choice during planning.

### Massif (v3) hardening pass

Following this project's standing security-review workflow (see the round-1 "Security hardening pass" section above), the new Massif (v3) code — chiefly the OIDC subsystem, since it's the largest new externally-reachable attack surface added this phase — was put through the same three-stage identify → independently re-verify → report process. Four findings survived at confidence ≥8; all four were fixed and the full verification sequence (184 backend tests, 14 Playwright specs including all 4 SSO tests) re-run clean afterward.

**SSRF via org-configurable OIDC endpoints (High).** `Organization.oidc_issuer_url` is set by an org admin, not a server admin, and every OIDC step (`discover`, the token exchange, JWKS fetch) makes an outbound HTTP call built from it or from values returned by *its* discovery document (`token_endpoint`, `jwks_uri`) — so a malicious discovery document could redirect later calls to an entirely different host than the one an admin configured. Fixed in `backend/app/services/oidc_client.py` with `_assert_safe_external_url`, called before every outbound fetch: resolves the hostname via `socket.getaddrinfo` and rejects any resolved address that isn't `ipaddress.is_global` (blocks loopback, link-local, private ranges, and DNS-rebinding-style redirects to internal services), not just a naive hostname-string check. Skipped only when `oidc_internal_base_url_override` is configured (the dev/test-only Keycloak-networking escape hatch above), since that setting exists specifically to point the backend at an internal, non-public address on purpose. Unit-tested directly (no network calls, literal-IP hostnames) in `backend/tests/test_oidc_client.py`.

**Follow-up, raised by the user:** a genuinely self-hosted IdP (on-prem Keycloak/Authentik with no public IP, common on a corporate LAN/VPC) would be rejected by this guard by default — it's indistinguishable from an attacker-controlled internal target from the guard's point of view. Rather than weakening the default, added a second, deployment-level (not per-org) opt-in: `oidc_allow_private_network_targets` (`OIDC_ALLOW_PRIVATE_NETWORK_TARGETS` env var, default `false`), which disables the public-IP check entirely when set. Documented as a blanket, deployment-wide allow that should only be enabled when every org sharing the deployment is trusted not to point its issuer at the deployment's own internal infrastructure — appropriate for single-tenant or fully-trusted-tenant deployments, not one serving mutually-untrusted organisations. See [enterprise-integration.md](enterprise-integration.md).

**`external_subject` cross-issuer collision (proactive, sub-8 confidence but fixed anyway).** The OIDC spec only guarantees `sub` uniqueness *within a single issuer*; matching on `external_subject` alone (as originally implemented) meant two different, unrelated identity providers asserting the same raw subject string would resolve to the same local account. Fixed by adding `User.oidc_issuer` and matching on `(external_subject, oidc_issuer)` together in `find_or_provision_user` (`backend/app/services/oidc_provisioning.py`); covered by a new regression test asserting two different issuers with an identical `sub` value provision two distinct accounts.

**`last_login_at`/`is_2fa_enabled` info leak on the broadened user-directory endpoint (Medium).** The C-A-13 filter work above correctly gated the org-scoped *filters* to org admins, but the endpoint's response body was populating these two fields for every caller regardless of admin status — meaning a plain org member could learn any other member's 2FA status and last-login timestamp just by calling the existing unfiltered listing. Fixed in `backend/app/routers/orgs.py`'s `list_org_users` by gating both fields on the same `is_admin` check already used for the filters, rather than only gating the filters themselves.

**Login-CSRF / session-fixation via a trusted callback URL (Medium).** `OidcCompletePage.tsx` originally accepted any `token` value found in its own URL with no proof it belonged to the current browser's own in-flight login — an attacker who completes their own legitimate SSO or native login could hand a victim a crafted `/oidc-complete?token=...` link and silently log the victim's browser into the attacker's account. Fixed by having the frontend generate a random nonce and store it in `sessionStorage` *before* navigating to the login-start endpoint (`OrgLoginPage.generateClientNonce`); the backend round-trips it through the signed `state` parameter (`security.create_oidc_state_token`, now `(organization_id, client_nonce)`) and the eventual callback redirect, and `OidcCompletePage` refuses to accept a token whose nonce doesn't match what it itself stashed. As a second, related improvement made at the same time: the token handoff moved from the query string (`?token=...`, which proxies commonly log and which persists in browser history) to the URL fragment (`#token=...`, never transmitted to any server over HTTP), cleared from the visible URL via `history.replaceState` immediately after being read.

### Playwright flakiness surfaced (not introduced) by this pass

Adding new nav links ("Requirements due for review," "My reviews due") and new advisory-action buttons ("Vote to approve"/"Vote to reject," stage review-response "Approve"/"Reject") exposed several pre-existing Playwright specs using loose, non-exact `getByText`/`getByRole(..., {name})` locators that happened to still be unique before this pass but are legitimate substring/text matches against the new UI. Fixed by switching the affected assertions to `exact: true` or role-scoped locators (`golden-path.spec.ts`, `mockup-engagement.spec.ts`, `pelion-v2.spec.ts`, `e2e-workflows/change-request-approval-separation.spec.ts`). Separately, three specs' "New project" step relied on the org picker defaulting to the correct organisation, which broke once the E2E seed script's three additional organisations sort alphabetically before "Default Organization" — fixed by selecting the org explicitly, using the project's already-established `toContainText(expected option)` wait pattern (stronger than a bare `not.toHaveCount(0)`, which can be satisfied by an unrelated combobox elsewhere on the page before the real one has even mounted).
